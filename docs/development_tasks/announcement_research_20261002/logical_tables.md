# 公告结构化逻辑表草案

这是字段设计说明，不是 DDL，也没有创建表。配合 [业务分类与流程方案](classification_and_extraction_plan.md) 阅读。模型只输出新增的语义抽取结果，系统已掌握的源 ID、URL、哈希、证券身份、模型配置等由程序填写。

## 1. 共用结构与研报结构的对应关系

| 研报现有结构 | 公告建议结构 | 相同之处与必要区别 |
| --- | --- | --- |
| `reports` | `announcement_documents` | 文档身份、来源、时间、摘要、内容版本；公告保留源类型，不复制券商评级/目标价字段 |
| `metric_fact` | `announcement_metric_facts` | 原值、数值、单位、实际/预测、来源；公告增加月/季/累计及时间点口径，不仅是 forecast_year |
| `metric_def` | 尽量复用现有定义，经营指标按审核后的定义扩充 | 同名不代表同口径；不把机构预测、管理层预计与正式实际值混算 |
| 研报正文中分散的事件/关系 | `announcement_events`、`announcement_participants` | 事项进展、关键日期和参与角色对公告查询有独立价值；每份公告可为零到多项 |

四张表承载业务结果。原 PDF/HTML、逐页解析及 OCR 产物放独立归档，通过 hash 与引用关联；任务记录复用已有作业设施，不把技术状态塞进业务表。如果现有设施不适用，后续另评估最小作业账本，不在本轮预造平台。

## 2. `announcement_documents` — 公告文档与抽取快照

粒度：一个来源文档的一次可复现内容/抽取版本。`document_key` 稳定定位原公告，`document_version_id` 定位本次快照；不同版本不能在对外数量统计时当成多篇新公告。

| 字段 | 逻辑类型 | 用途与归属 |
| --- | --- | --- |
| `document_key` | 稳定标识 | 系统由来源命名空间及完整 URL 生成；不使用未保证唯一的源 id |
| `document_version_id` | 版本标识 | 绑定元信息、内容及解析/抽取版本；系统填写 |
| `source_system, source_record_id, source_url` | 文本 | 原始来源、源编号、原始链接，保留不重写 |
| `resolved_url, original_hash, original_ref` | 可空文本 | 实际原件地址、hash及受控归档引用；尚未下载可空 |
| `title, language, source_name` | 文本 | 复制源元信息；来源网站与公告披露公司不是同一字段 |
| `issuer_id, issuer_name` | 可空标识/文本 | 披露主体，经现有主数据映射；不能用标题猜完整法人 |
| `security_code_raw, security_code, market` | 原值及可空标准值 | 原编码永久保留；A/H及前缀代码通过主数据处理 |
| `source_type, source_type_new` | 可空文本 | 原两套公告编码，不冒充系统业务分类 |
| `business_category, document_form` | 可空文本 | 分类建议，如“业绩披露”“更正”；便于检索，不限制后续能抽什么 |
| `published_at_raw, published_at` | 原文及可空时间 | 保留原值；只有源时区/日期精度确认后归一。仅有日期时记录精度，不伪造首发时刻 |
| `source_updated_at, observed_at` | 可空时间/时间 | 源更新时间与本系统取快照时间；不能相互替代 |
| `content_ref, content_hash, parser_version` | 文本/可空文本 | 指向独立正文或解析归档，不回写 PG；记录使用已有 content 还是下载补解析 |
| `extraction_version, extraction_model, structured_at` | 版本/文本/时间 | 系统记录实际抽取配置及时间 |
| `summary, extraction_notes` | 可空长文本 | 自然语言核心内容及缺口；ignore 或无正文可不生成摘要 |
| `ignore, ignore_reason, selection_version` | 布尔/可空文本/版本 | 只控制默认批量处理资格；理由包括依据是标题还是已读正文；源表不回写此值 |

`ignore` 是用户明确要求的处理资格，影响是否消耗下载/解析/模型资源，因此值得保存；它不是风险等级或 Agent 生命周期。其他技术进度沿已有任务记录管理。不能再加“很重要/一般重要/完整/半完整”等一串展示状态。

同一正文因模型或提示版本变化重新抽取时，保留旧结果。对外读取使用已验收的抽取版本和对应源快照；不得简单按“最后跑完任务”覆盖更晚的披露。原件未下载时，不能声称已有 PDF 页级引用。

## 3. `announcement_events` — 一项具体披露

| 字段 | 逻辑类型 | 用途与归属 |
| --- | --- | --- |
| `event_id, document_version_id` | 标识 | 系统生成与归属；模型不复述已知文档身份 |
| `event_type, event_title` | 可空类型/文本 | 如“现金分红实施”“合同中标”；类型服务查找，标题便于阅读 |
| `event_summary` | 长文本 | 谁做什么、本次变化、进展、条件与限制；一段或分段自然语言，不拆成大量说明字段 |
| `event_date` | 可空日期 | 本次具体事项发生日；未来生效日及其他日期放命名日期中；不默认等于发布日期 |
| `key_dates` | 可空小型日期集合 | 如登记日、除权日、发放日、解禁日、到期日；每项只含日期名/规范日期/原文与定位，服务日历和过滤 |
| `related_documents` | 可空关联集合 | 更正、补充、进展、正文/摘要等明确对应关系；无法确定稳定键时保留引用描述，不猜合并 |
| `source_quote, source_locator` | 原文/定位 | 支撑本项的引文和段落/物理页；必要时为小型证据集合，不要求一个句子包含所有角色和条件 |

`key_dates` 是有具体消费需求的机器事实，规模小、定义清楚；金额、指标仍进事实表，原因和风险仍在自然语言摘要中，不建任意嵌套业务 JSON。日期名称在已确认业务规约中归一，例如 `record_date/ex_date/payment_date/maturity_date`，原名称同步保留。日期集合不足以支持实际查询时再提升为专门日期表，不提前增加。

每项记录必须区分背景与本次新增披露。涉及多个独立交易时拆为多个事项；一个交易同时“关联交易/并购/融资”不复制成三份金额。跨公告是否属于同一持续事项先保留证据关联，不以“同公司、同类型”自动合并。

定位绑定原件或正文 hash 及解析版本。PDF 使用从 1 开始的物理页号，区别于印刷页码；字符偏移说明所用文本版本和坐标规则，跨页表保留实际涉及页，不能把全部单元格挂在首页。只有源 content 的材料保留文本位置，不伪造 PDF 页号。

## 4. `announcement_metric_facts` — 可比、可计算的指标事实

| 字段 | 逻辑类型 | 用途 |
| --- | --- | --- |
| `fact_id, document_version_id, event_id` | 标识，event 可空 | 定位事实及出处；财报通用指标不强制捏造事项 |
| `subject_id, subject_name, scope` | 可空标识/原称/口径文本 | 实际指标属于谁及统计范围，如集团、四家子公司合计、某产品或地区 |
| `metric_code, metric_name` | 可空正式码/原名 | 可核对时复用定义；未知指标名称可保留，不能直接统一聚合 |
| `value_raw` | 文本 | 原始数值表达，包括约数、上限、区间、负值 |
| `value_num, value_lower, value_upper` | 可空 Decimal | 数值或边界；区间不取中点冒充原文；单边上限不当作实际发生额 |
| `unit_raw, unit_code, currency` | 原单位/可空标准单位/币种 | 万元/亿元/股/辆/%/百分点等；数值量级跟随单位，不默认 CNY |
| `period_start, period_end, period_label, as_of_date` | 可空日期与原期间文本 | 区间指标、累计与时点余额分别表达，期间不能从文档日期机械推导 |
| `value_type, basis` | 可空约定/口径文本 | value_type 可沿用 actual/forecast；basis 说明公司预告、未经审计快报、已披露实际、计划额度、累计执行等，不把未审计等同预测 |
| `source_quote, source_locator, extraction_notes` | 原文/定位/可空说明 | 表头、单位、主体、期间和数值依据；缺口仅影响该事实的可用范围 |

同名金额也不能相加：计划上限、已实施额、期末余额是不同口径；合同总额与已确认收入不同；集团合计不能分摊给各公司。按这些口径选择事实是查询/分析方法的职责，不能用一个“可靠性分数”替代语义。

本表首期只保留原披露及确定性单位换算，不离线生成股价目标、利润增厚或风险分。若后来增加计算事实，须明确计算公式与输入事实引用；不能把模型估算写成原文披露。

## 5. `announcement_participants` — 事项中的参与方

| 字段 | 逻辑类型 | 用途 |
| --- | --- | --- |
| `participant_id, event_id` | 标识 | 系统生成，归属具体事项 |
| `entity_id, name_raw, name_normalized` | 可空身份及名称 | 可匹配既有公司/机构/证券主体；未知及匿名主体保留文档内原称，不猜实体 |
| `role` | 语义明确的文本 | 买方、卖方、借款人、出借人、保证人、被担保人、质押人、质权人、股东、标的等 |
| `role_description` | 可空自然语言 | 对象范围、条件及容易混淆的身份说明 |
| `source_quote, source_locator` | 原文/定位 | 支持该角色的实际证据 |

保留这张表的理由是实际问答需要按“谁为谁担保、谁向谁采购、谁收购谁”查询，不能每次全文搜索后重新推理。角色属于此次事项，不成为主体永久属性；经理任职不能标成控制权，受托人不能标成债权人。没有具名对手方的经营/风险事项仍可正常保存，不因此拒收整篇公告。

## 6. 各类用同一结构落地的例子

| 需求 | 事项 | 指标事实 | 参与方/命名日期 |
| --- | --- | --- | --- |
| 月度产销 | 当期经营数据披露 | 销量、产量、出口量；按月/累计及产品区分 | 主体是集团或披露范围；实际期间在指标上 |
| 分红 | 预案或实施事项 | 每股/每十股现金、分配基数、总额、转增比例 | 登记/除权/发放日；不把预案和实施相加 |
| 股份解禁 | 解禁安排 | 数量、占总股本比例 | 解禁股东；上市流通日 |
| 担保 | 对特定融资提供保证 | 本次额度、实际余额、累计余额分开 | 保证人、被保证人、债权人；期限 |
| 收购 | 股权或资产交易 | 对价、收购比例、估值、业绩承诺指标 | 买卖方、标的；签署/审批/交割时间 |
| 中标 | 中标及后续签约事项 | 单项或合计金额，不逐家复制总额 | 实际中标方、采购方；履约期间 |
| 财报更正 | 修订披露 | 原值/更正值分属各自披露版本和口径 | 与原报告关联；来源发布日期分别保留 |
| 股权激励 | 授予/归属/注销事项 | 授予数、价格、考核目标、执行数量 | 激励对象范围；考核期、归属时间 |

因此暂不需要 `dividend_table/guarantee_table/lawsuit_table/...` 十几张物理专表。后续可在共同事实基础上提供不同业务视图，既让 MCP 易取数，也不让数据库跟随每种 UI 表达变化。

## 7. 上线前仍需定案的内容

权威类型字典及版本、源时间精度、证券编码规则、正文更新机制；原件与解析归档的保存位置/期限；实际指标定义与命名日期清单；抽取样本验证后的字段长度、索引和当前版本选择策略。先完成人工金标与错误分析，再据实际查询生成 DDL 和最小作业代码。
