# DSH Opt 上下文优化：实施与同题验证（2026-09-06）

前置调研：[上下文与执行效率复核](financial_qa_dsh_context_audit_20260906.md)。

## 最终实施范围

本轮以确定性数据传递和原生阶段预算改动为主，没有修改 DSH 框架源码、Catalog 定义、模型或 maxTokens；没有加入候选检索、公司关键词路由、业务 validator 或新阶段枚举。

| 环节 | 实施 | 保留的契约 |
|---|---|---|
| DSH 内部 MCP 桥 | 显式返回原生 `CallToolResult`，text 使用紧凑 Unicode JSON，structuredContent 保留完整对象 | 所有字段、规则、方法、例子均保留；不是摘要或截断 |
| 小结果首次传递 | 最多 50 行，完整 row-dict 在现有字符预算内则一次带齐 | 超预算仍为样例；公开原始结果、result_ref 不变 |
| DSH 模型投影 | 完整小表不按 5/10 行机械截断；超预算样例改为连续行；预算计入键名、数值和 JSON 结构，多步骤共用样例行预算 | 只投影模型可见副本，不修改持久化结果 |
| 完整性/分页 | 投影后同步现有 sample_complete；page.returned/has_more 描述可见连续行；移除 guidance 中重复的完整性断言 | 不再同时出现“已完整”和“已截断” |
| 快速模式 | 原生 concludeTurn 仅用于系统声明的 data-only；summary 模式保留回答步骤；执行器禁用该模式下的自动源请求重试 | 正常模式/CC 原有重试不变 |
| DSH 阶段预算 | 普通模式在已确定目录后的 query 阶段改为 off；路由、修复保持 low；快速模式因没有修复机会，保留 query=low | 相同模型；所有 maxTokens 保持原值；显式旧配置仍可覆盖 |
| 失败交付 | 无结果且有明确查询失败时，即使 Harness 生命周期为 completed，也上报实际查询错误 | 不把失败混同为正常零行或“没有返回内容” |

职责：编码、引用、完整性、分页与输出模式属于 HARD 衔接；本轮没有把业务语义固化为新分支。`dsh_system.md` 保持原样，尊重已有人工修改。

预算说明：`queryMaxRows` / `detailMaxRows` 现在是**超预算时的样例行上限**，小表完整携带仍受 50 行和原有字符预算约束。`queryTotalMaxChars` 是一次工具结果内样例行 JSON 的共享预算，`detailTotalMaxChars` 是明细行 JSON 预算；它们不是整个请求（含 schema/目录/元数据）的 token 上限。长文本仍有显式摘要投影；本轮未实现同一字段内的文本游标，不应声称所有长文本已可完整翻页。

## 未通过的提示词精简实验

保留失败样本，不混入最终通过版本的统计：

1. v1 同时精简阶段提示、finance_query 说明和 DSH 回答偏好。前两道行情题误选 window；宁德时代经历无效请求和修复后 max-tokens，约 72.7 秒。停止批次，保留此前已完成的记录。
2. v2 只恢复原路由阶段提示。第二次茅台仍没有取得数据，约 43.4 秒，因此也不作为提交版本。
3. v3 撤回上述**全部提示词精简**，保持初始模型输入与基线一致，仅保留表中确定性改动。通过日志对第一轮 system、tools、config、用户/阶段消息进行规范化 SHA-256 对比。
4. v3 的 10 次运行虽然上下文下降 34.8%，但平均耗时增加 3.1%，模型阶段耗时增加 12.7%，仍未通过效率门槛。
5. v4 仅再调整普通 query 阶段的推理预算为 off。10 次正常模式实跑达到下述指标，成为最终普通 Opt 默认值。

快速模式附加实验中，query=off 曾照抄目录例子中的 `$stock_codes`，发生未绑定变量错误。没有针对该变量写补丁，也没有违反 fast 的无重试约束；最终**不将这个预算变化扩展到快速模式**。现有 `budgets` 下增加可选的 `fast_query` 预算档，不新增 loop 阶段。旧配置显式提供 query 而未提供 fast_query 时，两种模式都继承原有显式 query 配置，保持调参兼容性。

保留 low 后快速模式仍出现过首轮误选 window、随后生成不存在的 stock.quote.query；另跑原始基线 fast data-only 两次，也有一次没有取得结果。因此快速模式本身尚不稳定，不能将普通模式的 10/10 入口结果推广到 fast。最终错误透传的测试已验证：这类失败不会再伪装为正常空结果。没有为通过测试而添加修复重试。

这证明“更短”不能替代效果验收；但少量随机调用并不能证明具体哪一句提示词是唯一根因。冲突工具说明、错场景研究提示、目录范围提示同源生成，留待独立的 SOFT 实验，不把此次试验性改写推入生产。

未实施：旧阶段目录退出历史、全零结果提前省略生成、同阶段并行查询改造。特别是零行省略生成，需要同时验证多目标、部分失败和准备性查询的完成边界；本轮不扩大生命周期控制。

## 同题 A/B 方法

- 基线：Git `17796e4` 的独立源码快照；候选从同一快照复制，仅覆盖本轮明确列出的金融文件。
- 使用服务器的同一 Python 环境、远端 MySQL、目录 revision，以及阿里云同一 `deepseek-v4-flash-0731` endpoint；仅从既有 `.env` 读取配置，不复制或输出密钥。
- 正常模式 DSH Opt，research_mode=fast，data_only=false；5 道已有问题，每版每题 2 次，每次独立请求/新会话。每个实例只有 1 个 worker，无请求排队混杂；实例启动期间有时间重叠，不是严格随机交错试验。
- 实际调用 Chat/MCP 共用的金融 `answer` 服务、DSH 模型和真实查询执行器；不包含 HTTP 鉴权、顶层意图识别或前端渲染，不将此处耗时宣称为整站响应时间。
- 另外实跑快速模式 raw+summary、data-only，检查结束行为；不并入正常模式 A/B 均值。
- 对比入口与实际执行 DSL、返回数据集行数、模型调用数、累计输入（含服务端缓存）、输出 tokens、总耗时和真实工具耗时。精确 API 字符串一致率不等于正确率，例如 report.query 与 report.agg 可以分别用原始评级行和分组计数回答同一比例问题。

复现实跑脚本：`scripts/eval_financial_qa_dsh_context_ab.py`；汇总脚本：`scripts/analyze_financial_qa_dsh_context_ab.py`。内部原始证据在 `outputs/financial_qa_dsh_context_ab_20260906/`，不提交原始会话与业务数据。远端隔离目录为 `/tmp/fin-agent-context-ab-20260906-1XBOsp`，与线上服务目录分开。

## 验证结果

普通 Opt：5 题 × 每版 2 次，共 20 次配对运行。下表为每题两次均值，时间单位为秒，累计上下文是每次模型请求输入之和（包括缓存输入）。

| 问题 | 执行入口 | 平均时间：旧 → 新 | 累计上下文：旧 → 新 | LLM 次数：旧 → 新 |
|---|---|---:|---:|---:|
| 贵州茅台近 5 个交易日行情 | stock.quote | 29.18 → 17.82 | 24,781 → 16,473 | 3 → 3 |
| 宁德时代近 10 个交易日行情 | stock.quote | 21.93 → 19.57 | 35,871 → 16,661 | 4 → 3 |
| 今世缘机构估值方法差异 | stock.report | 13.16 → 15.86 | 28,274 → 33,465 | 3.5 → 4 |
| 中际旭创研报多空比例 + 净利润走势 | stock.report + stock.financial_3_table | 20.08 → 15.29 | 50,595 → 21,236 | 4 → 3 |
| 兴森科技 2024Q4 出货量边界 | stock.report | 16.00 → 15.67 | 24,712 → 21,449 | 3 → 3.5 |

整体指标：

- 平均服务耗时 **20.07 → 16.84 秒，下降 16.1%**。
- 平均累计上下文 **32,846 → 21,857 tokens，下降 33.5%**。
- 模型阶段耗时合计 **128.94 → 118.35 秒，下降 8.2%**。这是 session 中 step/start 到 assistant/message 的计时，不是供应商内部推理耗时。
- 输出 tokens（含思考）合计 **10,168 → 9,166，下降 9.9%**。
- LLM 调用合计 **35 → 33**，明细调用 **5 → 3**。十日行情和多目标小表均省去明细轮；长文本题可能需要更多证据读取。
- 未缓存输入 **164,623 → 67,015**；缓存输入 **163,840 → 151,552**。缓存由模型服务端决定，且实验顺序有预热影响，不能据此直接声称费用下降 59.3%。不使用项目历史 total_tokens 字段代替完整输入总量。

重要限定：

1. **不是每题都变快**。今世缘两次基线分别查 25/20 行，其中一次只依据首次样例回答；新版本查 15/20 行，两次均读取明细，完整文本投影更多，因而时间与上下文都增加。这不是同一工具结果的压缩率比较。
2. 茅台基线的查询执行耗时含一次约 30 秒的数据库长尾，新版约 9 秒。不能将全部 16.1% 的服务加速归功于模型优化。剔除茅台两对运行，其余 8 对平均服务耗时仍下降 **6.7%**。
3. 样本较小、非严格随机交错，没有固定模型随机种子，不能外推为全量评测提升或稳定 SLA。

### 入口与原始结果核查

- 最终 10/10 次有实际查询结果，无执行错误或 max-tokens 结束；同题的**主要入口均保持**。
- 精确 API 集合为 **9/10 对相同**。唯一差异是兴森科技的第一条基线还查询了不提供出货量的 business_segment，新版没有这次附加查询；不是删除用户要求的数据目标。
- 所有最终具体目录读取均带 operation=query，没有重复 v1/v2 的行情 window 误选。10/10 对的第一轮完整输入规范化哈希相同；目录 revision 全部为 `686df4321eb802a41df2849fef7fa964916d4b1306c9922a903646a496780820`。
- 行情的原始结果始终是 5 行与 10 行，4 对行情样本返回给调用方的前 5 行 row-dict 完全相同。多目标旧版为 3 条研报 + 10/7 个财务报告期，新版为 3 条研报 + 11/15 个报告期，没有退化成只查最新一期。
- 兴森科技依然不能提供题目所问的结构化出货量。报告文本按不同发布时间范围返回 5 或 0 行，不能把“查到研报”误判为“查到出货量”。
- 真实 MCP 日志中的同一行情 execution pack 从 **13,556 → 4,940 字符**，JSON 对象相同，字段/例子无损。

### 摘要质量的独立问题（不隐瞒）

这里的通过标准是用户本轮指定的入口选择和效率，不是“最终回答事实正确率 100%”。人工检查发现：

- v4 的 multi-1 原始归母净利润值为 `13,651,149,693.27 元`，summary 却写成 `1,365.12 亿`，放大约 10 倍。原始 row-dict 与工具样例正确，错误发生在最终自然语言换算。
- 有行情 summary 在未查询成交量时使用“放量”，边界题 summary 推及未实际查询的公告披露情况。这些是现有最终回答环节的事实约束问题，不能当作来源已证明的结论。

本轮未添加公司/指标定制 validator 或改动用户维护的 system 提示；上述摘要问题需独立按 SOFT 回答契约与可验证计算路径处理。在此之前，不能将这些 summary 作为已完成事实校验的分析报告，也不自动更新生产服务。
