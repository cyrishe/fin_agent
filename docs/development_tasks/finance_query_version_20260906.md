## MCP 回归口径

复用原67题及增量117题，全部走 finance_data_query 的 MCP HTTP 入口；runtime=dsh、标准 Opt、response_mode=data，不传 conversation_id。每次独立查询，返回各数据集真实行数、schema与前2条，不生成 summary。使用服务器现有 Aliyun 模型和远端数据库。

从提交版本创建隔离源码快照，临时只监听 loopback 的真实 HTTP 服务；临时 key 仅存内存，关闭进程即失效，不改线上 key 和服务。关闭测试请求计数写入，其他金融执行路径不变。

先人工检查6题 pilot，再跑剩余题；并发3，不自动重跑计费请求。传输错误、意外 summary、单题超过120秒或完成至少10题后失败超过20%时停止投放，保存已在途结果。

评测报告独立列出请求完成、耗时、Token、所选数据、数据集条数/样例、入口覆盖和待复核项。不把数据为空、HTTP200、同入口或旧报告重跑成功视为真实性证明。

### 已还原的根因

RTE016的原生session记录能够逐步还原以下过程：

1. 第2步查到7篇研报。请求没有data_request_complete=true，工具返回data_only_complete=false。
2. Opt的updateAfterStep进入data_only_followup_allowed，仍处于query，requiredAction=true。这个成功分支也没有检查maxQueryAttempts。
3. 第3步模型请求load_finance_result，被query阶段工具白名单拒绝。原始assistant消息的参数完整，详情事件中的空对象是被拒调用的记录，不能据此归因模型端点兼容问题。
4. 第4步模型已经生成回答，turn-stopping又注入“本阶段尚未取得数据”的不实阶段提示。第5步相同查询被去重拒绝，随后转repair并继续要求查询。
5. 第7、9步再次取得重叠数据。第4、6、8、10步实际都生成了回答文字。最终MCP响应summary=null，仅证明返回层隐藏回答，不能证明未消耗生成回答的Token。

因此这是现有data-only完成语义、阶段允许动作、turn-stopping指引之间的衔接缺陷，非此次SQL三个月扫描导致，也不是数据库执行慢。现版不追加针对题目的提示词补丁，不以切换fast掩盖问题。应在后续修复中区分“数据已取得但需要检查后续依赖”和“尚未取得数据”，保留多数据目标及正常终止能力，补协议测试后再按同题回归。
