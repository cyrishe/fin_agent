## 确认的根因

### 1. 零行显示错误：失败被误当成成功

`tools.py` 静态失败返回 `validation.ok=false`、`failed_step`、`completed_steps`，没有顶层 `error/ok=false`。`dsh_service.py:1155` 的展示失败判断只检查顶层error/ok；随后1184—1212只读取 `steps`，没有正确处理 `completed_steps`。缺失的 row_count 被默认成0。

因此同一次flow中，实际成功的600行以及未执行的第二步，都显示成“当前条件下为0条记录”；去重失败也同样误显示。这是展示适配bug，不是市场筛选结论。工具被guard拒绝时的空payload亦被明细展示当作成功读取0条。

### 2. 组合引用命名不一致

模型输出 `r1 = ...`，系统按会话已有结果重命名为r11；后续仍引用 `r1.stock_code`，命中了历史研报结果r1而失败。`result_registry.py:85`只改赋值左侧，不改rN引用；支持同flow内稳定引用的是 `step1.stock_code`。

工具Schema规定 `result = ...` / `step1.column`，但执行目录仍有大量 `r1 = ...` / `r1.column` 示例。模型没有遵循flow局部引用契约，同时命名规则和目录示例存在可诱发该错误的不一致。不能仅靠再加一条提示解决，也不能盲改r1引用，因为r1也可能是用户真实要复用的历史结果。

### 3. limit=-1在窗口实现中错误变成100

`quote_provider.py:403`使用 `_bounded_limit`；529—536行把所有非正数改成100，再裁剪返回。标准协议中的显式全量-1在该窗口路径未落实。日K明细已经有单独的全量限制处理，不能据此认为窗口同样正确。本次300只行情实际齐全，只是返回被裁掉，不是缺200只数据。

### 4. 修复预算的范围与终止解释

`dsh_loop_policy.mjs:743`累计全轮失败次数，不在成功修复后归零，也不按失败子任务区分。第一个引用错误已修好，第二个无关的去重错误仍使整轮进入final；尚未执行的PE、ROE也一并禁止。

`dsh_loop_policy.mjs:568`又将Skill路径的final统一描述成“本轮取数预算已结束”，所以回答中“预算已耗尽”来自框架提示，但不精确描述实际原因。上一次扩大总查询额度并未放宽这一独立限制，因此不是部署没有生效。

### 5. 不必要的模型周转

Skill分析扩容后，非强制阶段统一使用low和8192上限，连“再读一页”“整理去重”等下一步选择也进入该配置（`dsh_loop_policy.mjs:1088`）。第5—7次合计115.482秒，且没有取得新必要条件的数据。

final阶段为保持缓存前缀继续展示完整工具Schema，由guard限制实际可调用工具；模型第7次仍选了已被禁止的数据读取。这是工具可见性与执行权限之间的取舍产生了实际代价，应结合本次证据评估，而不是直接宣称模型必须多想一轮。

## 优化判断（未实施）

该题需要模型理解筛选意图、选择Skill与入口、生成查询流，以及解释最终候选；目录读取、数据查询、同flow依赖展开、去重、交集、排序、分页本身是确定性执行，无须每个动作单独回模型。

优先修复：失败/零行显示、窗口limit一致性、局部flow引用与历史结果的清晰命名。然后调整“失败子任务修复”与“全请求总预算”的职责，保持真实无进展循环受限，而不是一次已修好的错误消耗所有后续容错。最终分析的表达额度不应无差别扩大每个机械取数决策。

外层3次调用也存在合并审视空间，但本次主要延迟在DSH后半段，应先修这些已证实的问题。不要根据这一个case添加沪深300关键词路线或固定某只Skill的特殊流程。

## 二次复核：为什么提前读50条，又回头聚合去重

### 现场动作，而非对模型思维的猜测

再次只读核对服务器当前 worker 的 `home/sessions/--data-cyris-fin_agent--/financial-qa-21ba372f219972545e7890fe04546163/session.jsonl` 中实际工具参数、工具结果与阶段提示。

- 第5步明确调用 `load_finance_result(r12, offset=0, limit=50, columns=[code,name,pct_60d])`。50是模型选的页大小，不是默认值（默认10）。工具实际将50行交回模型。结果缺PE与ROE，不能用于核验全部条件。
- 前面的窗口请求没有 `order`。`quote_provider.py:_sort_kd_rows` 默认按代码排序，所以这50行是代码顺序的前50行，**不是走势最强的50只**。在只返回100行的基础上继续读另一页也无法恢复被截掉的其余200只。
- 第6步的明确工具目标是“获取沪深300去重后的全部成分股清单（按stock_code分组）”，实际调用 `index.constitution.agg`，聚合参数 `count(index_code)`、分组 `stock_code, stock_name`。不是模型自行算出一份去重名单。
- 聚合在静态检查中失败，未执行SQL。直接原因是此聚合路径将源字段作为三段式指标引用检查，裸字段 `index_code` 被拒绝；不能将错误解释成“数据库不能去重”。这属于聚合字段作用域契约需要统一审视的问题，不应为本题加一个特殊去重入口。
- 但本题根本不必额外去重：`python_filter.py:bind_references` 已用 `dict.fromkeys` 将引用列转换成去重集合，再编译为参数化 `IN` 条件。同一指数的两套代码产生600行，不会让下游查询同一股票两次。前一版报告中“去重应交给代码”的表述需要补充：**这段确定性能力已经存在，只是没有被顺畅利用。**

### 框架的真实引导偏差

`dsh_loop_policy.mjs:queryNeedsDetails` 仅依据 `sample_complete=false` 与结果引用存在来决定是否转入 details。这里的事实只是“本次工具回复未展示全部存储结果”，不是“用户的数据目标已经完成，也不是接下来必须读明细”。

第4步成功后的实际阶段为 `details / query_success_sample_incomplete`，框架引入了：

> 查询已经成功。现有样例足以回答时直接完成；答案需要样例之外的内容时，用 load_finance_result 按必要列读取明细后完成。

此时PE与ROE尚未执行，框架却突出“读取明细后完成”。Skill路径仍允许查询、目录与明细工具，所以不是强制只能读明细，而是**错误的阶段推导和收尾引导影响了后续规划**。不能把全部责任归为模型随机选择不佳。

另外，`projectRows` 对50行以内且字符总量较小的数据直接完整保留，因此虽然详情投影配置有 `detailMaxRows=10`，本次50行短记录仍全部可见。这是当前上下文体积策略，不宜靠将50改成10来掩盖“条件还没查齐就浏览中间表”的主线问题。

### 用现有能力即可表达的合理流程

按原Agent已采用的“60交易日累计涨幅衡量走势”口径，一条合理执行链是：

1. 指数成分查询，得到股票代码集合。
2. 估值查询：上一步集合内，最新PE TTM＜50。
3. 财务查询：上一步集合内，最近一期ROE＞0。
4. 窗口查询：只计算交集内股票的60日涨幅，按value降序取10只。
5. 用这10只代码查询其PE与日期。
6. 用这10只代码查询其ROE与报告期，供最终逐股解释。

第5、6项是候选确定后的窄范围证据回取，不是必须新增的业务步骤；若能复用此前已存值，可减少回取。当前跨结果列引用已支持集合筛选，但不能据此宣称已有任意结果表的通用join、投影、排序工具。此处无需先扩建结果处理框架。

以上6条请求已在服务器当前版本逐条执行解析、flow局部引用解析和静态验证，**6/6通过**；检查使用列结构句柄，不查询数据库、不调用模型，也不生成新的选股结果。各步引用分别为 `step1.stock_code`、`step2.code`、`step3.code`、`step4.code`。`finance_query` 已支持最多8步按顺序确定性执行，无须每一步返回模型重新决定下一步。该检查证明协议可表达，不证明全量执行正确：现有 `limit=-1` 截断问题仍是执行前必须修复的独立问题。

筛选、集合传递、窗口计算和排序归确定性执行层（现有SQL与Python实现），模型负责语义口径、生成查询流、处理真正需要观察的分支，以及解释最终小集合。不应让模型阅读大批候选来代替既有条件筛选，也不应将所有业务一律固化成上述顺序。
