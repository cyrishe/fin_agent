# 封存CC与当前DSH：同五题对比

**结论：可以继续优化DSH架构，没有发现这五题的取数能力明显退步。** 这不是生产全量验收，也不是“五题都有完整答案”：权重缺失、目标价缺失和板块窗口空结果，两端都存在。

## 结果

| 原题 | 数据结果判断 | CC耗时 | DSH耗时 |
|---|---|---:|---:|
| 宁德时代最近10个交易日收盘价、涨跌幅 | 两端10行逐值一致 | 19.35秒 | 15.84秒 |
| 沪深300当前成分股和权重 | 两端600行集合一致；对应两个指数代码、各300行，权重均缺失 | 36.53秒 | 17.87秒 |
| 近5日主力净流入合计最高的板块前10名 | 同一窗口方法均返回0行；DSH如实结束，CC又绕路查询并发生引用校验错误 | 77.38秒 | 5.43秒 |
| 名称包含债券的基金代码、名称 | CC返回10行、DSH返回50行；CC结果包含于DSH，名称均符合条件 | 17.94秒 | 9.93秒 |
| 指定三个月内天齐锂业研报最高目标价 | 两端取得同一篇研报，目标价均缺失；DSH完成了身份→研报的后续查询 | 16.99秒 | 13.12秒 |

最高目标价题两端均使用“按目标价降序的明细查询”。区间只匹配1篇、目标价为空，这种路径可以揭示所需数据及其缺口，不因未使用agg判错。本次没有覆盖真正多行聚合计算的执行，也不能据此宣布data-only模式的提前结束问题已经修复。

本批DSH耗时少约63%，含缓存Token少约73%。CC原始usage没有保留缓存字段，已从原生会话按message ID去重补齐；DSH使用原生逐步usage，因此不是把一个含缓存、一个不含缓存的数值相除。这是Token用量，不是费用。

耗时优势受板块空结果题影响较大；剔除该题，剩余四题合计约90.81秒对56.76秒，DSH仍快约37%。API执行时间合计约6.84秒对2.53秒，但本次同时比较了旧/新工具实现，数据库缓存和请求时序也会影响结果，不能把所有提速归因于Harness。

## 仍然需要注意的事

1. **DSH配置依赖要明确。** 首次隔离运行因MCP子进程清理密码环境变量而认证失败，未纳入效果和耗时统计。根因是DSH的`buildChildEnv`会删除凭据类变量，而本项目的MCP配置没有显式传递业务库凭据；原项目依靠`ai_service.py`加载工作目录`.env`。本次在私有隔离目录按现有机制临时提供必要配置后重跑，结束即删除。仅通过服务进程环境注入的部署方式仍需验证/完善，不能假定密码一定传到MCP。
2. **Summary有小瑕疵，但不是少取数据。** DSH目标价回答首句称“1篇包含目标价的研报”，后文却正确说明目标价缺失，首句不严谨；成分股回答附加了近似推算权重的建议，超出了本次查询范围。CC行情回答也把实际3涨7跌误写成2涨8跌。应单独优化回答的证据一致性，不改数据协议去迎合这些措辞。
3. **默认返回量不一致。** 基金题用户未指定数量，DSH取50条、CC取10条；本次数据覆盖不退步，但不能把条数差异当准确率提升。
4. **共同空结果不等于已证实缺数据。** 板块窗口两端都没有给出榜单，本次只证明DSH未弱于CC；未进一步诊断底表覆盖、窗口实现等空结果根因。

因此，继续以DSH为主线是合理的；没有理由为了复制CC的绕路和错误恢复旧设计。后续架构优化优先处理凭据传递、整轮超时/回收、同会话结果引用等系统边界，再分别回归data-only完成性与summary。五道单轮题不能替代这些测试。
