# 最新线上请求全过程复核：Skill 消耗与效果

日期：2026-09-10。审计样本截至北京时间13:47:07完成的8条请求。承接 [五维分析](dsh_harness_five_dimension_review_20260909.md)，本轮只读取证与文档保存，不修改运行时、不重跑模型、不部署。

## 1. 结论

Skill 消耗高不能归结为“Skill太长”或“思考太多”。本批真实问题分别发生在**目标理解、完成控制、上下文恢复、证据读取、计算与解释**：

1. **3条请求已经生成完整答案，因早先的 `data_request_complete=false` 又被系统要求再回答一次。** 第二次生成前没有新增工具证据，合计多处理67,592输入token、3,579输出token，模型步骤耗时39.035秒。这是可直接定位的框架往返浪费。
2. **简单取数也可能比Skill更贵。** 中际旭创融资余额只取1行，却处理121,533累计输入token；本轮消息重复附上18,874字符的全历史结果索引，还继承上一轮研报分析历史。不是本题需要如此多证据。
3. **“读取完全部行”与“读取完全部观点列”被混淆。** 茅台研报读了56行评级/标题，但本轮投资要点仅有3行样例；科大讯飞第二次也只读了3/10篇投资要点，却作多机构综合。这属于证据消费缺口，不能通过删读取轮数制造提速。
4. **最新财务质量分析发生对象替换。** “易中天和东山精密几只股票”被改成“易天股份和东山精密”。身份查询没有证实这层映射，最后的免责声明不能补回研究对象错误。该请求72秒、63,552输入输出token，执行顺畅但目标层不合格。
5. **还有几项确定的轻量浪费：** 身份解析被方法入口guard挡一次、已经显式加载的Skill再读一次、读未使用的目录、读取60行触发最大50行校验再修复。
6. **部分消耗是合理的。** 财务质量分析使用多期数据、研报分析读取真实投资要点、最后组织有依据的分析，均有必要；不能以统一降低输出/推理预算替代上述根因修复。

8条均有成功的核心运行结果，不能据此写“8/8业务正确”。队列等待均为0，未观察到预算耗尽或超时。本批高消耗主要发生在模型路径与上下文，不支持把worker并发或DB加速列为当前第一优先级。

## 3. 逐例全过程与效果

### A / C：山东黄金近90天机构看好理由

两条原题一致，实际匹配2篇研报，两篇投资要点分别1258/971字符，均完整进入模型上下文。两家评级一为买入、一为优于大市；机构/样本数与来源可复核。核心观点归纳有实际材料支撑；没有独立核验公告原文，因此不作公告级事实背书。

**A，5次模型：**

1. 加载研报Skill、report及report_metric目录。
2. 单独解析证券身份。
3. 一次查询取全2篇，提交`data_request_complete=false`。
4. 根据完整样例写出完整答案。
5. 完成hook注入旧false及成功引用，模型再写完整答案。

**C，4次模型：**

1. 加载研报Skill与report目录。
2. 解析证券身份。
3. 查询同窗口2篇；未显式写false。
4. 一次生成最终答案。

判断：C路径基本合理。A的report_metric目录没有被调用，且最后重复生成无新增证据。身份解析若可与初次发现同轮执行还有机会减少往返，但不能用“猜代码”替代身份确认。A→C整体时延差不能全部归因于优化：C单次最终回答反而更长，模型响应和缓存亦有差异。

### B / D：科大讯飞大模型催化分析

两条均加载`equity-report-analysis`与`stock-research`，实际研报均10篇。

**B，7次模型：**

1. 双Skill、report/report_metric目录。
2. 身份解析。
3. 一个flow查询10篇研报及60行预测指标，声明false。
4. 读取全部10篇投资要点；另一次要求读取60行，超过schema最大50，被拒。
5. 改为读取50行预测指标成功，仍有10行未读。
6. 综合研报与预测生成完整答案，37.667秒。
7. 被完成hook要求再回答，12.648秒，无新增取证。

合理：确实补读了所有10篇投资要点；观点分析不是仅依据3条样例。问题：60→50是可避免协议修复；预测并非完整总体，不宜泛化为全部机构分布。答案虽有来源说明，但把研报转述放在“已披露事实”名下，证据层级仍有混淆；旧年度预测与当前时点的关系也应明确。

**D，5次模型：**

1. 双Skill、report目录。
2. 身份与财务目录。
3. 一个flow取得10篇研报和2022–2024三年财务数据。
4. 只读取10篇的ID/标题/日期/机构/评级，没有读取剩余7篇投资要点。
5. 一次长答案，34.388秒。

判断：D读取财务以核验经营事实有合理贡献，也省去了重复终稿。但是投资要点覆盖仅3/10，长答案却跨多机构归因；不能把138,112→70,049 token称为“效果等价降耗”。它自行选择较旧财务窗口，不能把本轮只查询到2022–2024说成数据库仅有这些年份。宏观增长与AI因果联系也不是仅靠收入同比就能证实。

双Skill贡献需要进一步拆分：native返回中研报方法2642字符、stock-research方法5941字符，确有额外上下文。但B高消耗还包括完整证据读取、协议修复和双终稿；不能把这些都算在Skill正文头上。更适合做“研报主方法＋按具体缺口补财务方法”的同题实验，不在框架强行限制只能选一个Skill。

### E：茅台研报数量与看好观点

原始问题要求近期多少份研报看好、具体观点。用户未给固定时间窗，Agent明确采用近一年，可以作为可见业务口径继续，但需要保持查询窗口与实际样本日期的区分。

6次模型：研报方法/目录 → 身份与56篇全量查询（false） → 读前50条评级元数据 → 读剩余6条 → 完整回答 → 完成hook触发第二份回答。

**数据完整性分开看：**

- 56条评级都读到了。
- 56篇投资要点仅3条初始样例可见；两次后读的columns均不含investment_highlights。
- 第一份答案却声称已经读完全部投资要点；最后一份仍把总体统计和观点覆盖混写。

服务器保存结果的确定性统计：

| 评级 | 实际记录数 | 最后答案的表格 |
|---|---:|---:|
| 买入＋买入-A | 43（40＋3） | 约41 |
| 强烈推荐 | 3 | 2 |
| 优于大市 | 3 | 3 |
| 增持 | 4 | 4 |
| 区间操作 | 3 | 3 |
| 合计 | 56 | 53 |

按答案自身“除区间操作外算看好”的口径，实际看好记录为53；最终总数恰好一致不代表分项正确。应由已有聚合或确定性结果计算完成评级计数，再让模型解释。

去重也没有可靠依据：56个report_id互异；按标题+机构+日期有3组双记录、53个组合。答案称约7对重复、49篇独立研报，未给可复核标准。标题组合只是本次排查口径，不能直接当作权威唯一研报数。

这例首先需要修正计数与证据覆盖，再考虑减少分页；不能简单把两次读取删掉，而仍要求模型准确统计56条。

### F：中际旭创融资余额

4次模型：

1. 读取margin目录，同时调用身份解析；身份解析被“先读取方法或数据执行包”guard拒绝。
2. 同名身份解析再次调用，成功。
3. 最新交易日查询，仅1行，明确完成。
4. 回答。

核心数值折算与保存结果一致，时间标注为最新可用交易日，主要取数目标有效。

两项浪费很明确：

- 第一次身份解析不依赖新金融执行包，却被入口顺序限制挡住。当前保护包契约的必要约束不应机械延伸到独立身份查询。拒绝发生在重复guard登记之前，所以第二次相同调用成功；本例不是“暂时失败重试被重复guard挡住”。
- 同一会话继承茅台研报历史，本轮新消息又带上13份旧结果的完整索引，18,874字符。第一轮模型输入已经28,807token，最后32,293token，累计121,533；其中有与当前对象无直接关系的历史结果。

当前索引JSON从18778字符紧凑编码可到11338字符，对象内容完全相同，约减少40%字符。这只是序列化测量，不是token或费用节省承诺。更大的机会在于保留权威历史、按本轮关联提供可寻址信息，避免每轮把所有旧列覆盖再附一次；必须验证离题返回和旧rN复用，不能清空对话。

### G：茅台今日行情

3次模型：quote/basic_info目录 → 单flow取盘中快照与5日日线 → 回答。查询快、数据样例完整，没有补读或重复终稿。快照加日线对“有什么变化”有实际贡献，整体路径合理，basic_info目录未实际使用是小优化点。

效果仍有错误：快照开盘1291.00、昨收1290.88，程序差值为+0.12；答案却说低开约0.01。“尚未放量、常规缩量调整”也没有同时间段成交量基准，盘中累计与完整日线不能直接等同。

本例证明简单取数路径通畅也不保证附加解释正确；应让确定性比较与数值交给已有数据运算，SOFT避免超出查询证据的趋势/成交解释。

### H：最新财务质量比较

用户问“易中天和东山精密几只股票”的财务状况，显式选择财务质量Skill。

6次模型：

1. 身份查“易中天”无匹配、东山精密有匹配。
2. 模型自造易天股份/中天科技/易天网络候选做身份查询。
3. 读财务目录，并再次读取已在本轮prompt中显式加载的财务质量Skill。
4. 按易天股份与东山精密取2022–2025四年数据。
5. 补两公司2025/2026中报进行同比。
6. 长分析，40.864秒；结尾让用户若对象不对再纠正。

**对象层不合格。** “易中天”在市场语境中通常指新易盛、中际旭创、天孚通信这一组合；结合“几只股票”是重要语义候选，不能直接按名称相近改成易天股份。该用法已由本轮独立查阅的证券时报报道交叉确认；这不是声称百分之百确定用户意图，而是证明存在更合理的组合解释，且“易天股份”的替换没有依据。[证券时报原始报道](https://egs.stcn.com/news/detail/2331555.html)

身份工具的零匹配只证明身份表未匹配输入词，不证明市场不存在该组合称呼。正确做法是SOFT先解释组合语义，再用身份工具确认各对象；仍不确定时，只对影响研究对象的歧义简短澄清，同时可以继续已明确的东山精密部分。不要为此在底层写死“易中天→某三股”关键词表。

查询年报后再补最新中报、从现金流/利润/营运资本/杠杆组织分析，方法本身合理，不能把整次72秒全算无效。但错误对象的取证和比较不应靠降低token上限解决；应先保证目标正确。

**已加载Skill重复读取可确定。** 原生user输入带“用户显式选择并已加载的业务Skill”，随后工具返回的1141字符method与初始prompt逐字匹配。这里无需重新加载；可利用已有skill_id/revision/hash和实际可见内容，保持共享真源与可追溯，不新增业务状态。该读取与目录同一模型步发生，不单独承诺能省一轮。

## 4. 消耗归因与新发现

### 4.1 完成hook反而制造重复终稿

| 案例 | 追加的模型步 | 无新增证据的输入 | 输出 | 步骤耗时 |
|---|---:|---:|---:|---:|
| A | 5 | 13,808 | 1,268 | 12.391s |
| B | 7 | 31,726 | 1,218 | 12.648s |
| E | 6 | 22,058 | 1,093 | 13.996s |
| 合计 | 3 | 67,592 | 3,579 | 39.035s |

这些追加步共71,171输入输出token，占这3条请求处理token的约24.4%；步骤时间约占3条核心耗时合计23%。它们是历史真实追加成本，不是已实现的提速；移除前仍需比较两份答案质量和真实未完成流。

根因链路：早期false → `queryIsPreparatory()`把结果归为`identity_scope_ready` → `requiredAction`保留 → 正常无工具答案不消除该历史声明 → `agent/turn-stopping`再次注入 → 同证据重写。E后续的明细调用又会清掉requiredAction并使分析预算生效，但终止hook直接检查最后query的false，仍会追加；不能只改一个布尔值遮住现象。

另一个关联问题是预算受临近工具动作影响：A已经实际加载Skill，但false之后直接回答时记录为off/3072；E在false后读过明细，最终回答记录为low/8192。额度是上限而非实际输出量，但这说明“当前是否还有必须执行的动作”也在控制分析预算，不能简单认为所有Skill最终回答始终使用同一配置。后续应核对资源配置是否准确表达当前生成任务，不靠无意义的明细调用切换预算。

方案方向：把必要的“尚未完成事实”随工具结果放进本来就需要的下一次模型请求，让模型在生成终稿前决定补证据或交付。正常分析回答完成后，不再仅凭旧false要求整篇重写；真正失败步骤、未执行后缀及data-only明确交付条件仍按既有协议处理。用原生hook实现，不新增审查模型，不用答案关键词推测是否完成。

### 4.2 列覆盖与总体覆盖是不同事实

之前报告重点是“子集没有可复用引用”和“长字段后半段读不到”。本批暴露的是更前面的缺口：**后读根本没请求观点列**。本批涉及的投资要点单元格大多短于2400字符，不能把所有缺证据归因于字符截断。

已有result_ref、columns、page、sample_complete足以说明本次看到了哪些行/列。优先在工具返回和SOFT方法中准确呈现“评级全覆盖、观点仅样例”，并让业务方法按目标读取；不新增每条业务结论必须绑定JSON证据树的强制协议。

### 4.3 列表统计缺少便捷的程序路径

E用两轮把56条评级送给模型，仍手算出错。现有stock.report聚合入口应优先验证是否能完成相同口径统计；如果需要只在已保存资产上计数，再在现有结果读取/计算能力上补最小通用聚合，不造金融专用计数validator。去重按什么定义应由业务语义决定，程序只执行所选标准。

### 4.4 初始路由、身份解析和Skill复用还未完全协调

F是强制方法先于身份造成的真实额外轮。H则显示显式加载已允许身份先运行，但同一Skill又被重新读取。说明问题不在模型“永远先多想一步”，而是不同入口可用能力与已加载事实提供不一致；应利用现有上下文修正衔接。

### 4.5 外层与追问消耗也要算清
