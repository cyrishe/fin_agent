# 金融查询 Harness：任务推进与完成控制方案

日期：2026-09-09。状态：分析方案，未实施、未部署。

## 结论

采用“已知依赖交给查询流、后续决策交给 Agent、结束前检查已知未完成事实”的机制。复用 DSH 原生工具循环和 turn-stopping 钩子，不建立金融条件清单校验器，不强制每个问题创建 Todo，不新增业务阶段状态机。

这能消除框架引起的提前收尾，约束已提交但未执行完的工作；不能确定性证明模型已理解并覆盖自然语言中的每项要求。后者仍由模型判断，并用评测衡量。不得将“所有 Todo 已勾选”冒充语义正确证明。

## 本项目的根因

`src/scenarios/financial_qa/dsh_loop_policy.mjs` 在 updateAfterStep 中用 catalog/query/details 的调用结果决定业务阶段：

- 查询成功且 sample_complete=false → details；
- details 提示要求读取必要明细后完成；
- 明细读取达到次数 → final；
- 全轮累计查询失败超过一次 → final，连新的必要取数也被禁止。

本次PE、ROE未执行，窗口结果只展示部分样例，却已经进入 details。随后一个不必要的聚合错误触发全轮修复上限。这不是模型把全部条件判成合格，而是模型规划偏移与框架不恰当的阶段控制叠加。

现有 step_evidence 已包含调用条件、字段、结果引用。缺少的不是另一份条件提示，而是：工具回执与任务完成分开、查询依赖可靠执行、继续与停止权限合理。

## 具体改动设计

### 1. 已确定的工作：继续使用 finance_query.steps

模型一次提交已能确定的查询及依赖；Python顺序执行、分配正式结果引用、绑定去重列集合。中间步骤无需再调用模型。

真正取决于前次返回内容的分支，仍交给后续模型决定。不能为了“完整计划”强迫模型预先猜所有分支。

修改点：

- `tools.py:finance_query` 保留现有steps协议和执行循环，不新增计划DSL。
- `result_registry.py:resolve_flow_refs` 与目录示例统一使用流内stepN、跨流rN；禁止将有效历史rN引用盲目改成局部引用。
- 失败回执保留 submitted flow、completed_steps、failed_step；未执行后缀可由当前请求与failed_step确定性推导，无须模型重复填写未完成清单。
- flow中间失败时停止依赖执行是正确行为；需要给Agent成功结果与未执行后缀，不直接结束整次请求。

### 2. 取消展示信息驱动的业务阶段跳转

修改 `updateAfterStep`、`stageTools/stageAllows`、`promptFor`：

- 普通模式下，query成功、sample_complete、明细页数都不直接表示业务已完成，不据此关闭其他取数能力。
- catalog、query、load、Skill是可选动作，不再用上一动作类型硬推导下一业务动作。
- query的契约加载与版本检查继续由已有guard执行；load继续检查有效结果引用、权限和分页范围。
- 样例投影只改变模型看到多少内容，不改变真实存储结果、任务完成判断或工具可用性。
- 清理catalog/query/details自动收尾的阶段提示，而非新增“每项条件都必须检查”的反向提示。

阶段标签若仍用于性能配置或展示，只是派生信息，不得继续兼任结束权限。没有必要再新建一套active/planning/review状态树。

### 3. 明确完成交接，复用已有字段

保留 `finance_query.data_request_complete`：它是模型对本轮取数目标的判断，不是后端核验全部自然语言条件的证明。

- true只有在该flow全部成功后才能成为有效取数完成声明；失败返回不能沿用请求中的true。
- false表示模型自己已经声明还有后续取数，应在当前请求内保留；不能被随后一次读明细覆盖。
- 缺省仍兼容，含义是没有声明，不从sample_complete或行数补推为true。
- 普通聊天取数完成后仍允许分析或补充查询；声明不应不可撤销地关闭工具。模型的新查询会更新当前执行证据。
- data-only模式继续使用现有显式完成交接。即使是快速模式，也应区分“预算只允许一批查询所以结束”和“全部取数完成”，不能因查询成功自动证明后者。

普通聊天中的最终文本可以是完整回答、澄清请求或部分结果，不能一律当成成功完成。兼容路径也不能强迫模型发起空查询只为补一个完成字段。对外通过已有detail/执行元数据保留完成声明和实际中止原因；不新增业务输出字段树。

### 4. 将原生结束钩子从“阶段纠偏”改为“结束时对账”

修改现有 `agent/turn-stopping`，不增加独立审查Agent。

钩子只在模型准备结束时运行，读取已有执行记录：

1. 用户取消、超时或资源硬上限：遵从停止，不继续steer；保留实际未完成事实。
2. 若存在失败flow的未执行后缀、最后一次明确的data_request_complete=false，或启用Todo后的开放事项：第一次结束尝试提供一份简短的事实回执，允许模型继续处理或明确交代缺口。
3. 回执由已记录的goal、结果引用、failed_step和错误生成，不通过另一个模型拆解用户条件，不写PE、ROE等特定场景分支。
4. 模型可以修复、换路线、说明局限或询问用户。不能强制所有历史失败都必须修好，因为分支可能已被替代，或确实无数据。
5. 复用现有steer次数约束，结束对账每个请求最多触发一次，不按不断变化的stage/reason重新获得无限机会。再次结束若仍存在明确未完成证据，保留为部分交付，不强制死循环，也不偷偷把false改成true。

注意：这里保证的是“已知未完成不会被系统静默改成成功”，不是保证模型所有自然语言表述都正确。若模型从未表达某个要求，系统无法凭空识别；若模型错误宣称业务充分，仍需业务评测。不能隐藏这一能力边界。

### 5. Todo按需使用，不作为第一批必要依赖

第一批先修执行主线，避免同时引入规划工具而无法归因。如果原题和跨领域回归显示仍存在明显遗忘，再在隔离评测中加载DSH原生todo_write。

- 由Agent决定是否使用，不按问题关键词或硬编码条件数量启用。
- 复用原生content/status，不增加must/optional/verified及每个金融条件的状态。
- Todo记业务子目标，不记每次翻目录和分页；不能每次工具调用前后都强制更新。
- 开放Todo只触发有限结束对账，不直接禁止读取或分析；全部勾选不代表数据验证通过。
- 原生Todo要求整表重发，有额外调用和token开销；不强行用于可以一次flow完成的请求。

引入Todo只能作为可评测的记忆辅助，不能取代第一批框架修复，也不能承诺没有新增模型周转。

### 6. 资源限制与业务完成解耦

取消“整个请求累计第二次查询失败就禁止全部后续取数”的独立熔断；保留总查询/目录/明细调用上限、超时、权限和重复调用限制，控制成本与循环。

局部调用额度用尽只限制相应动作；是否还能完成剩余目标由Agent依据可用能力判断。总预算耗尽才结束整个请求，并保留停止原因。该调整不意味着无限重试。

修复结果截断和回执失真：limit=-1必须与实际执行一致；如果实际有安全上限，应明确实际覆盖范围。失败不能默认显示0行。窗口、查询与聚合的排序/limit一致性需要按执行实现回归，不通过叠加提示修补。

## 对本题应产生的行为变化

这是重放预期，不是已经跑出的新结果：

1. 已知条件可在同一flow中串联：成分范围→PE→ROE→60日走势排序→最终候选证据。
2. 若模型仍先查询行情，得到部分可见样例后，框架不再转入“读明细后完成”，继续开放估值与财务查询。
3. 已提交flow失败时，Agent收到成功结果及未执行后缀；一个后来失败的无关聚合不终结全请求。
4. 若模型准备结束且已明确还有取数工作，原生停止钩子提供一次执行事实对账机会。
5. 真正预算耗尽时可以交付部分结果，但不能包装为“没有满足条件的股票”或完整筛选结果。

## 验证方式与发布边界

先用固定模型响应的协议重放测试，不靠真实模型偶然成功证明控制逻辑：

| 场景 | 必须成立 |
|---|---|
| 相同真实结果分别展示完整/不完整样例 | 不改变业务完成状态与后续工具权限 |
| 一个flow有多步，第一步成功第二步失败 | 成功结果保留，后续未执行可追溯，不标记全任务完成 |
| 修复成功后另一个新查询失败 | 不因历史一次失败强制终止全部取数 |
| 明确false后模型尝试结束 | 至多一次事实对账，不从行数推断完成 |
| 用户需要澄清、取消或接受部分结果 | 能正常结束，不强制查询直到清单全勾选 |
| 真正空结果 | 与未执行、错误、截断区分；有效空集可以完成取数 |
| 简单单次查询、不使用Todo | 正常路径不额外增加模型轮次 |
| 旧参数、旧结果、缺完成声明 | 能继续使用，不擅自推定任务完整 |
| 原始数据/摘要/普通聊天 | 完成声明与中止原因一致，不受展示模式影响 |
| 历史成功结果及新flow引用 | 不混淆流内stepN与历史rN |

之后使用原始沪深300问题及已有20题跨subject/view样本对照：完成程度、必要工具选择、无效明细读取、未完成误报成功次数、模型请求次数与耗时。包含先观察数据才能继续和研报文字阅读场景，避免只优化数值筛选。不要把没有数据计为协议失败，也不要把固定回放通过当成模型效果通过。
