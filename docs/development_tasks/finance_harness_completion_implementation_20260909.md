# DSH 完成控制与中间结果筛选：实施与验证

日期：2026-09-09。本文记录本地实施时的验证；基础 HEAD：`9dab00768fbba34027f2d65be154372aeca75ecf`，叠加本轮改动。后续以业务提交 `9d66556` 同步服务器，后端待管理员重启；部署回执见 `deploy/server/ai-agent-kingdomai/RELEASE_20260909_HARNESS_COMPLETION.md`。原有前端等待提示改动已一并发布。

## 结论

框架提前收尾和显式全量被截断的问题已修正。原题最新一次能完成必要取数，并由程序筛选出正确前10；但是答案仍把229只PE/ROE合格股票误写成229只同时上涨股票（实际上涨112只），且有未取证的行业归因。因此：**数据执行路径改善，不等于整篇答案完全正确；暂不作生产效果放行结论。**

## 原生能力与本项目改动的边界

| 内容 | 来源 | 本轮处理 |

## 怎么做，而不是只要求模型这么做

1. 普通模式查询成功后，继续开放目录、查询与结果读取；`sample_complete`只表示展示样例是否完整，不表示任务完成。读取一页不再切断后续取数。
2. 不再因为整轮累计第二次查询错误就强制结束。仍受总查询次数、重复调用、超时约束；旧 `maxQueryRepairs` 配置兼容接收，不再作为独立终止条件。
3. 结束钩子只核对最近提交的执行事实和显式未完成声明，不创建语义条件检查器、不追加审查模型。模型从未表达的遗漏条件，系统仍无法确定性识别。
4. 已存表先在Python中筛选、排序，再分页投影给模型。支持字段条件、现有contains写法及 `code in rN.code` 集合引用。原始表和rN引用不变，返回匹配总数及原始总数。
5. 行情窗口、估值明细/窗口、财务明细遵守已有 `limit=-1` 全量语义；估值/财务SQL不再追加有限LIMIT，财务后处理也不再误用负数切片。默认100、正数上限等旧行为保留。本轮没有逐一修改所有其他provider。
6. 修复查询流部分失败的进度展示：成功前缀仍显示真实记录数；未执行/失败步骤不再伪装成“0行查询成功”。

主文件：`src/scenarios/financial_qa/dsh_loop_policy.mjs`、`tools.py`、`result_view.py`、`dsh_service.py`，以及phase2下quote/pricevalue/financial三个provider。没有修改金融Skill业务判断或增加PE、ROE专用分支。

### v3原题的12次LLM分别做了什么

| LLM次序 | 随后动作 | 评审 |
|---:|---|---|
| 1 | 加载stock-screening和成分/估值/财务目录 | 合理，可并行 |
| 2 | 成分名称查询，返回600行 | 两个沪深300代码各300行，不是600只不同股票 |
| 3 | 补行情执行包 | 可在前期一并加载 |
| 4 | 改为一个指数代码，300只；随后窗口引用出错 | 引用错误是可恢复错误，成功前缀保留 |
| 5 | 修复引用，执行走势/PE/ROE三步 | 已知依赖在一次工具流内执行，但未写limit，均默认100 |
| 6 | 三项显式limit=-1重查 | 均返回300；属于可以避免的补查 |
| 7 | 筛选上涨并读取走势前50 | 已程序筛选，但读取量仍可更精简 |
| 8 | 获取正PE且低于50的集合229只、ROE为正集合278只 | 条件由执行器处理 |
| 9 | 走势表按两个集合取交集、排序、只读前10 | 正确核心路径；完整300行上计算，不是LLM逐行选10 |
| 10 | 读取两张合格集合各前50 | 冗余；引用的是原始走势集合，不是刚展示的前10集合 |
| 11 | 按前10代码读取对应PE/ROE | 得到10只的准确数值 |
| 12 | 最终回答 | 前10与数值正确；总体数量和额外归因有问题 |

5次finance_query工具调用承载了多个API步骤；LLM调用12次不等于12次数据库查询。模型响应阶段合计82.382秒；工具跨度简单相加5.794秒（并行工具有重叠，不能与前者机械相加当端到端时间）。模型阶段含请求准备和生成，不能分离出精确“思考耗时”。

v3原题计量：非缓存输入37,077、缓存读取175,104、输出6,867；含缓存输入与输出共219,048 token。现有运行摘要的 `total_tokens=43,944` 不含缓存读取，不能误当全部处理token。reasoning token为2,737，已包含在输出计量中，不重复相加。

### 程序复核及剩余错误

复用已保存r6（走势300）、r9（PE合格229）、r10（ROE合格278），不重新请求数据库：

```text
filter: code in r9.code and code in r10.code
order: pct_60d desc
limit: 10
```

交集229只；再加 `pct_60d > 0` 为112只。两种口径排序前10相同，且最终表格中的PE、ROE、涨幅与保存值一致。最终回答把229说成同时上涨的数量，仍属错误。

前10：药明康德、山东黄金、紫光股份、荣盛石化、今世缘、卫星化学、世纪华通、山金国际、亿联网络、迈瑞医疗。

模型还自行采用PE>0，答案说明了此口径；这不等于用户原始条件严格要求PE>0。诸如“资金流入”“景气回升驱动”“未达过热阈值”的解释没有对应取证，不因名单正确而认定解释可靠。本轮不为这些个例加入提示补丁或关键词校验。

## 当前边界和下一步

系统已提供安全、确定的集合筛选能力，也排除了样例展示控制任务完成的框架缺陷；**并未禁止模型阅读表格，也不能保证模型每次都会选最短路径。** 普通结果浏览、探索性判断仍保留。

真正值得继续观察的通用缺口是：默认有限查询的范围表达、跨结果读取时前10集合的复用，以及答案数字/因果解释的证据一致性。应先跨题复现，再判断最小改动落在工具输出还是SOFT归纳层，不为本题单独创建条件清单、排名validator或额外审查Agent。
