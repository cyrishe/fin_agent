## 2. “协议生成、复杂组合失败”具体是什么

| 问题 | 还原的根因 | 处理 |
|---|---|---|
| 涨幅榜反复字段报错 | catalog 把 `note:` 放在可执行例子末尾；模型照抄后，注释被解析成输出字段 | 模型目录投影把执行串与说明分开，说明保留在 guidance；不篡改用户筛选语义 |
| 成分股引用失败 | 结果列引用实际是集合，协议仅支持 `field in rN.column`；模型按标量使用 `=` / `!=`，错误提示又笼统引导改成 in | 说明集合引用和标量比较的区别，修复反馈明确保留原比较含义；未把 `!=` 自动改成 `in` |
| 多目录组合卡住 | DSH 读完首个目录后便禁止补读，修复阶段也禁止读目录；原题后续目录请求确实被 guard 拦截 | standard 模式允许必要补读，保留目录次数、重复调用及修复预算；补读不重置修复预算。fast 的单次目录约定不变 |
| 多条调用塞进一个 request | 贪婪正则把后续调用吞进第一条的参数，报成不存在的参数、limit 类型错误 | 按引号和括号边界解析单次调用，准确提示拆成多个 steps；不自动重写业务调用 |
| 基础信息问题被强迫继续查询 | 框架把所有 `.basic_info` 当成身份预查，忽略它可能就是用户最终所需数据 | 使用现有 `data_request_complete` 表达后续取数依赖，不再从 API 名称推断任务完成情况 |
| 有 summary 却缺少原始结果 | 服务器两组 DSH 子进程实际共用 worker 0/1/2 的同一路径，上下文与 trace 存在覆盖冲突 | worker 文件按服务实例隔离。路径冲突已实证；原次 trace 被覆盖，无法断言还原那一次覆盖的精确顺序 |
| 前面成功、最后失败仍标成功 | 运行时只在没有任何 result_ref 时检查查询错误 | 保留前面数据，但最后查询失败不能成为成功请求；成功修复后可恢复成功 |

没有自动补 `.query` 后缀别名、没有按关键词重写问题，没有把跨视图过滤伪装成合法协议，也没有增加“所有股票涨幅 ≥9.9% 就算涨停”的规则。

### 仍未解决的复杂题

“人工智能板块成分股今天平均涨跌幅和涨停家数”仍失败。需要区分：

1. `plate.constitution.agg(agg=avg(stock.quote.pct))` **本身是已有合法能力**，不是不支持聚合；但默认行情时间口径不能直接等同今天实时行情。
2. `stock.quote.pct >= 9.9` 不是成分股视图可直接接受的 filter 字段；该固定阈值也不能代表所有证券的涨停规则。
3. `is_limit_price` 在历史日 K 来源中存在，但实时 `mode=2` 的可执行字段集合不提供该字段。目录的模式适用范围尚不够清晰。
4. 修复机会内，模型仍可能生成不支持的组合并耗尽推理预算。本次最后一次回归耗时约 105 秒，明确记为失败，不能说性能问题已解决。

后续应先统一“各行情模式的可用字段/时间范围”在目录与执行侧的表达，再设计实时涨停标记的数据来源或可靠计算能力。这是通用能力边界问题，不为这一道题补特例。
