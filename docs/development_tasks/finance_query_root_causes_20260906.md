# 金融查询问题排查与修复

2026-09-06。范围：方法选择、交易日历兼容、日线/分钟行情性能。

## 结论

已修复确定的数据层问题，并更新服务器金融 API。模型、推理强度、工具入口描述和查询协议未改变。方法选择仍有个别规划问题，不能用 HTTP 成功替代效果判断。

## 1. 明细替代聚合：按问题判断，不按方法名字判错

| 例子 | 判断 |
| --- | --- |
| 宁德时代最近10日收盘价、涨跌幅 | 本来就应返回逐日明细。此前先查平均涨跌幅、再尝试不存在的 kline 方法，是模型选择问题；本次接口回归已正确返回10日明细。 |
| 全市场过去20日振幅排名 | 完整日线包含计算所需数据，可以交后续分析，并不必然要使用固定聚合。但有约11.6万行，须考虑数据传递/截断；直接按单日振幅取20行不能替代完整区间数据。 |
| 指数过去20日涨跌幅排名 | 日线或正确对齐的期初、期末价格都可用于后续计算。发现底层把显式历史日期和默认最新日期同时加入 WHERE，造成空集，已修复。模型仍需正确确定窗口和证券覆盖范围。 |
| 机器人热点的热度变化、板块强度 | state 已包含所需字段，省略辅助 basic_info 查询是合理的，不算退步。 |

没有新增语义 validator，没有把明细强行改成聚合，没有给未注册的 compute/kline 增加猜测性兼容。

## 2. 新交易日历：建表时漏了既有查询依赖

实际新表有 market_code、calendar_date、is_trade_day 等字段，但缺少多个近 K 日 Provider 使用的 trade_seq。原建表脚本满足了监控页需求，却未覆盖区间查询契约。

已备份并补齐 trade_seq 和 (market_code,is_trade_day,trade_seq) 索引。242 个交易日按市场连续编号，休市日为 NULL。原365个日期、开闭市标志、来源均未改变。初始化脚本同步修正，再运行插入0行，修复可重复执行。

原基金近20日涨幅 API 已恢复，接口回归取数约0.64秒。注意：目前日历只覆盖2026年，跨到2025年的长窗口仍需补充经核实的历史日历，本次未编造或扩充日期。

## 3. 行情慢：索引与 SQL 形态共同导致

- 日线表原来只有 (trade_date,stk_code) 主键，单股历史查询缺少代码优先索引。已在线添加 (stk_code,trade_date) 索引。单股原 SQL 从8秒诊断超时降到约44毫秒。
- count 查询原来先对全历史做 ROW_NUMBER，再截取每个证券最近 N 条。改为按证券做有界索引读取，保留证券各自的最新日期，不用统一日期排除停牌标的。
- 分钟表已有代码/时间索引。改为先选需要的K线主键，再读取完整字段，避免全历史宽行排序。
- 分钟实现还错误地把 limit 当作每股根数。按既有说明修正：count 是每股根数，limit 是最终总行数，默认 count=240。

固定 API、绕过模型的验证结果：

| 查询 | 修复后取数时间 |
| --- | ---: |
| 全市场每股最近1日日线，按涨幅取前20 | 4.5秒 |
| 宁德时代最近10日日线 | 20毫秒 |
| 全市场每股最近20日日线，完整返回115842行 | 6.1秒 |
| 分钟原请求省略 count，按既有定义每股240根后取前20 | 17.9秒 |

这些是单次数据执行时间，不含模型。分钟查询仍较重；不能为了速度擅自把240根改成1根。
