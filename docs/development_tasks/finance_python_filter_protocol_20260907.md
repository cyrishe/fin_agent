# 金融数据条件协议优化：查询、窗口与聚合

日期：2026-09-07。状态：本地实现及回归完成；服务器仅使用隔离目录测试，未发布生产。

当前目录为 `python-filter-v2`：按用户要求移除首尾匹配的解析与执行，仅保留模糊包含匹配。统一条件说明改为规律性的简述，删除财务目录中反复强调“每年12月31日”的业务引导；接口特有的字段口径与默认范围保留。本次未调整推理预算、重试策略或外层 DSL。下方模型实跑记录来自此前 v1，不代表 v2 的生成效果。

## 1. 结论

新条件表达比原来混合 SQL 风格的写法更统一；解析、引用绑定和执行也更可控。基础查询、K 日窗口、同分钟窗口、行情/成分/研报聚合均已检查，不是只替换简单查询中的 `like`。

但应区分两件事：**确定性执行层已改进；模型整体生成效果尚未证明优于上一版。** 原题 20 条首轮的请求完成数为 18/20，上一轮为 19/20；本轮平均耗时也更高。针对性复跑有所恢复，但仍有业务范围不完整的回答，因此不能据此宣称整体准确率提升或直接全量发布。

## 2. 协议到底改了什么

外层 API 路径、参数名称、`->` 输出、`agg`、`group_by`、`order`、`limit` 和 `k` 的结构不变。主要改变 `filter` 的推荐表达；旧写法继续走兼容入口。

```text
r1 = fund.basic_info(filter="'债券' in name", limit=100) -> code, name

r2 = stock.business_segment(filter="source == 'salessegment' and '新能源' in project_name", limit=50) -> code, name, project_name, segment_sales, gross_profit_margin

r3 = index.quote.kd_pct_sum(k=20, filter="code in ['000300.SH', '000905.SH']", realtime=0) -> code, name, value as pct_20d
```

| 需求 | 推荐表达 | 后端处理 |
| --- | --- | --- |
| 等于 | `name == '贵州茅台'` | 参数化等值条件 |
| 包含 | `'债券' in name` | 转为字面包含的参数化 LIKE |
| 多条件 | `(pct > 5 or pct < -5) and amount > 100000000` | 保留完整布尔树和括号 |
| 集合 / 前序结果 | `code in ['600519.SH']` / `code in r1.code` | 绑定集合值，不把结果文本拼进表达式 |
| 空值 | `field is None` / `field is not None` | `IS NULL` / `IS NOT NULL` |

这里采用 Python 风格的有限条件语法，不是完整 Python，也不需要 `lambda`。模糊匹配统一为字面包含，后端固定补通配符并转义输入中的 `%`、`_`、`!`；普通等值比较仍遵循现有数据库字段口径。已移除的首尾方法不会被偷偷转换成包含条件。

模型仍只表达查询需求。模板决定 FROM/JOIN/计算结构；字段来自目录映射，条件值通过数据库参数绑定。新的 filter 路径使用 AST 解析，不执行模型条件代码，也不靠正则逐条替换条件。外层 DSL、旧协议兼容及其他既有参数解析仍有原来的解析代码，没有声称整个项目完全移除正则。

已迁移 55 个目录示例，并在统一说明里定义一次条件语法。没有增加按用户问题关键词修正意图的规则。

## 3. 窗口和聚合如何处理

| 方法类别 | 条件和计算顺序 | 本次处理 |
| --- | --- | --- |
| 普通查询 | 原始记录筛选 → 排序/限量 → 输出 | 统一条件树编译与参数绑定 |
| 日线 K 日窗口 | 对象筛选 → 完整交易日窗口计算 → 结果筛选 → 排序/限量 | 修复结果条件丢失 OR；不提前按计算结果截断原始窗口 |
| 同分钟 K 日窗口 | 确定分钟及对象 → 对齐历史同分钟数据 → 计算 → 结果筛选 | 统一身份、日期、结果阶段的条件解析，保留现有窗口口径 |
| 行情聚合 | 原始数据筛选 → 分组/聚合 → 排序/限量 | 保留完整布尔条件；修复真正的 median 实现错误 |
| 成分聚合 | 成分关系筛选 + 指标数据筛选 → 按主体聚合 | 修复显式历史日期与默认最新日期同时生效的冲突 |
| 研报/指标聚合 | 研报或指标明细筛选 → 指定分组/聚合 | 共享条件语法，不新增业务分析指标 |
| 动态计算 | 原有取数与计算 → 结果筛选/排序/限量 | 对接条件树；不能完整执行的跨阶段 OR 不再静默丢弃 |

成分关系与指标是不同查询阶段。`关系条件 and 指标条件` 可以拆分；同阶段的 OR 也可保留。跨阶段 OR 如果无法在同一行集上表达，则明确返回结构错误，不能偷偷改成 AND。动态计算若已丢掉判断 OR 所必需的字段，也不能假装过滤成功。

保持既有“通用模板 + 特殊业务公式”的设计：`kd_pct_sum` 的首尾收盘价涨幅、融资余额的 `sum/change/pct_change`、估值百分位等未重定义。`latest` 不会被改写成 `sum`，也没有依据问题文本替模型选日期或方法。

### 确认并修复的确定性根因

1. 原有若干 provider 把条件拆成扁平列表，窗口结果阶段逐项 AND，可能丢失 OR/括号。新路径共享同一条件树；只把安全的必要条件提前下推。
2. 跨结果引用原来依赖文本替换，可能把字面量中的引用样式当成引用；空集合处于 OR 分支时也不能一概终止。现在绑定树节点，保留另一分支。
3. 成分指标聚合即使明确给了历史日期，仍叠加默认 MAX 日期，造成冲突/空结果。现在仅在没有显式日期时使用默认最新日期。
4. 日线、分钟/实时 `quote.agg(median(...))` 内部曾直接使用全量 AVG。这是 provider 实现错误，不是模型理解错误。已使用共享的排序取中间项模板修复。K 日 `kd_*_median` 原先就有正确排序和取中间项的实现，其末尾的 AVG 是正确算法的一部分，未误改。
5. 第一步请求在生成进度标题前报错时，错误处理可能再次引用未初始化的变量；现已初始化，原始协议错误可正常返回给模型。
