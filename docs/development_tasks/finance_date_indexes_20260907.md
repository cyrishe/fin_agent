# 新 kingdomai 日期索引与查询优化

2026-09-07。范围：`47.94.1.2:3312/kingdomai`；不修改旧库或 `stock_agent`。

结果：已在线新增 **36 个索引，涉及 25 张表**。未删除旧索引、未修改业务数据。所有 DDL 成功且索引存在性已逐项验证。

其中 18 个用于监控日期统计、7 个用于证券行情/资金/估值/两融历史、4 个用于按公司查询披露/财务、7 个用于公司披露跨证券日期范围。最后只读复查已无待新增候选；小表按既定策略保留现状。

## 改了什么

- 依据实际 Python provider 和状态页的 SQL 访问方式审查索引，不给所有日期字段盲目建索引。
- 行情、资金、估值、两融的历史查询：补充缺少的“证券代码 → 日期”索引。保留原来的“日期 → 代码”主键，供市场截面和日期区间统计使用。
- 公司披露/财务：按实际需要补充代码/报告期、业务日期、监控日期索引。
- 状态页：补齐大表的 `update_time` / `ann_date` 等索引，使原先“待优化日期索引 · 已跳过大表全扫描”的监控项能重新观察。研报监控沿用 `reports.publish_at`，指标事实通过 report_id 关联；没有凭空给指标表增加发布日期。
- 五类行情（股票、基金、债券、指数、板块）的 `count=N` 共用按证券限量读取模板，不再让非股票先给全部历史排序。之后再执行原来的整体排序与 limit。
- 全市场、明确日期/日期区间的查询仍优先使用日期主键扫描，在该范围内排序；不机械地改成逐证券随机读取。回归中发现后一种做法会使债券单日截面从约 0.66 秒退化至 2.27 秒，已保留日期扫描路径。

API 名称、参数、模型目录描述及业务输出字段不变；没有增加模型调用、业务判断器或新的协议状态。

## 三个月策略

三个月是**优先读取范围，不是数据保留范围或业务截止线**。

| 查询类型 | 处理方式 |
| --- | --- |
| 公司披露多来源、按时间取最近 N 条 | 复用三个月优先读取；不足 N 条则丢弃预查，执行一次完整范围查询 |
| 股票/基金/债券/指数/板块最近 N 条行情 | 直接走代码/日期索引；无需先查三个月再回查，长历史和稀疏证券也保持一次查询 |
| 分钟 K | 保留已有实时/历史有界读取，不用日级三个月规则替代实时性 |
| 财务三表、资金、两融、估值的默认查询 | 保留最新报告期/最新日期截面，不擅自改成近三个月明细 |
| 研报原文/指标 | 保留可选三个月预查接入；默认不额外预查，避免稀疏或空结果多一次数据库往返 |
| 明确历史日期、全量、聚合、交易日窗口 | 保留用户及 API 的范围；不自动截成三个月 |
| 基础资料、成分关系 | 不按近三个月排除仍有效的老资料/关系 |

`FIN_AGENT_RECENT_SCAN_ENABLED` 不设置时按上述策略；`0` 关闭预查；`1` 仅用于安全条件满足的诊断 A/B。不会让聚合变成三个月聚合。

## 回归发现的实际问题

股票模板原有 `code=A OR code=B` 会放弃证券范围下推，导致枚举全市场，本次真实对照触发 20 秒超时。修复为：纯证券条件的完整表达式可原样下推；混合 OR 不抽取局部条件，避免漏数据。修复后该股票样本约 55 ms，返回的 4 行与完整历史参考 SQL 一致。

## 操作与证据

- `scripts/optimize_finance_date_indexes.py`：默认只读审查；指定 `--apply` 才执行。限定新 kingdomai，识别等价索引，不重复创建；每表变更前保存建表语句、索引、执行计划。使用 `ALGORITHM=INPLACE, LOCK=NONE`，失败不降级到锁表复制，不自动重试 DDL。
- 小于约 10 万行且非研报日期入口的表，先保留现有索引；不是每个可能的索引都值得增加写入成本。
- `scripts/verify_finance_quote_topn.py`：相同只读快照内，对比参考 ROW_NUMBER SQL 与新有界 SQL 的完整有序结果及 SHA-256；不是用行数替代正确性验证。
- `scripts/verify_finance_recent_scan.py`：完整结果对比预查开/关，覆盖跨三个月、明确历史日期、空结果及各公司披露视图。
- 原始证据：`outputs/finance_date_indexes_20260907/`。保留最初超时记录，不将失败算作通过。
