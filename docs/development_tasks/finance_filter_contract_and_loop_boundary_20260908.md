# 有限筛选契约与 Loop 边界优化

2026-09-08。本轮承接研报 20 题的四题追溯，以修正设计问题为目标，不追求消除所有首次生成错误。

后续修订：根据用户最新反馈，文本包含已改为 `field.contains('文本')` 并接入解析器；下文记录的是第一阶段修改。当前推荐协议与实现以 [contains 有限操作集](finance_filter_contains_contract_20260908.md) 为准。原文本 in 写法只作兼容，历史评测结果保持原样。

## 判断与实施范围

| 问题 | 判断 | 本次处理 |
|---|---|---|
| `name.lower()` | 提示只写“Python 风格”，执行却是有限表达式，两者的能力边界没有对齐。不能从一个样本证明唯一因果，但定义不完整是确定的问题 | 明确有限操作范围；保留 AST 和参数化 SQL，未扩展或改变解析行为 |
| 催化分析错走 metric | 旧 report 描述已有“催化因素”，不是完全缺少引导；与核心观点字段的联系可以更直接 | 在 report 视图、明细用途和 investment_highlights 字段各自层级正向说明 |
| 蔚来零行 | 初始研报查询的入口、协议、执行可以视为通过；没有匹配数据不等于协议失败 | 保留历史结果；新增 A 股正向样本与非 A 股覆盖对照，合法零行均按取数通过评价 |
| `.query` | 上层目录的 operation 与实际 API 路径混淆，且没有读取目标执行包。不是“多写一个词”这么简单 | 在统一目录入口精炼说明：operation 选择执行包，实际调用使用包内 api_name/request_pattern。没有添加禁止词或自动去后缀逻辑 |
| 修复机会被拦 | tool/call 先计数，guard 再用 >= 拒绝，导致预算最后一次无法执行 | 修正查询、目录、明细读取的同源计数边界，预算数和最大修复数保持不变 |
| 基础信息描述超出字段范围 | 描述包含公司简介、主营业务，但实际只有 4 个身份字段 | 描述收敛到代码、名称、行业、上市日期；没有新增数据字段 |

SOFT 改动是目录用途与契约表达。HARD 改动只有既有调用预算边界修复；没有新状态、validator、协议层或公司特判。其他任务正在修改的业务 Skill 未被本轮改写。

## 1. 现在模型看到的筛选范围

原文：

```text
filter 为条件表达式字符串，支持范围：比较 == != > >= < <=；组合 and/or 与括号；文本包含 '文本' in field；集合 field in [...] / field not in [...]，列表也可用 rN.column 或 stepN.column；空值 field is None / field is not None。字段取自当前方法，值使用带引号的文本、数字、True/False 或 None。
```

这是对现有协议的有限表达式说明，而非完整 Python 授权。文本包含继续采用已有的 `'文本' in field`，其内部语义为 contains；没有新增 `contains()`、中缀 contains 或另一套匹配语法。规范比较使用 `==`；旧 `=` 等兼容输入仍由原兼容边界处理，没有破坏历史调用。

位置与加载方式：

- 唯一源：`src/tools/finance_data/catalog/api_view_catalog.json` 顶层 `filter_syntax`。
- 装配：`FinanceDataToolCatalogService._build_model_dataview`；有 filter 参数的执行包获得该说明。
- 第一层路由索引不携带筛选语法。选到具体执行包后加载一次，不按公司、不按题目增加例子。
- 明细、窗口、成分关系和聚合共享此说明；本次测试逐视图检查同源装配。动态计算仍使用其已有方法定义，没有借此限制自然语言计算需求。

解析器、字段验证、条件树、引用绑定、窗口计算和聚合算法、SQL 参数化全部未改。任意 Python 函数或方法调用仍按现有安全边界拒绝。

## 2. 研报观点的正向用途

三处职责不同，不扩张成通用分析提示：

| 层级 | 现在的说明 |
|---|---|
| report 视图描述 | 逐篇机构研报的评级与变动、目标价、核心观点、风险和来源；核心观点提供增长催化、业绩驱动、竞争格局与市场份额、竞争优势及战略展望的分析依据 |
| stock.report 明细用途 | 查询逐篇研报的评级、目标价、核心观点、风险与来源；investment_highlights 提供机构判断的理由与催化因素 |
| investment_highlights 字段 | 机构投资逻辑与判断依据，包括增长催化、竞争优势和经营展望 |

字段原来的“投资要点 / 核心观点”别名保留。研报聚合仍专注分组统计，不塞入催化分析策略。分部数据、财务数据可作为分析背景，没有强制所有包含“催化”的问题只查 report。

## 3. 阳光电源实际使用过的提示词

[按五层阅读的历史原文](evidence/report_protocol_failures_20260908/RTE020_actual_prompts.md)：

1. 常驻系统提示。
2. 用户问题、系统日期、授权 Skill 目录、快速回答要求。
3. 五个工具的说明与实际参数 Schema。
4. 真正读到的 stock 概览、两份 Skill 正文以及后续 report/basic_info 执行包。
5. 各轮阶段提示。

首次错误前的重要原文包括：

```text
subject 定对象，dataview 定数据，operation 选方法。
明确的数据请求一次读取对应执行包，按其中的精确 API 入口、调用格式、参数和字段构造请求。
```

当时读到的 stock 概览只是：

```json
{"name":"basic_info","desc":"股票代码、名称、行业、上市信息、公司简介与主营业务。","operations":["query"]}
```

此外读过 sector-theme-analysis 和 stock-research 的正文。**basic_info 的精确调用格式并未在首次错误前加载**；第 4 轮才读到。系统有分层说明，不代表每次执行都已经获得对应视图的契约。

本次把入口工具原来的一句说明替换为：

```text
operation 用于选择执行包；调用使用包内的 api_name、request_pattern、参数和字段。
```

这是一条通用、正向的目录与调用关系说明，不是“禁止 .query”的反向补丁。没有引入强制为每条请求再次读目录的流程，也没有宣称一句话会彻底消除幻觉。

历史文件保留当时真实文本，不以现在修改后的 catalog 或其他任务的新 Skill 替换。全部调用与错误另见 [RTE020 完整现场](evidence/report_protocol_failures_20260908/RTE020_context.md)。

## 4. Loop 的修复机会

本轮目标是保证系统兑现原有预算，不是提高容错次数。

```text
Harness 记录 tool/call → 本次计数已经 +1 → guard 检查
旧：本次计数 >= 上限就拒绝
新：本次计数 > 上限才拒绝
```

查询、目录读取、明细读取共用这一调用顺序，因此一起修正。原 `maxQueryAttempts=3`、`maxQueryRepairs=1` 保持不变。第 3 次可以用于已有修复；第 4 次仍拒绝，阶段完成、重复调用等原有约束也保留。

测试按 Harness 真实顺序“先 tool/call，再 guard”执行，覆盖预算内调用、最后一次调用、同轮超额调用、失败后修复、合法零行和稳定前缀两种模式。旧测试有一处在下一次 tool/call 尚未发出前检查次数上限，本次同步修正了这个模拟顺序。

此前 detail 工具记录遗漏守卫/Schema 提前拒绝的问题仍保留在追溯报告中，本次没有顺带重构 trace 汇总。

## 5. 零行与样本

通过标准应区分三个维度：数据入口/协议正确、请求执行成功、结果是否有记录。合法查询零行可以通过前两个维度，不应因数据稀缺去倒逼模型反复换条件。

蔚来不是 A 股，但这也不意味着研报库绝不可能收录它。用实际返回判断覆盖，不在引擎中按公司名称或市场强制空结果。

原始 20 题及原始首跑不改写。`tests/evals/finance_data_chat_v1.json` 增加：

- 看多比亚迪的机构主要理由是什么？——A 股的正向取证样本。
- 看多蔚来汽车的机构主要理由是什么？——保留非 A 股覆盖对照；合法零行视为取数通过。

这是下一轮评测资产，尚未调用模型执行。更换主体后的结果不会冒充原题改善。
