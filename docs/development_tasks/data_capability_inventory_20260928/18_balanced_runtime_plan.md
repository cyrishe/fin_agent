# 计算量、时效与行情API压力：首期运行方案

日期：2026-09-28。本文是进一步分析后的首期建议；没有改变生产采集、任务调度、数据库或通知配置。运行现状以16为准，17保留区间回放实验。本次新增了服务器100股的有界只读容量样本。

## 推荐决策

**现有全市场分钟事实保持10分钟分批采集，优先将批内突发请求改为平滑限速，并减少未变化数据的重复派生/写入；指标查询按需计算并复用；已启用的个人或平台公共信号任务按时效要求自动检查新到数据的完整区间；普通观察报告可默认30分钟；主动查询即时使用最新已到库数据。所有任务按股票、分析周期和输入合并，模型解释按用户任务需要生成。**

普通观察的输出以当前状态、持续性和必要区间摘要为主。分钟条件短暂成立不自动升级为提醒；捕获触发数量不是分析质量指标。先把新增标准分钟指标的定时运行做到零额外上游行情请求，再考虑降低已有采集本身的请求量。

这不是承诺所有功能10分钟内更新：全市场采集存在批间到达时间，结果必须保留实际数据截止时点。计算频率不能改善源数据尚未到达的问题。

## 哪些能力必须后台运行，为什么

不能从“指标使用历史/递归计算”直接推出“必须在过去每个时刻执行过”。也不能因为历史可重算，就认为及时提醒和公共信号服务可以完全取消后台执行。应分开判断输入能否保留、计算能否重建，以及产品要求何时交付结果。

| 能力 | 能否用保留数据事后重建 | 后台运行的必要性 |
|---|---|---|
| 当前MA、BOLL、量能比、session VWAP等 | 可以，需完整输入、明确时点与口径 | 普通问答无需预计算；高频共享预计算属于性能选择 |
| 当前session MACD/RSI/ATR | 可以，需固定递归起点/初始状态和完整历史 | 递归不等于必须常驻运行；现有代码就是按输入历史重算 |
| 交叉、连续三根站稳、先突破后回踩等已完成K线规则 | 可以，需要逐根处理足够历史和前序上下文，不能仅取末值 | 事后问答不要求曾经定时执行；要求及时发现时必须自动检查 |
| 风险提醒、持续更新的候选名单/公共信号池 | 可以重建部分市场条件，但不能事后补回当时的提醒或响应 | 一旦作为产品能力启用，就要后台运行；平台任务不以某个用户当场提问为前提 |
| 仅保留当前值的报价/盘口瞬时条件 | 未保存的输入通常无法准确重建；分钟OHLC不包含完整逐笔路径 | 首先需要相应采集与留存；及时信号还需要随采集检查，单独提高计算频率无效 |
| 当时实际发过的提醒、阈值版本、用户确认或真实成交 | 不能仅凭K线重建真实操作历史 | 在实际发生时记录事实；定时重算不能代替事件记录 |

以“连续三根5分钟收盘站上某个已确定价位”为例：10:05、10:10、10:15都满足，10:20又跌回。10:30读取完整历史，可以判断10:15曾完成确认，无需计算进程在10:05就启动。但若承诺10:16提醒，就必须在相应数据到达后自动检查；当前10分钟批采未必已取得10:15数据，即使每分钟运行公式也无法兑现这一时效。

本次核对的DSA `src/stock_analyzer.py`通过相邻两根DIF与DEA差值判断交叉；InStock `turtle_trade.check_enter`读取历史窗口比较收盘位置，均不依赖“昨天任务有没有运行过”。但只在10:30对最后两根做交叉判断，会漏掉10:05已经出现又消失的交叉；必须逐根扫描待处理区间，而不是单纯提高snapshot调用频率。

本方案形成时，分钟查询适配器只返回末值。现已实现逐根序列、区间信号与现有任务调度接入，具体代码及未部署边界见[19](19_minute_signal_implementation.md)。当前实时快照8项也只有短缓存；若将来要求保留快照级历史事件，需要明确采样粒度和必要证据，不能声称现有1分钟K足以恢复供应商所有实时值。

信号任务只处理已启用的规则和股票范围。时效要求接近当前采集能力的任务，在新数据到达后评估；允许半小时滞后的任务可每30分钟检查全部新增K线；模型报告可以采用独立的30分钟汇总频率。没有平台或用户任务要求时，不创建全市场通用定时预计算。

后台必要状态首先是已覆盖到的实际数据时点以及真实事件记录，用于恢复和去重，沿用已有任务资产；业务公式中的临时中间状态通常可以重算，不为每个条件新增持久化状态机。保存规则版本、输入依据、信号对应K线时间和实际发现时间，避免将事后回放或迟到信号伪装成当时实时发现。历史修订后的重算也不能覆盖“当时实际发过什么”的事实。

因此，30分钟既不是所有分钟指标统一刷新周期，也不是所有信号成立的前提。后台信号处理应作为能力保留，是否启用、范围和间隔由明确的服务用途与时效决定。

## 已验证的成本分布

在现有服务器Python3.10.12、pandas2.3.3、numpy2.2.6环境，只读取当日顺序前100个日线股票代码的分钟数据。其中99只各有240根完整1分钟K，1只无分钟输入，共23,760行。未调用上游行情API、未修改数据库、未向外复制行情明细。

| 项目 | 本次耗时 | 边界 |
|---|---:|---|
| 连接、日期/代码读取、5组每组20股分钟查询 | 1.2313秒 | 行情只读取一次，后续在内存复用 |
| 100股范围1分钟指标冷计算 | 5.8783秒 | 99份完整输出，含聚合、输入编码和全部指标公式 |
| 相同输入1分钟指标再次计算 | 3.4668秒 | 公式缓存命中；仍然进行了聚合和编码，不含再次读库 |
| 100股范围5分钟指标冷计算 | 2.9913秒 | 99份完整输出 |
| 相同输入5分钟指标再次计算 | 1.1599秒 | 公式缓存命中；不含再次读库 |
| 单进程峰值RSS | 约122MiB | 包含Python、依赖和样本，不能直接按股票数等比例外推 |

脚本：[probe_minute_capacity.py](../evidence/data_capability_inventory_20260928/probe_minute_capacity.py)。结果：[minute_capacity_server.json](../evidence/data_capability_inventory_20260928/minute_capacity_server.json)。这是盘后单进程样本，不是交易高峰并发压测，也没有测试数据供应商的容量或允许配额。

**推论：** 当前百股级标准指标计算没有必要为了节省几秒钟而统一牺牲问答时效。缓存需要覆盖重复读库/聚合，而不只缓存公式最后一步；普通任务少展开不需要的周期，比把一切都推迟到30分钟更有针对性。千股、全市场及多进程负载仍应实测，不按本样本直接承诺SLA。

|---|---:|---:|---:|---:|---:|
| 14:40 | 5,708 | 17.276秒 | 200秒 | 132.009秒 | 349.975秒 |

三轮`error_targets=0`、无超时未完成目标，但每轮只有5,098只被计为有当前有效K，另有370个空结果目标；该覆盖计数不是全日分钟完整率，不能把其余股票全部认定为停牌或有效数据缺失。需要核对交易状态和空/旧数据原因，不能因一次空结果就剔除目标。

这些日志显示的首要优化点是**批内请求突发、重复持久化和固定等待**，不是Fin Agent新增的数学公式。按日志抓取阶段时长换算约321—330次请求/秒，这是抓取阶段均速，不是逐秒峰值测量；批间40秒等待不能为批内峰值提供硬上限。

## 各层执行与保存

| 层 | 首期执行规则 | 上游API与保存 |
|---|---|---|
| 日线指标 | 保持现有盘后共享批次 | 沿用日线两表 |
| 原始分钟K | 保持stock_agent现有10分钟分批采集 | 不因新增指标再抓一份；保留1分钟事实 |
| 普通观察任务 | 配置后可默认30分钟一次，仅处理任务股票并集及所需周期 | 只读库；共享相同输入结果；任务摘要/证据留存；不是全局预计算 |
| 主动问答 | 立即读最新可用缓存；缺失或输入变化时按需计算 | 默认只读库；明确数据截止时点 |
| 已启用的个人/平台公共信号监控 | 按服务时效自动执行；较及时任务配合10分钟数据到达，检查全部新增K线；输入未变不重复计算 | 只读库；保留真实发现与通知记录；不能声称获得逐分钟送达的数据 |
| 最新价格类问题 | 需要时复用现有实时快照入口 | 同机共享短缓存和请求合并；仅取确有需求的股票 |
| 严格最新分钟指标 | 需要补齐最新分钟历史时，进入采集侧统一限额的按需补取 | 此路径尚待接通，不能用最新价冒充最新MACD历史 |
| 模型解释/报告 | 用户询问、配置的报告时间或明确需要解释的变化 | 确定性公式不调用模型；不为每股每个周期重复生成报告 |

执行间隔不是K线周期。30分钟任务仍可使用5分钟K指标。首期默认仅展开任务要求的周期，不能每次对7个周期全展开。当前session递归指标每日重新预热；扩大执行间隔不会补足历史，数据不足仍返回不可用。

共享以数据计算为单位：相同股票、周期、公式、完成/试算口径和实际输入复用；个人阈值、持仓与解释仍保持各自归属。缓存包含真实输入版本或内容指纹，同时间戳的修订不能被旧缓存遮蔽；旧结果的data_as_of不能刷新成现在。

首期可以在现有进程/同机缓存和任务批处理内实现，不为预计中的高并发先引入新消息平台或分布式计算框架。现有公式LRU仅每进程128项，并非已经实现跨进程共享的分钟结果缓存；上表中的完整复用需要补足。

## 行情API控制：先避免增加，再按证据减少

`stock_indicator_minute.py`查询既有分钟表，外部请求数为0。每半小时重算、不重算或者多算几个指标，都不会改变stock_agent已经发出的采集请求。现有采集单只股票一次请求，1000只一批是客户端分组，不是供应商一次批量API。

首选改造是在原采集器增加一个显式请求速率上限，同时保留并发上限；以均匀派发替换固定批间40秒暂停，不能在现有暂停之上机械叠加限速，导致每轮超时。未变化OHLCV的重复派生和覆盖写也应优先减少，同时保证补数和修订会重新计算。

按最近三轮样本，**25次/秒可作为受控验证的候选配置**：5,708次请求约需228秒，加现有132—164秒持久化，合计约360—392秒、另加少量开销，接近当前350—382秒。它有望在维持10分钟周期时显著压低抓取阶段突发。此值是排程估算，不是供应商公布或批准的配额，也未实际改动或试跑；必须以供应商约束和完整轮次实测为准。如果许可速率更低、无法完成10分钟全量，才进入以下分层降频方案。

以先前核对的5,708只采集范围、240分钟交易网格作容量算术，忽略开收盘额外轮次、缺数修复和失败：

| 采集安排 | 每交易日预计单股请求数 |
|---|---:|
| 全市场每10分钟 | 5,708×24=136,992 |
| 全市场每30分钟 | 5,708×8=45,664 |
| 全市场30分钟，另100只关注股10分钟 | 45,664＋100×16=47,264 |

第三种相对第一种理论减少65.5%的请求，**它才是实质减少现有上游调用总数的方向**。但本期不直接改为该模式，原因是这张表同时服务市场概览、实时排名、动量排名和既有指标刷新。让关注股10分钟、其他股票30分钟更新后，直接取全表最大时点可能只得到关注股截面，或者混合不同时间数据，影响全市场结果。

若采集日志显示现有调用超出约定配额或造成持续超时，下一步就实施30/10分钟分层采集，前置工作仅包含确实必要的三项：

1. 全市场比较明确使用共同基准时点和覆盖数量，关注股较新行情不混入同一截面冒充全市场；检查上述实际消费者的时间语义。
2. 修改取数覆盖窗口。当前20根无法覆盖30分钟；普通轮可先以60根作为验证起点，并按最后成功覆盖位置补缺。60根不是故障恢复保证，失败跨轮时须按缺口取更长历史，沿用现有低优先级补数能力；午休和收盘单独收尾。
3. 在现有采集端统一约束常规、按需和补数请求，限制速率及并发并合并同股请求。降低每日总轮次不等于降低轮内峰值；需要平滑派发和实际供应商限额，不能只靠增大批次间隔。

当前新实时指标入口的30批/分钟限制只约束该入口，不覆盖所有旧行情调用；不能当作全系统或供应商批准的额度。API总压力仍需以采集日志、失败率与供应商约定为准。没有明确配额时，不扩大现有全市场采集频率或并发，也不让每个用户各自启动一套自动补取循环。

上述每日调用总数仍是配置与股票范围的算术估计，不是本日完整实测总量；三轮无错误也不能代表长期稳定性或供应商限额验收。降低请求次数不必然同比降低字节数或数据库写入：例如20根×24轮与60根×8轮的名义返回条数相同，需要分别量测。

## 数据库与输出量

每轮按股票批量读，多个周期复用同一份分钟输入；同一时刻不同用户的重叠股票合并。按内容指纹复用最新指标，减少重复查询、聚合与计算。当前按需接口最多20股/次，批处理沿用分块，不直接把整市场送给模型。

原始分钟K继续使用现有事实库；分钟指标只保留有界最新缓存，任务保留自身报告、必要区间摘要与证据。不追加全市场每轮指标历史。6,000股×8轮×21天仍约101万行/月，因此半小时频率本身不能解决全市场历史落表体量。

如未来确实要跨服务永久保留最新指标，可再评估每股每周期覆盖更新的快照，记录数随活跃股票与周期数变化；当前不为此新增数据库表。

## 实施顺序与验收

1. 在stock_agent现有采集器受控验证平滑限速与取消相应固定等待，检查整轮耗时、尾批覆盖和收盘收尾；排查无需采集的已退市/非目标证券以及空结果原因。API候选限速必须服从源方约束。
2. 批量读分钟事实、共享多周期输入、缓存完整结果；正常分钟分析不新增外部调用。当前问答接口保持兼容。对采集端未变化数据减少重复派生/写入，并验证历史修订仍会生效。
3. 接入现有用户任务：普通30分钟、明确持续监控10分钟、临时提问按需。相同输入不重复计算，不重复生成模型报告；保留实际数据时点。
4. 补充区间计算/持续性摘要，使报告区分当前状态与期间变化，业务规则决定哪些变化值得提醒。上次未到的数据后续补扫，不能把检查时间当作已处理到的数据时间。
5. 先验收100股、单周期及两个周期、多用户重叠查询，再依据真实负载增加范围。记录DB读取、CPU、缓存复用、源数据滞后、外部请求数和失败；百股样本不是全市场容量证明。若需要降低现有请求总数，再按前述消费者适配与完整性验证落地30/10分层采集。

这是一个首期方案及清晰的采集降压边界，不是额外增加一套调度系统。默认优先复用已经取得的数据，时效要求更高的服务只覆盖明确需要的范围。
