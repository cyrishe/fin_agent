# 分钟按需补取、龙虎榜双源与竞价采购调研

2026-09-28。根据用户最新确认修订方案。仅进行了公开页面/接口的小样本只读请求、源码解析回放和文档整理；未新增生产采集、写数据库、采购或部署。

**结论：十分钟批量分钟K保留为基础覆盖；即时问题允许按需补取并立即计算；持续监控对订阅股票并集刷新和计算。龙虎榜采用东财主源、新浪备用，主源失效才切换，通过基本抽取检查后入库，不增加日常双源比对或冲突裁决。竞价结果与竞价过程分别选源，不能用日线或连续交易分钟K替代。** 本文对09中“不允许按需直取”“免费来源一律排除”的旧建议作出修订，其余已核实的采集器事实仍有效。

## 1. 十分钟延迟是否可以接受

取决于问题要求的观察时点；不能对所有分钟指标笼统回答“可以”。

| 用户问题 | 十分钟左右延迟是否适用 | 获取与计算方式 |
|---|---|---|
| 复盘上午走势、比较昨天各时段量能 | 对已经结束且完整的目标时段适用 | 读历史库，按需计算 |
| 看截至14:30的分钟趋势结构 | 适用，明确截止时间 | 读库或已有该版本结果 |
| 现在是否突破、最近5分钟是否放量 | 不适用，必须取得足够新的输入 | 指定股票按需补取最新分钟尾段，与库内历史对齐，立即计算 |
| 持续盯住我的100只股票，突破时提醒 | 需要连续更新；不能等用户再问才发现 | 对所有订阅用户的股票并集刷新，收到新数据后计算所需指标 |
| 秒级价格穿越、竞价过程中未匹配量突变 | 普通分钟K不足 | 使用具备对应时效和字段的快照/推送/竞价接口 |

例如14:43提问“目前5分钟趋势是否突破”，若要求完成bar，可以补齐至已发布的14:40完整5分钟bar及所需历史；若问最近5个交易分钟，应使用对应滚动窗口；若要观察尚未完成的14:40–14:45窗口，则需要最新分钟尾段或实时行情，明确为临时值。不能用一个最新成交价伪造整根OHLCV，也不能把“完成5分钟bar”与“过去5分钟”混为一谈。

### 建议的执行路径

1. Skill根据自然语言确定股票范围、指标、完成bar或当前临时窗口，以及问题的时间要求；不强制每个用户填写技术参数。
2. 查询统一数据入口；数据足够新且窗口完整时直接计算或复用结果。
3. 数据不满足本次时间要求时，在供应商总预算内补取指定股票的最新尾段。历史初始化窗口仍读库；超过正常20根重叠覆盖范围的缺口须另行补足，不能拼接成假连续数据。
4. 新数据统一单位、复权和交易时段后进入共享事实缓存/现有存储，再立即计算本次需要的指标。不同来源重叠窗口须核对口径，不能机械拼接。
5. 同股、同窗口的同时请求合并；后来的请求复用足够新的事实与计算结果。刷新失败就说明当前时点无法确认，可附旧时点结果，但不能声称已回答“现在”。

采集刷新与指标计算是两个独立决策。**一次问答立即按需算，持续监控随输入更新算，公共日线盘后预先算。** 不全市场每分钟预计算所有技术指标；有活跃监控时，也不每次输入变化都调用大模型。数值条件由确定性函数执行，解释和交互由Skill处理。

缓存依然有价值：已完成历史窗口、同一最新输入的重复问答、同一次在途请求均可共享。实时快照可使用符合业务时效的短缓存；结果缓存以输入时点/修订及公式参数定位。TTL不是“新鲜”的证明，数据停更时不能通过续TTL继续称实时。

### 限流与容量

现有5,708只股票每600秒一轮，跨轮平均约9.51次单证券请求/秒，存在批内突发；这是本地名单和实现的算式，不是上游承诺额度。新增200只股票每60秒刷新，若仍为单证券请求，单独测算约3.33次/秒；调度去重可能降低新增量，重试和补缺会增加量。不能认为“只加200只”就没有压力。

后台基础轮询、订阅刷新、按需补取及同供应商其他实时调用共同记账，合并重复对象；在既有入口内实现限流和优先级即可，不新建通用调度平台。按需刷新要有预算，持续高频需求按用户订阅股票并集规划。优先核对既有UpChina供应关系的额度、商用范围、完成分钟发布时间和尾段取数能力；本轮没有压测现有接口，因此没有承诺新的延迟SLA或可售股票数。

### 为什么适合沿用，以及如何落地

龙虎榜披露后才产生，适合盘后低频统一取数、入库、多用户共享。网页展示改版未必影响背后的JSON数据，优先解析命名字段；新浪分类HTML只负责发现证券、日期和原因，再取命名字段的席位数据。InStock的东财席位函数按列位置重命名，不建议直接照搬。

按用户最新要求，生产路径只保留：

`东财取数 → 基本检查通过 → 入库；东财请求/解析失效 → 新浪取数 → 同样检查 → 入库`

以一次日期/证券/上榜原因的披露为单位选择一个来源，不拼接两家的买卖席位，不做每日投票、金额裁决或双源合并。保留来源和取数时间即可追踪；无需因备用源可用而额外获取一份主源正常的数据。盘后发布时段抓一轮，必要时少量补查修订，所有用户共享入库结果。

抽取只做四类基本检查：

1. 日期、证券、上榜原因与本次请求对应，区分单日和多日榜，避免同股多个原因互相覆盖。
2. 必要字段存在，买卖方向没有颠倒，金额可解析并按来源单位转换；错误页/字段缺失不能当作有效空榜。
3. 同一披露中的完全重复记录不能被重复计入；同名机构席位不能仅按名称去重。已知重复导致明细不完整时，这份异常明细不覆盖已有有效数据，不据此伪造完整净额。
4. 保存来源与抓取时间，入库幂等；两源都无法取得有效结果时保留旧数据并说明本日未更新，不写零或“未上榜”。

这些检查放在现有取数/适配函数和少量固定样例中，不建设通用数据质量框架，不新增业务状态机。小样本测试覆盖日期、单位、多个原因和此次重复样例即可。长期可用率仍需上线后观察，本轮不声称已经验证。

### Skill维护解析模板

这个设想可以采用，定位为采集维护能力，复用现有代码修订、测试、发布机制：

`保存失败响应样本 → Skill比较原模板与新结构 → 生成解析补丁 → 历史和新样本回放 → 发布有版本的解析器`

机器保留来源、样本、解析器版本和运行证据；Skill理解页面变更，不额外建立一套业务状态机。只影响定位/字段结构的改版，可以在回放通过后沿已有发布流程替换并可回滚。回放复用上述基本检查，主源修复期间由备用源承接。上游缺数据或网络失败交给已有重试/主备路径；Skill负责解析变化，不猜造缺失的席位或金额。

### 如何组合进我们的数据体系

- **开盘结果**：全市场在结果可用后统一拉取，少量检查修订后入库；竞价金额、开盘幅度和相对历史竞价量能等共享计算。用户9:28问“今天哪些股票竞价明显放量”可复用这批数据；这回答不了9:20的状态。
- **竞价过程**：需要竞价期间分析时，对订阅股票并集用专用接口刷新/推送，按需计算变化率、未匹配量等；若供应商允许事后取回完整当日序列，复盘可事后批量获取，无须全市场实时持续轮询。
- **保存历史**：本文通达信竞价接口只明确当日参数，不能假设有多年历史。若试用证明可拉全当日序列，可在当日留存后做历史基线；回测缺失历史另购，不以今天开始采集伪装已有多年样本。
- **因子边界**：虚拟价、匹配量变化能刻画可观察的竞价过程，但不自动等于逐笔撤单量或某类资金的真实意图。InStock“抢筹”是供应商派生排行，不能与上述事实互换。

### 下单前需要供应商回答的具体问题

优先向既有行情供应商核对同等能力；新增供应商试用重点如下，不泛泛索要“有竞价数据”：

1. 沪深京分别覆盖什么，开盘/收盘竞价是否都含；过程接口在9:15–9:25期间是否持续更新，实测发布时间和时间戳精度是多少。
2. 匹配/未匹配量的股/手单位和方向符号，是否为完整过程快照、采样频率如何，盘后能否重取全序列及保留多久。
3. 历史起始日期、漏点/修订处理、批量上限；批量SDK是一次后台请求还是内部逐股循环，如何限额/计费。
4. 公司账户在Fin Agent中缓存、跨用户共享计算、展示原始值和派生结果分别怎样授权和报价；明确企业价格及服务支持，不能用个人试验价格直接估算对外产品成本。

建议先交付“已有日线指标 + 分钟按需补取 + 龙虎榜盘后主备入库”，竞价结果与过程分别试用选型。其中通达信正式接口值得优先验证过程数据，Tushare可作为开盘结果的明确预算候选；米筐作为结果/历史与整体数据服务的询价备选。三者均未被本轮宣布可直接投产。
