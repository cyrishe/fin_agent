## 2. 全盘分类：技术只是其中一部分

### 2.1 按金融业务领域分类

| 领域 | 典型数据/指标 | 主要回答的问题 | 仓库与现有系统的关系 |
|---|---|---|---|
| 行情和交易事实 | 日/分钟 OHLC、成交量额、换手、涨跌停、有效时点 | 价格和交易活动发生了什么 | Fin Agent 已有日线、分钟K和最新快照入口 |
| 技术趋势与动量 | MA、MACD、RSI、KDJ、ROC、DMI等 | 趋势、动量、摆动与背离如何 | InStock 的主要本地计算增量；现有 MA/MACD/RSI 部分重叠 |
| 波动与量价结构 | ATR、BOLL、量能倍数、前高、形态、筹码估计 | 波动是否收缩、是否突破、成交集中在哪 | 原始数据可复用；估算和确定性特征分开命名 |
| 交易资金与市场结构 | 大单资金、两融、龙虎榜、板块广度、相对强弱 | 参与度、交易结构与风格有什么变化 | 部分已有 moneyflow/margin/aggregate；席位等须补源核验 |
| 财务和成长质量 | 收入、利润、现金流、ROE、利润率、负债率、增长 | 经营是否改善、利润是否可靠 | 现有三张报表和派生指标覆盖较广，优先复用 |
| 估值和预期 | PE/PB/PS、预测盈利、PEG、机构评级 | 价格隐含何种增长、与同业/历史如何比较 | 现有 pricevalue/report/report_metric；供应商预测口径需核对 |
| 股本、股东和分红 | 股东户数、机构持有、股本、股息、分红实施 | 所有权结构和现金回报如何变化 | 现有 shareholder/corporate_action；机构分类不一定逐项同口径 |
| 公司事件与风险 | 预告、订单、重组、增发、解禁、质押、监管 | 新事实如何影响经营和风险 | 现有事件/公告/报表数据；DSA 提供分析方法参考 |
| 新闻与关注热度 | 公告、新闻、资讯、平台热度、主题关联 | 市场在关注什么，证据是否支持 | 现有 SearchGateway/hot_event；平台热度不能当全市场情绪 |
| 组合和研究评价 | 持仓、权重、成本、回撤、信号后验表现 | 个人组合风险与研究方法表现如何 | 用户数据在私有 scope；现有回测与评测承接 |

从 InStock 的 206 个选股器字段看，本次按用途分组：技术标签/统计 63；财务与质量 34；股本/持有人 27；公司事件/风险 19；估值 14；交易资金 11；平台热度 10；行情 10；证券/成分关系 10；身份时间 4；分红 3；机构观点 1。分组用于说明覆盖，**供应商输出不等于仓库实现了该字段公式**。

DSA 的 15 个方法中，9 个偏技术趋势/形态，3 个偏主题、情绪与市场结构，3 个偏成长质量、事件与预期重估。它整体仍有较强交易视角；公司深度研究继续以我们现有 Skill 和财务、研报证据为主。

| 性质 | 例子 | 系统应如何对待 |
|---|---|---|
| 外部事实 | 成交价、成交量、公告、财报数值 | 从权威数据入口获取，保留来源、单位、日期和修订 |

## 3. 每项用途如何进入现有数据体系

沿用现有subject/dataview目录及`query/window/aggregate/compute`四类operation；成分关系继续由现有constitution能力承接，不建立平行的“因子 Agent”或按业务关键词写路由分支。

建议每个可用指标有一份简洁的说明，**名称和字段属于可寻址事实；用途、解释和局限保持自然语言**。优先利用现有 desc、aliases、方法 rules/examples；只有执行必需的信息才进入机器参数。

示例：

> **ATR14 / 收盘价**：衡量相对于股价的波动幅度，适合跨价格水平比较、波动收缩筛选和情景风险尺度。输入为口径一致的高低收与前收，使用明确版本的ATR14算法。单位为比例或百分比，目录中只能有一种明确约定。日线结果可读盘后快照，用户研究盘中变化时可按最新报价计算临时值。高低不直接代表预期收益，不能用涨跌幅绝对值均值冒充ATR。

实现和目录通过正式函数/工具修订关联。数据输入版本、参数和完成时点由系统记录，模型不重新抄写完整元数据。一个指标有多个用途，避免为每种用途造一份重复公式。

### 自然语言驱动的具体路径

用户：“在我的股票里找波动逐渐收窄、今天成交开始活跃的公司。”

1. 现有 stock-screening/technical-structure-analysis 理解范围和目的，按问题选择 ATR/价格、布林带宽或其他合适指标；不以关键词表强制指定唯一算法。
2. 模型读取对应目录的用途、精确调用和特殊口径，确定日期、窗口及用户需要的筛选定义。
3. 确定性的计算/查询入口读取已有共享结果；未覆盖参数只对缺口计算。**缓存选择和重复合并由程序完成，模型无需每次决定走哪张表。**
4. 返回候选和核心证据列，完整表格通过已有结果引用保存；模型不接收全市场所有指标矩阵。
5. Skill 解释为何命中、关键未知及后续观察点，Renderer 展示结果与来源。

当前工作区已实现`stock.technical`日线query/window/aggregate，以及独立的分钟与快照查询视图，见[接入说明](21_indicator_data_tool_integration.md)；这不代表生产服务已加载相同版本。compute保留当前dynamic_cal的探索用途。原始行情继续在stock.quote，财务继续在原视图。供应商标签只有在定义与可用性核验后才登记。

当前 `stock.quote.dynamic_cal` 每次会请求模型生成代码，再在宿主内执行 DataFrame 计算；它不是已经部署好的无模型固定公式服务。高频共享指标应调用正式固定实现；一次性探索保留现有动态计算用途，可反复复用的自定义逻辑经已有工具创建/修订流程保存。不能把所有盘后任务都变成每次重新写代码。

## 4. 实时、盘后、披露更新和按需的分工

**这里“实时”指按请求或分钟级快照获取最新可得结果；本轮没有设计逐笔流式或 Level-2 服务。日线技术分析不需要全市场每秒更新。**

补充核验：[stock_agent实际配置](09_minute_refresh_and_event_sources.md)为每10分钟一轮、每批1000只、12并发、批间40秒、统一截止时点。分钟粒度不等于每分钟送达；即时需求允许在统一限额内按需补取，持续监控对订阅并集刷新/计算。下表订阅1/5分钟仍是需验证容量的需求，不是当前可交付刷新承诺。龙虎榜采用网页主备与基本抽取检查；收费竞价暂停。最新实施边界见11。

| 能力 | 默认执行方式 | 原因与保存范围 |
|---|---|---|
| 日线标准MA/MACD/RSI/ATR/BOLL、常用量价窗口 | 盘后一次共享预计算；缺口按需 | 同一股票同一时点可跨用户复用；先选少量标准参数 |
| 实时价格、当日涨幅、实时成交额 | 读取供应商/既有快照，按源刷新 | 主要成本在取数、时点对齐和分发；不必重新扫历史 |
| 同分钟成交活跃度、盘中突破距离 | 订阅股票的1/5分钟或按需计算 | 必须与同时间段历史量比较；当日累计量与完整日均量不是同一个量比 |
| 财务、股东、预告、分红、解禁与质押 | 随披露更新入库 | 披露时间决定可用性，不应每天用模型重新生成 |
| PE/PB/市值等随价格变化的指标 | 复用可得分母，按报价/盘后更新 | 财报分母按披露变，价格分子按行情变；TTM与预测须分开 |
| 形态识别 | 选定形态盘后批算；临时历史研究按需 | 计算本身可很便宜，但61个全部展示不增加用户价值 |
| 筹码估计 | 先对订阅并集盘后共享；条件成熟可全市场日更 | 日更CPU未显示不可承受；默认不做每分钟全市场重算 |
| 全截面排名、分位数、行业中性化 | 同一时点/股票池批量计算 | 不可只缓存单股值就声称排名有效；依赖完整比较范围 |
| 自定义参数/窗口/复合规则 | 按需或用户已确认的定时任务 | 复用已有输入与相同参数结果，不预计算无限组合 |
| 深度基本面/事件研究报告 | 用户请求或订阅触发 | LLM与取证成本单独计量；个人上下文不进入公共缓存 |
| 信号后验与长历史回测 | 异步/盘后批量 | 有成熟窗口、历史股票池、成交和成本等独立要求 |

首期优先固定预热窗口、分块向量化重算。MA可以增量、EMA/ATR等也可递推，但递推初值、数据修订和复权变动会增加恢复成本；在固定窗口计算已足够便宜时，不先引入新的状态持久化。将来分钟负载证明需要时再做局部增量，并验证与同口径批量结果一致。

## 5. 本机计算基准：目前能支持什么

|---|---:|---:|---|
| 现有 Fin Agent MA/MACD/RSI 路径 | 0.431秒 | 23.081秒 | 实际原函数，输出逐行字典 |
| 实验常用指标内核：MA、MACD、RSI、ATR、BOLL、量能比、前高 | 0.011秒 | 0.776秒 | TA-Lib数组运算、取末值；未上线，未证明与原函数数值等价 |
| TA-Lib 全部61个K线形态 | 0.198秒 | 4.785秒 | 全部函数计算，保留方向输出；不证明交易有效性 |
| InStock整套DataFrame指标流程 | 12.087秒 | **约725秒，线性估算，未实跑6000次** | 全量内部列、递推和DataFrame写入；不能与实验小内核作同任务优化倍率比较 |
| InStock筹码估计：210日、150价位 | 1.473秒 | 88.056秒 | 每只计算一个末端分布，不是每只重算完整历史分布 |

判断：

- 少量常用指标的全市场盘后共享计算具有可行的CPU基础；当前没有证据表明需要GPU。
- 筹码全市场日更也可能可行，不能仅凭“筹码复杂”就判定必须按只收费；但88秒串行计算不支持每60秒全市场重算，何况还没计入数据和服务开销。
- 整包复制InStock计算路径会明显增加成本。应选定需要的公式、复用历史输入、分组计算；是否做更进一步优化须先锁定数值口径。
- 初次长历史回填、每只每天全历史滚动筹码、不同参数组合和全市场分钟留存，比“每日末值更新”重得多，不能用本表直接乘一个并发数宣称支持。
- 生产部署的CPU、供应商批量接口/限频、数据库吞吐、模型时延和计费都未实测，运行容量仍为 NOT_READY。下一阶段需要在目标环境绑定实际workload做端到端验证。

原始三次耗时、环境、源码哈希和进程峰值RSS见 [benchmark_results.json](../evidence/data_capability_inventory_20260928/benchmark_results.json)，可复跑脚本见 [benchmark_compute.py](../evidence/data_capability_inventory_20260928/benchmark_compute.py)。峰值RSS是整个探针进程的值，不是6000只真实行情在内存中的容量。

### 本地已有运行约束

- 行情查询默认硬行数上限为500,000；6000只×300根=1,800,000行，不能当成一个交互查询直接取回。建议按100–200只分块，且只读必要字段，首批用小并发验证。
- StrategyRunExecutor 默认并发4；它是策略执行约束，不是所有数据/分析工具已有统一资源队列的证据。
- PythonExecutionRuntime 默认单次10秒超时，旧因子包装另有5秒设置。原InStock流程100只约12秒不能直接塞进默认单次执行预算；正式固定批处理用分块作业承接，用户自定义执行仍遵循已有隔离和限额。
- 动态计算当前使用宿主exec，本轮不把它当成已具备CPU/内存隔离的共享计算服务。高频公共计算使用经过测试的固定代码；真正自定义代码继续走正式运行时。

建议首期验收预算而非现有承诺：已缓存结果查询p95≤1秒；200只标准指标增量计算段p95≤2秒；全市场标准日更取数到可查询≤15分钟。必须在目标环境实测后决定是否可交付；模型报告耗时另列，不能混入纯计算预算。

## 6. 用户提出的共享与收费模式

### 6.1 计算范围取决于结果能否复用

| 层次 | 内容 | 调度范围 | 可考虑的权益边界 |
|---|---|---|---|
| 公共标准数据与特征 | 合法可共享的行情事实、标准日线指标、公共板块统计 | 先验证，成本合适则全市场一次计算 | 基础查询；不是每用户重复付出一遍计算成本 |
| 订阅范围内的额外计算 | 高频刷新、较重估计、长历史、特殊参数 | 对所有订阅需求按“股票+参数+时点”去重后统一运行 | 股票覆盖数、刷新频率、历史深度、额外方法/参数能力 |
| 私有研究与策略 | 持仓成本、风险偏好、私有材料、自定义策略、个性化报告 | 用户scope中的独立任务；公开行情输入仍可复用 | 模型用量、研究深度、运行频率和任务额度 |

只讨论可计量维度，不在这轮确定价格。供应商费用、授权范围和数据分发权限可能比CPU更影响成本。

例如，100位用户关注集合合计有10,000次“股票订阅关系”，但仅涉及800只股票。对相同定义、参数和日期的筹码日更，可以只算这800只；每位用户仍只能查看自己有权限的数据与任务。不同参数形成不同计算键；用户持仓或私有材料一旦参与，不能作为公共结果共享。

公共共享条件至少是：同一证券身份、频率/有效时点、数据快照、复权口径、计算修订和参数。截面排名再加股票池版本。公共报表文本如需共享，还要在生成前确定它只使用公开/可共享输入并绑定方法/模型版本；不能事后从用户私有报告中按代码相同抽取出来共享。

跨用户重复计算应在后台按规范化计算请求合并；执行状态沿用现有任务/运行机制。用户任务持有共享结果引用，不复制一套计算服务。已有定时任务的至少一次执行语义仍要求结果写入幂等。

### 6.2 先记录成本，再确定收费策略

观测通道记录：取数耗时和调用量、计算CPU/墙钟时间、处理股票与bar数量、命中缓存/合并次数、结果字节量、模型token和调用耗时。用户只看到任务范围、更新频率与结果时点；不把内部计量字段要求模型写入研究正文。

缓存命中降低系统成本，但是否减少用户额度扣减属于产品定价规则，不能由底层缓存实现隐式决定。首期只建立可举证的用量，不实施收费或扣费。

## 7. 预计算结果如何保存

### 7.1 三种结果形态

1. **标准日线特征**：每股票×交易日一行的紧凑宽表/分区结果，先选20–40个有实际需求的数值列。由既有Provider读出；存储方式按目标数据服务确定，不为每个指标建一张表。
2. **参数化/较大结果**：自定义窗口、筹码分布、回测明细等复用已有文件/运行资产与结果引用；目录登记用途和读取入口。避免无限参数变成无限固定列。
3. **研究正文和证据**：沿用报告/会话/运行资产，保存本轮正文和既有引用；事实记录与模型解释分开。

标准特征行的逻辑定位：证券、交易日、频率、参数配置、计算修订和输入快照；行值为真正被查询/排序消费的数值。可用时间/完成时点及来源沿用数据元数据。这里是设计说明，尚未创建SQL表或新Schema。

### 7.2 更新和修订

- 盘后等数据源的完整bar可用后计算；市场交易日历决定运行范围，工作日cron不能替代交易日。
- 输入先形成有版本的计算范围；同一版本写入幂等。分块完成情况由现有任务证据说明，查询如遇未更新证券，显示对应实际日期，不把不同日结果冒充统一截面。
- 修正行情、复权或财报后，对受影响窗口重算；旧报告继续指向旧输入/旧结果证据，不静默改写当时结论。
- 盘中临时值与收盘完成值分开定位；陈旧结果、缺失和预热不足不能填零或标成已更新。
- 财报保留报告期、披露日期和修订；历史研究按当时可得信息，不能只按report_period回填最新修订。

### 7.3 存储量级

以6000只股票、40个float64数值列、252个交易日估算：**日线数值本体约0.484GB/年**。这不含键、索引、版本、空值、原始行情、JSON和副本。

若相同规模每分钟保存一份，按每日240个时点约 **116GB/年数值本体**，仍未包括上述开销。因此默认长期保留日频结果；分钟频按订阅需求与保留周期配置，不把日频便宜外推成所有频率都便宜。按交易所实际时段计算，多市场不能统一套240分钟。

## 8. Skill 数量与吸收方式

现有15个业务Skill：

- 市场与板块：market-overview、sector-theme-analysis、capital-flow-analysis。
- 个股研究：stock-research、equity-report-analysis、earnings-analysis、valuation-analysis、financial-quality-analysis、stock-comparison、technical-structure-analysis、dividend-analysis。
- 筛选与因子：stock-screening、factor-analysis。
- 基金与债券：fund-analysis、bond-analysis。

DSA的15个方法按以下方式归入，**首期新增顶层Skill建议为0个**：

| 方法 | 归入现有Skill | 本轮建议 |
|---|---|---|
| 放量突破、均线金叉、多头趋势、缩量回踩 | technical-structure-analysis；筛选调用stock-screening | 首批吸收方法，正式Tool计算数值；四种方法可组织为一份按需量价参考 |
| 成长质量 | financial-quality-analysis、earnings-analysis、stock-research | 与现有经营/财务方法对照补缺 |
| 预期重估、事件驱动 | stock-research、valuation-analysis、equity-report-analysis、sector-theme-analysis | 整理事实到经营/估值传导，复用现有催化与反证参考 |
| 热门主题、情绪周期、龙头识别 | sector-theme-analysis、market-overview、capital-flow-analysis | 等相应广度/资金/成分证据可用后按需引入 |
| 箱体震荡、底部放量、一阳三阴 | technical-structure-analysis | 方法参考保留，规则化前逐条定义 |
| 缠论、波浪 | technical-structure-analysis | 暂不默认加载或自动交易化；用户明确需要时再研究 |

InStock的10条布尔筛选是计算规则模板，不是10个Skill；61种形态也不是61个Skill。固定评分、统一止损、多Agent投票与一串新方向状态不进入系统底座。

Skill需要知道有哪些合适数据/方法，用户无需知道来源仓库。目录负责可发现和可执行；专业方法负责选择、组合与解释；报表和证据由系统保存。

### A. 先确定数据与公式口径

按上表27个数值输出和3条规则推进；[输入核验](08_base_data_readiness.md)已确认已有字段、样本与源库声明单位，后续验证除权样本、股票池历史覆盖、盘中/收盘语义和来源保障。已有字段优先复用；供应商字段不足以证明公式时保留待核验，不用同名替代。龙虎榜网页主备按用户确认单独实施，收费竞价暂停。首批11项计算与开发拆分见11。

验收：正常行情、缺失、预热不足、分红复权、盘中未完成bar和时间边界均有必要样本；同输入同修订可复现；原有MA/MACD/RSI不被静默改口径。

### B. 共同计算与盘后试运行

固定公式Tool → 100–200只分块 → 标准日线结果保存 → 原目录查询入口 → 现有Renderer。先100/200只，再扩到6000只的目标环境端到端测量；与在线问答并发验证。默认小并发，不按CPU逻辑核数盲目放大抓取并发。

验收：查询/计算/写入分段耗时、覆盖率、供应商限频、作业恢复、相同计算去重和输入修订重算；没有当前workload证据就不承诺全量SLA。

### C. Skill 与自然语言效果

吸收首批量价、成长质量、事件与预期方法，补固定样本验证自然语言选择数据、计算结果正确、关键判断有证据、没有统一乱打分。设计十余条跨技术/基本面/事件问题，包含追问修改窗口和已有资产读取。

### D. 订阅共享与持续复核

对用户任务的公共计算需求去重，私有研究保持owner边界；复用定时任务与报告历史。完成重复请求、数据修订、缓存过期、不同参数、私有上下文和失效恢复的协议/权限验证，再讨论收费与开放范围。
