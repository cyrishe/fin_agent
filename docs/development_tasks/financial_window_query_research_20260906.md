# 金融窗口查询：保留历史、精确选型、减少扫描

## 结论

优先采用“匹配访问方向的索引 + 基于现有 ApiCall 的静态 SQL 模板选型”，不要把近两个月变成默认数据边界。此优化属于共享数据 provider，CC/DSH 均可受益，不增加 LLM 调用。

## 必须先分清三种业务窗口

| 语义 | 精确执行方式 | 禁止的等价替换 |
|---|---|---|
| 最近 N 个市场交易日 | 日历解析出固定日期集合/边界，再筛选证券行情 | 停牌记录不足时，向更早日期凑足 N 条 |
| 每只证券最近 N 条有效记录 | 每证券按时间索引倒序取 N，可跨越两个月 | 统一日期下限或给多证券套一个全局 LIMIT |
| 用户指定起止日期 | 原范围内过滤、计算、排序 | 因结果少而自行扩大范围 |

当前 `execute_kd_quote_api` / `_kd_dates_cte` 已使用交易日历；`count` 的逐证券记录查询是另一路。不要把两者合并为“所有窗口只查两个月”。成交稀疏或长期停牌使两种定义产生实际不同结果。

还要保留过滤与 Top-N 的先后语义：“最近20条中上涨的记录”不等于“最近20条上涨记录”。优化只能改变访问路径，不能挪动会改变结果的过滤、聚合或限量步骤。

## 静态 SQL 优化建议

在现有解析后的 ApiCall / provider 中按确定的查询形态选模板，不再调用模型重写 SQL，也不采用通用正则替换 SQL。

1. **单证券最近 N 条**：证券与合法日期条件下推，沿 `(stk_code, trade_date)` 倒序取 N。外层按用户要求排序，保留 count 与全局 limit 的不同职责。
2. **明确多证券最近 N 条**：仅用请求中的证券集合驱动，每个证券有界取 N；可选 LATERAL 或小规模参数化 UNION ALL。不是对整个历史表排序后再过滤，也不应为两只股票枚举全市场。
3. **全市场最近 N 条**：可用证券键集合驱动 LATERAL，并保留每证券各自末次记录。最终按指标排序的范围约为“对象数 × N”；仍需实测与原窗口计划对比，不能断言 LATERAL 在所有数据量下最快。大 N/全历史应保留适用的集合运算计划。
4. **最近 N 个交易日统计**：先确定日历边界，利用日期优先索引读取相关截面，再计算；保留实际有记录天数，不静默补日期或金额。
5. **分钟级宽表**：先选有限的主键/时间键，再回表取展示字段，避免排序大量宽行。只有不改变过滤顺序时才能延后取字段。

已有本地未提交的日K/分钟 Top-N 改动正在沿该方向实现；本轮未覆盖或代为发布。看见 SQL 改动、索引存在，不代表其所有语义边界已验收。

MySQL 8.0.14 起支持相关的 LATERAL 派生表，已核验服务器版本可用。[官方说明](https://dev.mysql.com/doc/refman/8.0/en/lateral-derived-tables.html)

## 索引优先级

- 日K个股时间序列：`(stk_code, trade_date)`，已存在，避免重复建。
- 全市场指定日期：现有主键 `(trade_date, stk_code)`，保留。
- 分钟K按证券与周期查询：已存在 `(stk_code, kline_type, trade_date, bar_end_time)`；应先利用，不先堆新索引。
- 日历：按市场、交易日标识、序号的查询应核对相应索引和序号完整性。只存在字段不等于日历范围、连续性都正确。
- 研报/财务等其他表：按实际高频 WHERE/JOIN/ORDER 和执行计划评估，不从行情经验推断“其他表也都缺索引”，也不为每个返回字段建立索引。

联合索引的列序决定可用于检索的左侧前缀；一个证券时间序列索引不能替代所有日期截面索引。[官方联合索引说明](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html) 索引有序访问与 LIMIT 配合可提前停止，但 filesort 与全量排序仍可能消耗大量工作；并列排序需明确稳定的次级键。[官方 LIMIT 优化说明](https://dev.mysql.com/doc/refman/8.0/en/limit-optimization.html)

## 两个月热数据：可选加速层，不作为事实删减

目前有正确代码优先索引时，取少量历史记录不必先增加冷热分层。

以后若规模或存储成本确实需要，可把近期窗口当作工具内部的首轮读取范围。仅对“最近 N 条记录”语义，逐证券检查是否已取得足够的匹配记录；不足的证券再向历史扩展，直至满足或确认历史确已耗尽。用户指定日期不能扩大，查询错误/超时不能伪装成历史耗尽。应在同一数据快照下保证分页边界和去重，而不是让模型循环扩大条件。

即使分区，优化收益仍依赖可裁剪的日期条件；没有日期下界的逐证券历史查询不能假设自动只访问近两月分区。[官方分区裁剪说明](https://dev.mysql.com/doc/refman/8.0/en/partitioning-pruning.html)
