# MCP 仅数据模式修复与上下文验证

## 用户确认的边界

- 不传 `conversation_id`：每次独立，不继承上一问题、结果或目录上下文。
- 同一用户显式传相同 `conversation_id`：保留多轮续接能力。
- 不同用户即使传相同 ID，也保持隔离。
- Chat 多轮能力不改。此次修改不更新生产服务，不覆盖 `finance-query-20260906` 基线标签。
- MCP 查数始终需要 access key。评测为每个隔离服务生成仅存内存的随机 key，通过 `X-API-Key` 调用；正式服务认证不改。评测启动时实际验证无 key / 错误 key 返回401、正确 key 可列出工具，否则不启动查数。协议测试另确认未认证调用不会进入 gateway。

## 根因与修复职责

旧 RTE016 实际发生两类浪费，不是同一种现象：

1. **重复请求/重叠查数**：第一笔取得7篇研报后，阶段控制仍要求继续查询。第5步完全相同的请求被去重拦截，未执行数据库；第7、9步更换输出列或范围，又实际读取了重叠数据。
2. **内部生成回答**：第4、6、8、10步生成回答，MCP最终隐藏summary。因此返回没有summary，不等于没有生成回答的成本。

根因是 data-only 完成声明可缺省、成功结果仍强制留在 query，以及“尚未取得数据”的错误阶段提示共同作用。并非数据库慢，也不是历史问题上下文串入造成此次重复。

改动属于场景 HARD 执行契约及其 SOFT 适配，不更改 DSH 框架源码，不新增枚举阶段：

- 使用 DSH 原生、agent-scoped 的 `system-prompt/assemble`，仅在当前 data-only 请求中把已有 `data_request_complete` 加入模型可见 required 字段。全局 MCP tool schema 不被改写，预热 worker 与 Chat 切换不会缓存错误模式。实际请求头已核验该 required 字段生效。
- 完成所有取数目标后，沿用 `agent/pre-step` 停止模型调用，不进入最终回答轮。多个并行 flow 必须都完成才结束。
- 真正有后续依赖时允许读取已有结果、选择下一目录并补查；成功取数不再触发“未查询”的强制重试。查询与读取沿用已有次数限制。
- 去掉 data-only 请求中无关的回答深度要求。数据来源文字本身是可返回数据，不要求为了撰写答案而阅读全文。
- 工具 tracker 记录成功 flow 的完成事实。失败/不完整执行不能仅凭存在结果行就报全部完成；保留已有结果并明确未完成。
- DSH `isolated_request=true` 时强制生成新 session/result scope，即使内部调用复用 thread_id 也不会误续接。显式会话仍沿用原稳定 key，API 网关的可选 conversation_id 语义保持不变。

## 默认独立与显式续接的原生会话证据

原生 session JSONL 与运行记录交叉核对：

- 6题独立请求：6个不同session，turn_numbers均为[1]，resumed均false，isolated_request均true。三个worker均复用客户端，但会话没有复用。

- 两轮在同一session中，turn_numbers=[1,2]，resumed=[false,true]，isolated_request=[false,false]。实际第二笔API仍为鹏鼎控股、np_parent、forecast，只将forecast_year从2026改为2027。各返回17行，第二轮只需1次模型调用。
- 全部8次请求：data_only_complete=true，模型可见schema都要求完成声明，未发现不含工具调用的纯回答消息。

这里核验的“没有回答生成轮”是原生assistant/message内容，而非仅检查API的summary=null。
