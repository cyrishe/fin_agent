## 涨跌停和时间

原接口封装请求 `eHqData=1`，只包含基础行情；扩展字段虽然存在，却返回默认零值。实测 `eHqData=3` 同时取得基础和扩展行情，包括：

- 当前行情：`stSimHq`。
- 当日涨跌停价格：`stExHq.fZTPrice / fDTPrice`。
- 行情日期和时间：`iTradeDate / iTradeTime`。

数据层按接口给出的价格精度比较现价和涨跌停价，映射至原有 `is_limit_price`：0 非涨跌停、1 涨停、2 跌停，无法确定则为空。不采用代码前缀推测比例，也不使用次日预测涨跌停价。则成电子返回的涨停价为 23.590001，按两位精度为 23.59；N天博、C格林、N杰锋均返回两个限制价格为 0，按无涨跌幅限制处理。

`snapshot_time` 使用每只证券自己的行情源时间，不以请求时间冒充行情时间。接口没有的 K线完成状态、区间成交等字段保持空值，不伪造分钟K信息。目录只描述业务含义，不要求 LLM 知道 Upchina、请求掩码或存储路径。

## `.query` 为什么出现

原题 RTEF112：机构对新宙邦的未来增长预期是否一致？

1. 模型读取 `stock.report_metric` 的 aggregate 目录。
2. 随后决定取机构预测明细，却生成 `stock.report_metric.query(...)`，并遗漏 `->`。
3. 第一层解析只报告遗漏输出字段；唯一修正机会被用于补 `->`，错误 API 路径保留。
4. 静态校验再拒绝不存在的 API，最终回答错误声称该视图没有明细接口。

全部 47 个目录方法模式均未注册 `.query`。这是模型生成了不存在的名称，不是系统改写。但不能简单归咎于随机幻觉：operation 切片会移除其他操作的函数，模型看不到真实的 `stock.report_metric(...)`，于是把当前切片误当成整个视图的能力。选择 aggregate 本身并非必然错误，问题是之后转向明细时没有获得对应契约。

本次最小调整：操作详情仍只展开选中操作，但附带简短的真实入口导航，例如：

```json
{"query": "stock.report_metric", "aggregate": "stock.report_metric.agg"}
```

导航从原目录自动生成，不维护第二套方法；提示词只澄清 operation 是分类、api_name 是调用路径。没有增加 case 关键词、业务 validator、重试次数或后缀纠错。
