# DSH 主运行器：能力覆盖与退出 CC 的判断

日期：2026-09-08。范围：当前本地工作区、实际装载的 DSH SDK、历史评测证据。只做分析与离线诊断，未改生产代码、配置、服务器或数据库，未新增模型调用。

## 1. 决策：DSH 是主线，CC 是基准，不是兼容目标

**停止为了 CC 同步优化提示词、循环、恢复和性能。金融数据查询优先围绕 DSH 自身的正确性、效率与可运维性优化。**

上一份兼容报告提出的“统一两端取数收尾”不应成为必做项目。应修正为：DSH 内部的目标、执行、结果与结束契约一致；CC 保留固定版本的评测参考即可。若自然的薄适配还能运行，可以保留；若需要平行提示词、额外状态或专门分支，就不继续维护。

现在可以确定这个技术方向，但**还不能宣布当前版本已经满足无条件独立生产运行，更不能直接卸载整个项目的 Claude SDK**。本轮已发现确定的运行与结果引用缺陷，见第4节；保留 CC 并不能消除共享执行层缺陷。

判断目标也不是复制 CC 的调用路径。应比较：是否取得问题所需的数据、标的/时间/单位是否正确、覆盖是否完整、空结果是否如实交付、时间和成本是否可接受。明细代替聚合可以成立；错误的 CC 基准不值得追平。

## 2. 功能覆盖：查询能力与整个产品分开判断

| 业务能力 | DSH 当前情况 | 是否值得为此保留 CC |
|---|---|---|
| 股票、指数、行业、板块、基金、债券、研报等标准取数 | 同一7 subject、31 dataview、47入口，已有真实跨域样本 | 不需要；金融 API/MCP 已默认 DSH |
| query/window/constitution/aggregate | 共用真实数据执行器，目录与协议已验证；存在模型选择和目标完成方面的个别问题 | 不需要复制 CC；修 DSH 和共用执行层 |
| compute 自定义行情计算 | 入口和分发具备；实际代码执行边界尚不充分 | 不是 CC 功能差距；是对外开放该能力的安全与资源边界问题 |
| 返回 data、summary、both、detail及用量 | 均有实现及历史实测 | 不需要 CC；当前版本应补齐 summary 与完整性回归 |
| 短多轮、结果引用、跨视图补读、静态失败修复 | 有实现、离线测试和部分真实成功记录 | 不需要 CC；不能外推成长会话/重启恢复均已验证 |
| 普通金融问答中的业务 Skill、渐进参考、配置补充工具、固定组合回测 | DSH 金融 QA 当前只开放3个数据工具，尚未接入这些能力 | 这是完整问答产品的范围缺口；先决定是否属于 DSH 查询服务职责，不能自动照搬 CC |
| 自定义工具需求、Design、Flow、Direct | 当前已有独立 DSH Opt 主控 | 已非 CC 主线，不需要再为金融 QA 迁移一次 |
| 工具 Coding/修改/测试 | DSH 编排后由 host 交给 Codex 实现 | Codex 与 CC 是两回事，移除 CC 不等于移除 Codex |
| 独立回测、旧 SkillRunner、顶层语义路由与展示 | 自有服务或普通模型 API | 不是 CC 专属能力，不应列成 DSH 待补功能 |

位置：金融 API 默认见 `src/finance_api/service.py:41`；DSH 金融工具范围见 `src/scenarios/financial_qa/dsh_mcp_server.py:18`；CC 额外工具见 `tools.py:1633`；工具开发 DSH 默认见 `src/web/flask_app.py:139`，host 启动 Coding 见 `src/services/custom_tool_service.py:2307`。

**默认值需要准确区分：**Web 代码缺省仍是 CC（`flask_app.py:394`），本地 `.env` 未覆盖；服务器部署模板则指定 `FINANCE_CHAT_DEFAULT_RUNTIME=dsh`。本轮未读取服务器进程环境，不能据此断言线上对话仍在使用 CC。`main_framework.md` 的8月19日地图也早于部分 DSH 改动，不能代替当前代码。

## 4. 真实问题：优先修这些，不为 CC 增加复杂度

### 4.1 整轮超时没有覆盖完整等待期——必须修

`dsh_service.py:1166` 同步调用 `worker.harness.run()`。配置的 `FINANCE_DSH_TURN_TIMEOUT_SECONDS` 被传给 SDK 的 `request_timeout_seconds`，但本机 SDK 在 `session/prompt` 获得回执后，继续通过 `subscription.next()` 等待 idle；这个通知队列读取没有 timeout，Fin Agent 外层也没有整轮截止机制。

已做安全离线探针：实际 SDK `Session.run` / `NotificationSubscription`，模拟客户端及通知，request timeout=50ms；150ms后仍未退出，显式投递 idle 后正常回收线程。无模型、外部进程或网络调用。

后果：缺失终止通知时可能一直占住 worker；`close()` 还要等该 worker 的锁。需要真实整轮截止、取消/回收及下一请求可用的保证，不是再调大/调小现有配置值。

异常返回还存在证据损失：模拟在一次成功查询后抛出 transport timeout，磁盘 trace 已有调用和结果引用，宿主返回的 `tool_calls/result_refs` 却都清空。数据未从磁盘删除，但本次交付和故障分析丢失已有证据，应与超时收尾一起修正（`dsh_service.py:1288`）。

依据：当前 SDK `cd5ef8148158c3a752a658978873241fdf8e2bbc`，`python/sdk/src/deepseek_harness/api.py:170`、`client.py:563`；宿主 `src/scenarios/financial_qa/dsh_service.py:724`、`:1166`、`:1393`。这是当前SDK实现边界，不是对所有未来DSH版本的断言。

### 4.2 同会话并行查询可能重名 r1——必须修

现有不同会话隔离测试不覆盖同会话内并行工具调用。离线使用真实 DSH Bridge 并行提交两个 finance_query，仅替换最终 provider：两个查询均成功、都返回 `r1`；磁盘保存两份结果，但 working_set 只剩一个 `r1`。

根因：`tools.py:845` 先读取 `next_result_name`，之后 `:907` await 执行，直至 `:1123` 才登记结果；另一条并行调用可在间隙取得同一个名字。完整结果没有因此从磁盘消失，但后续 `r1.column` 无法唯一表示两个结果，可能引用到错误对象。

这是系统应保证的身份与引用问题。应在同会话的执行/登记边界实现最小串行或原子性，不让模型避免并行，不增加业务语义校验，也不影响不同会话并发。

### 4.3 data-only 误声明完成——必须针对真实目标闭合验证

当前 RTEF012 中，DSH 已读到完整 report 目录，但只执行 basic_info 就填 `data_request_complete=true`，因此没有查询目标价。自然语言计划尚有后续目标，机器完成信号却提前结束。

需要优化的是现有取数循环的完成信号与依赖衔接，验证该目标能通过原有 flow 或后续 flow 完成。不能恢复“basic_info永远不算完成”的黑名单，也不能新增一套运行时业务语义 validator。目录/字段存在不足以证明任务完成；query阶段推理预算是否影响误填，需要小范围对照才能判断，当前没有因果证据。

同一批样本的“读window、执行明细、下一问才补读query”属于目录准入标准前后不一致，主要增加绕路；应按DSH自身的按需加载原则收拢，不必同步设计CC guard。

另用模拟 Harness/trace 验证了宿主合并边界：同一组“目标A失败、无关目标B成功”按不同顺序交付，错误状态不同，因为 `dsh_service.py:1218` 仅检查最后一次查询。这是宿主级诊断，不是已观察到的真实模型全链路事件；Node标准循环本身有并行失败后修复控制。后续测试须保留这层区分，既验证失败不会被无关成功掩盖，也验证真正修复成功可以消除旧错误，不能简单把“历史有失败”永久判为失败。

### 4.4 compute 尚不是受限的代码执行环境——对外全量开放前必须解决

`stock.quote.dynamic_cal` 会让内部模型生成代码，在 MCP 进程内以 `exec` 运行 `compute(df)`。只有 AST 禁止部分调用，仍暴露完整 pandas / numpy；没有独立的文件、网络、CPU/内存权限限制。

本轮只运行AST校验，没有执行生成代码：包含 `pd.read_csv` 的函数和无界循环都被接受。这证明当前校验不等于沙箱；不是声称已经利用漏洞读取了文件。`asyncio.to_thread` 和 MCP 子进程也不等于受限执行环境。

依据：`src/experiments/staged_data_protocol/phase2/dynamic_cal_provider.py:411`、`:426`。这是共享数据工具风险，CC也有，不是DSH引入。

若本版要对外提供compute，需使用真实受限执行边界并验证可终止性；若暂时不开放，应明确版本能力范围。这需要产品范围选择，本轮没有擅自关闭接口或扩建沙箱。

### 已有基础，不必重复造轮子

DSH已有会话/owner作用域、worker隔离和复用、队列等待上限、catalog版本核对、静态检查、成功结果保留、有限修复与独立detail通道。保留这些稳定能力，在已有边界修上面的根因。

本轮已有DSH runtime、API Gateway/API app、结果存储相关测试 **58项通过**；上面的新探针仍能复现缺口，说明原测试覆盖的是部分正常及异常路径，不能仅用通过数量判定独立运行已就绪。

最小复现脚本：[verify_dsh_independent_readiness.py](../../scripts/verify_dsh_independent_readiness.py)，[观察结果及适用边界](evidence/dsh_independent_readiness_20260908/README.md)。仅使用本地临时数据、实际SDK等待类及模拟provider/Harness，线程显式回收，不启动模型或外部服务：

```sh
.venv/bin/python scripts/verify_dsh_independent_readiness.py
```

脚本打印观察结果，不以缺陷仍存在作为非零退出码。它是根因诊断入口，不是已经通过的发布门。

长会话压缩、用户纠正后恢复目标、跨进程恢复、真实并发长稳及取消后的清理，仍缺当前固定版本充分证据。应补测试，不预先为每一种假设故障增加状态机。

## 5. 最小验证与退出顺序

1. **先关闭确定性根因。** 整轮超时/回收、并行结果引用；明确compute开放范围并处理其执行边界；完成标记问题用原题和其他依赖查询验证。
2. **只跑 DSH 的跨域目标完成度回归。** 复用既有原题 RTEF012/112/070、BUS026/068/085/200/157/116/177/012/053：覆盖研报数值与文字、年报、窗口＋当前截面、全体排名/计数、今日板块、关系引用、基金、分钟量和合理空结果。不要求调用与CC一模一样。
3. **补交付与连续性。** 上述12题先data-only，其中4题再测both；复用3个已有多轮场景（6个用户轮次），再有针对性验证用户纠正、切题返回和重启恢复。低并发与故障恢复使用同组问题，不另造一堆金融题。
4. **按业务完成度判断放行。** 原问题所需数据/期间/集合覆盖、summary证据一致性、错误保真和用量时间分别记录；安全与引用错误不能被平均准确率抵消。模型效果不要求100%，但不能把可重复漏查、悄悄换日期或伪成功当正常空数据接受。
5. **验收后退出生产CC。** 金融查询无需继续双跑或自动回退CC；保留旧版本及原始基准供离线比较。完整金融问答中的Skill/回测等入口，按产品实际需要独立决定迁移、保留其他服务或取消，而非默认复制。

这是测试/发布清单，不是新增运行协议或状态体系。本轮没有执行这些新模型回归或生产迁移。

## 6. 去掉 CC 不等于重做框架

必须长期稳定的是金融目录、调用协议、结果资产、权限和对外API——它们服务所有调用方，不是为CC保留的包袱。可以放弃的是CC专用prompt组装、生命周期适配、shadow与兼容分支。

目前两个DSH工具构建仍导入 `claude_agent_sdk.tool`（`financial_qa/tools.py:574`、`finance_cc_system_tools.py:122`），因此不能直接卸载SDK。以后把工具的名称、说明、schema、handler改由中立定义持有、DSH直接注册即可；如保留CC基准，仅在基准适配处转换。这个依赖可以局部拆除，不需要建设多运行器兼容框架。

**最终建议：确定DSH主线、停止CC兼容性投入；先修并验证DSH独立运行所必需的少量根因，再退出CC生产路径。** 无法证明“永远没有未知问题”，但可以明确已支持范围、排除已知关键缺陷、补齐真实主线证据，并保留可观察、可停止和可恢复的运行边界。
