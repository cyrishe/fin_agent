# DSH Harness 现状与五维优化分析

日期：2026-09-09。范围：Fin Agent 金融查询接入与本地 DeepSeek Harness；分析和方案，不实施运行时代码修改。

后续证据：2026-09-10 已完成 [最新8条线上请求全过程复核](dsh_production_case_review_20260910.md)。该报告证实了完成hook重复生成、历史结果索引膨胀，并新增观点列覆盖缺失、组合证券称呼误识别、显式Skill重复加载等发现；后续优先级以该报告结合本文稳定性分析为准。本文保留9月9日的原始分析基点。

## 1. 判断

当前接入方向正确：最小运行配置、渐进式目录、原始结果外置、模型结果投影、原生生命周期 hook、复用 worker。继续优化的主要价值来自**消除不必要的模型往返、让已取得证据更容易精确消费，以及把超时和失败真正收敛到可恢复状态**。

不建议继续普遍压低推理或回答 token，不建议默认启用通用压缩、多 Agent 或模型生成程序替代现有金融执行协议。历史实验已经说明，上下文变短不必然更快，执行路径正确也不保证回答正确。

本次优先级判断：

1. **先修运行边界与证据盲区**：SDK 整轮等待缺少 deadline、API 入场等待无显式期限、异常记录丢失已完成步骤和 usage。
2. **主线效率与效果一起优化**：结果子集复用、查询范围明确、长文本可寻址读取。
3. **再做小范围 SOFT 实验**：减少重复阶段引导、改善统计口径与取证解释；保持现有修复机会。
4. **按测量决定后续投入**：目录精确复用、结果物化缓存、worker/session 回收；工具并行和通用 compaction 暂不优先。

## 3. DSH 特性与当前使用情况

| DSH 特性 | 当前接入 | 优化含义与边界 |
|---|---|---|
| Everything-is-a-plugin / Cordis effect 生命周期 | 金融控制在 `dsh_loop_policy.mjs`，由 patch 挂载 | 保持框架业务中立；生命周期问题应在正确的 SDK/宿主边界修复，金融判断留在本项目 |
| `sdk-minimal` 可组合运行配置 | 禁用 bash、pwsh、editor 工具，挂载金融 stdio MCP | 已避免通用 coding 工具上下文；底层基础插件仍有存在价值，不因“minimal”继续盲删依赖 |
| `agent/pre-step` | 注入阶段引导，data-only/明确空结果终止 | 可以省掉确定无贡献的模型步骤；不能把“样例已显示”当任务完成 |
| `agent/request` | 根据阶段调整 reasoning/maxTokens | 用于资源配置，不承载未记录的业务上下文改写 |
| `tools/post-execute` | 小表完整保留，大表/长字符串有界投影 | 比通用截断更适合金融；必须保证可恢复读取和完整性标记准确 |
| `tools.guard` | 执行包授权、工具额度、重复调用限制 | 拒绝非法执行有效，但完全相同参数不等于重复成功，需区分失败修复 |
| `agent/turn-stopping` | 成功前缀、失败后缀、显式未完成事实引导 | 已比固定轮数或页数结束合理；不能识别模型从未表达过的遗漏条件 |
| 原生 terminal result / `concludeTurn()` | fast data-only 使用 | 适合确定的机器结果交付，不宜推广到尚需解释的分析问题 |
| Session 日志驱动模型历史 | 模型可见投影、阶段输入走可回放事件；原始金融数据在 result_ref | 后续去重/压缩必须有可重建日志，不能只修改发给模型的临时数组 |
| 工具并发安全分类 | 原生支持；当前 MCP bridge 未注册 `isConcurrencySafe` | 当前这些工具按 exclusive 调度；同一轮产出多个调用可减少 LLM 往返，但不等于工具并行 |
| Compaction / tool-result-pruner | 当前读取到的 minimal 组合未挂载这些插件 | 原生存在不代表当前启用，也不代表适合金融合同与长文本证据 |
| Session/worker 持久与复用 | 默认 10 worker、预热、会话亲和、独立请求随机 session | 已减少冷启动；后续要测容量、热点排队、回收和重启恢复，不把进程复用误当会话复用 |

结构保持：用户语义 → DSH 渐进加载金融方法/目录 → `finance_query.steps` 执行 → 保存 `result_ref` → 程序筛选/明细读取 → SOFT 解释与 Surface 展示。DSH 原生层提供运行机制，Fin Agent 提供金融协议与权限，Skill 提供业务方法。

## 4. 五维现状

### 4.1 效率：模型往返是已知主要优化点，排队是尚未充分测量的尾延迟来源

**已有收益。** 小表可在字符预算内一次带齐；空结果在严格完成条件下省去最终生成；执行流允许多个依赖步骤一次执行。历史确定性空结果回放从 3 次模型调用降为 2 次，结果与前两轮输入一致；这项收益具有清晰归因。

**仍有浪费。** 沪深300历史 v3 为 12 次 LLM、约93.5秒，模型阶段合计约82.4秒，工具跨度合计约5.8秒。后两者口径存在重叠，不能机械相加或直接算精确占比，但足以支持优先减少模型往返。已观察到先默认100后显式全量重查、选出前10后仍读两个前50、再按代码取指标。

**当前并行边界。** DSH `executionMode()` 仅在 `isConcurrencySafe()` 返回 true 时并行。本地 MCP `createDefinition()` 没有该字段，Fin Agent MCP list 也未声明相关能力。不能把提示中的“可并行”视为实际调度证据，更不能只调 `maxParallelToolCalls`。

**宿主等待。** API semaphore 排队与 DSH worker 排队是两层。worker 有 queue timeout，API semaphore 没有显式入场期限；续聊亲和可能在其原 worker 忙碌时等待，即使其他 worker 空闲。后者是保存进程内会话的设计取舍，未经恢复验证不直接取消亲和。

### 4.2 消耗：已控制原始表入模，下一步看累计输入、重复引导和失败消耗

当前保存完整结果、只把有限样例送给模型，并通过稳定工具 schema/追加阶段消息尽量保留请求前缀。保留这条路线。

沪深300 v3 原始记录实际包含：未缓存输入37,077、缓存输入175,104、输出6,867；累计输入212,181，输入与输出合计219,048。旧 `total_tokens=43,944` 不含缓存读取。reasoning 2,737 已包含在输出中，不重复计费或累加。

**最新工作区变化值得单独评测。** 尚未提交的 loop 改动把注入去重键从 `stage:reason` 改成包含剩余预算，并在每次工具预算变化后追加完整阶段说明。它可能改善预算意识，也会增加重复上下文和提前收尾倾向。交接中“不提示剩余轮数”的旧描述已不能概括当前工作区。不要未经对照就认定这段改动提高效率或回滚它。

设新增一次引导为 s token，后面还有 k 次请求，累计输入额外贡献大致为 s×k；缓存命中会改变费用，但不会让这些输入从计量和上下文占用中消失。应比较完整提示、简短变化提示、仅关键边界提示三个方案，不重新设计状态机。

当前异常分支将 `llm_usage`、步骤和工具列表清空；如请求在若干模型/工具步骤后异常，本轮记录无法反映已发生消耗。失败成本必须先可见，才能正确比较优化。

### 4.3 稳定性：隔离较完善，整轮超时和资源回收存在明确待补边界

现有隔离包括 owner+thread 派生会话键、独立请求随机 key、进程实例独立 worker 文件、worker 锁、trace revision、Catalog revision 重建。这些应保留。

**已确认：RPC timeout 不是完整 turn deadline。** `dsh_service.py` 将 `turn_timeout_seconds` 传给 SDK 的 `request_timeout_seconds`。本地 SDK `Session.run()` 先提交 `session_prompt`，随后循环 `subscription.next()` 等 idle；`next()` 使用无 timeout 的 `Queue.get()`。RPC 超时只约束 RPC 等待，不能终止已经得到提交回执后的通知等待。minimal provider 默认 stream idle timeout 为172,800,000ms，远长于业务轮次配置；实际部署可覆盖，需核对生效组合。

本轮无网络 fixture 使用真实本地 `Session.run` 与 `NotificationSubscription.next`，模拟成功提交回执，然后不再发通知。RPC timeout 设0.05秒，0.25秒后线程仍在等待；注入异常后正常清理。它证明本地 SDK 的这个等待没有使用 RPC deadline，不等于线上已经发生过长时间挂死。

其他已确认代码事实：`prewarm(timeout=...)` 返回该值但未用它约束 executor 等待；worker 获租、Catalog 重建和 harness 创建部分在 run 的异常记录 try 块之外；API semaphore 没有自身期限。需合并成清晰的一条请求时间预算，而非继续叠加几个互不相干的 timeout。

**待测容量。** `_session_workers`、`seen_sessions` 没有在宿主中体现回收；原生 session store 与持久日志生命周期还需结合实际 runtime 测试。不能仅凭这些集合断言已发生内存泄漏，更不能宣称串上下文。应测固定worker下大量独立请求及长续聊的 RSS、session数量、磁盘增长和释放效果。

### 4.4 健壮性：完成控制已有改善，失败与重试之间仍有不协调

已取消“整轮第二次查询错误就结束”；成功前缀和失败后缀可保留，空结果提前返回有严格匹配，错误不再简单伪装成零行。

**已确认：重复 guard 不看前次结果。** `seenCalls` 在执行前登记，默认同样工具名+规范化参数只允许一次；前次失败后没有对应解除。因此在可恢复基础设施失败后，模型重发正确参数也会被挡。底层已有自动重试可能降低发生频率，仍须先核对其分类与总次数。不能为此允许无限重试，也不鼓励模型为了绕 guard 改金融条件。

**失败证据缺口。** run 抛异常时关闭worker可促使故障隔离，但记录丢失已收到的事件/结果引用。无进度订阅时 callback 直接返回，SDK 正常返回才能得到 `result.events`；异常中途无法通过该正常路径提取证据。应将轻量审计收集和 UI 渲染拆开，让无UI请求仍保留已经收到的执行事实。

**取消传播。** DSH 工具调用可传递 signal；Fin Agent `run_turn()` 未暴露取消参数，公开 API 通过同步线程执行。用户取消、断连、宿主deadline、Node工具取消、Python执行及DB中止之间尚无本轮端到端证据。HTTP连接结束不代表工作停止；仅让线程 Future 超时也不会停止工作。

### 4.5 效果：最大的剩余问题是证据的可消费性及解释口径

历史例子说明两类独立问题：执行得到正确前10，回答仍把229只PE/ROE交集写成229只同时上涨，实际再加上涨为112；还有金额换算错误、未查询成交量却写“放量”、未取证的行业因果归因。这些不是靠增加查询次数即可解决。

**子集语义不稳定。** 当前 `load_finance_result(filter, order, limit)` 返回视图，但 `result_ref` 仍指原始结果。模型看到的前10没有可复用的独立集合名，容易重读或手写代码列表。需要 HARD 保存的是程序已经选出的集合身份及来源，不是把业务分析说明拆成 JSON 树。

**长文本存在读取死角。** 大单元格投影只保留前缀；重新读取同一行仍经过相同投影。行 offset 不能读取该字段的后半段。工具级 `limit` 最大50适合表格行，底层document分支却按字符解释，另有潜在的极小文本页问题。当前入口的实际频率待测，但契约限制明确。原文保存在 result_ref 并不自动意味着模型能读到所需原文。

**预算不能代替能力。** Skill实际加载后为16/12/8的工具上限和8192输出上限；工具12次不等于LLM12次。普通模式工具上限仍为6/3/2。继续无差别降reasoning可能减少修复能力，继续无差别提高上限可能只放大重复读取。应先改善信息供给，再评估最终生成的low/off对照。

## 5. 建议方案与落点

### P0-A：建立真实的请求截止时间和取消闭环

职责：HARD 生命周期；不新增业务状态枚举。

做法：入口记录单一 deadline，API入场、worker排队、启动、SDK提交与完成等待共享剩余时间；保留工具自身局部超时，但不允许它超过剩余总预算。SDK的通知等待支持剩余时间和取消，优先在原生SDK通用层补齐；Fin Agent宿主只负责业务期限和调用。

到期后使用当前SDK/协议实际支持的取消接口，等待可配置且有界的清理；若无法收敛，关闭并淘汰该worker，确认旧运行不会继续写入下一轮context/trace后才释放。不要只包装 `future.result(timeout=...)` 留下后台工作。启动失败也统一进入同一请求记录。

验收：已ack但永不idle、模型无chunk、慢MCP、队列满、取消撞上工具成功、随后新请求能运行；有界结束、正确退出原因、旧trace不覆盖新轮、续聊按已持久事实恢复。部署实际SDK和Node构建先精确绑定。

### P0-B：保留失败请求的已知事实与计量

职责：HARD可观测性，走独立通道。

做法：轻量记录真实step/assistant usage/tool事件，不依赖是否渲染进度；异常时在关闭前读取revision匹配trace，合并已收到的计量与成功引用。没有服务端usage的中断请求标记“未知/不完整”，不写成零次、零消耗。优先复用现有record字段和结束原因；确需新增完整性元数据时保持可选、兼容。

验收：2次模型调用后第3次断流；前两次计量和成功工具仍可查，未完成调用成本不伪造，错误保持错误。统计区分核心/外层，旧历史未知继续未知。

### P1-A：为已保存结果的选择提供可复用引用

职责：HARD结果寻址；这是有真实跨调用消费需求的协议扩展。

做法：先做最小原型，在现有结果存储中可选保存 `filter + order + offset + limit` 所选出的精确集合，用现有result_ref/rN引用体系交给后续步骤。原结果不变，旧调用仍可只读视图。明确“全部匹配行”与“排序分页后的前N行”不是同一集合。

优先保存被请求复用的结果，而非每次预览自动制造新资产；来源保留原引用、选择表达式和顺序。业务文本仍用自然语言。接入前核对当前result store对派生表的注册、恢复和权限路径，避免新增一套结果注册表。

预期：减少人工抄代码列表、重复前50及再次筛选，改善前N指标对齐。不能预先承诺省几轮。

验收：300行上选前10再读PE/ROE，精确命中该10只；并列、缺值、空集、续聊复用、跨owner拒绝；旧原始引用和普通分页不变。名称和通用机制不要写死“股票前10”。

### P1-B：让完整范围与展示范围更容易区分

职责：Catalog/工具说明SOFT + 执行覆盖事实HARD。

做法：先核查常用provider是否一致遵守已有 `limit=-1`；Catalog由唯一真源解释默认限制、全量与展示分页。若系统确知来源总量/截断状态则直接提供已有覆盖事实；不能把“恰好100行”推断成已截断，不能为了完整默认无限查库。

对明确排名/总体筛选，Skill按全体候选范围表达需求，程序在完整已存数据上筛选；不添加“出现前10就自动limit=-1”的关键词规则。

验收：简单5日行情不增加调用，组合筛选不再先100再全量；query/window/聚合各自语义不被混同，超大查询仍遵守既有资源约束。

### P1-C：补上长字段与文档的定向读取

职责：HARD结果读取能力，SOFT决定读哪里。

做法：复用现有artifact文本读取能力，如现有入口无法覆盖，再给读取协议增加少量可选定位参数，表达result_ref、行/字段和字符范围。只针对显式文本读取使用字符分页，保留普通表格分页的行语义；返回实际位置、总长度与剩余事实，原始内容不变。

新读取片段应按同一预算交付，并允许游标前进；不能再截断成同一个开头。数值表不提高全局字符上限，研报也不整篇自动灌入模型。

验收：关键证据放在2400字符之后且只在指定列，模型可取到；重复请求同一段一致、越界正常、跨会话拒绝；无须读取长文本的题目无额外成本。

### P1-D：让重复调用保护与真实恢复一致

职责：HARD调用保护；采用现有错误分类，不以自然语言关键词推测网络异常。

做法：成功且无新增事实的相同调用继续阻止或复用已存结果；参数错误依旧要求修正。只有已有恢复标记确认可重试的基础设施失败，才在当前总预算内允许有限相同参数重试。先盘点provider/MCP/loop已有重试，避免多层乘法重试。

验收：暂时失败后原参数成功、确定性参数错误不可原样死循环、成功结果不重复查、fast仍遵守原有无修复语义。先用fixture证明，再决定是否真的需要改guard。

### P1-E：把回答质量与阶段提示作为独立SOFT实验

做法：明确程序统计和模型解释的职责。计数/排序/单位运算优先使用已有确定性执行能力；不足时再评估通用计算能力，不能直接开放任意代码执行。方法说明由Skill维护，区分“数据直接支持的判断”和“待验证解释”，不新增每题审查模型。

对未提交预算提示单独比较：当前每次变化注入全文、变化时仅给简短余量、关键边界才提醒。主要目标是证据完整下的总消耗与完成率，不是单看输入缩短。最终回答reasoning配置可再做独立对照，不与其他改动混测。

验收：统计总体、单位换算和因果取证三个维度独立评分；简单取数不被强迫加载Skill；接口结果正确但summary错误仍判效果未通过。

### P2：测量后实施的机会

| 方向 | 最小做法 | 为什么排在后面 |
|---|---|---|
| 目录重复加载 | 先统计相同Catalog revision/方法的重复；当前已支持历史执行包复用，优先修复复用失效原因 | 重写旧日志会破坏前缀缓存；目录内容可能已被压缩，不能只见一个加载标记就认定契约仍在模型上下文 |
| 字段名重复编码 | 小样本比较row-dict与可逆列式表格，仅投影层变化 | JSON可逆不代表模型理解无损，数值/空值/列对齐需验证；原始协议保持不变 |
| 结果读取与恢复 | 同一scope、同一不可变ref采用有界物化缓存，或按需恢复引用，先测耗时/RSS | 当前filter/order每次完整物化并排序，续聊恢复会读取历史结果；300行未必值得改架构 |
| worker/session生命周期 | 测独立请求与续聊增长；验证SDK/原生卸载和持久恢复后，再定回收策略 | 不能直接清空亲和映射，不能把磁盘文件保留量当内存泄漏证据 |
| 真正工具并行 | 先验证不共享可变状态的目录读取，再考虑有限独立查询 | result别名分配、tracker、catalog刷新、DB池有共享状态；MCP bridge也需正式表达并发安全，read-only数据库不等于并发安全 |
| 通用compaction | 只有长续聊接近实际模型窗口时再试，保留近期目标/反馈/结果索引并测试恢复 | 原生摘要多一次模型调用；head/tail pruner可能剪掉执行包中间的关键约束，且改早期历史影响缓存 |

## 6. 不建议现在采用的做法

- 全面切fast、继续统一降低reasoning或maxTokens：已有历史修复能力下降的证据。
- 把总工具额度再扩大当主要优化：上限不保证更完整，也可能增加尾延迟。
- 强制todo或逐题must清单：计划文字不能证明金融条件满足。
- 加一个回答审查Agent：额外延迟与消耗确定，纠错收益尚未证明；先处理证据供给和确定性计算。
- 默认上PTC/任意Python/SQL替代finance_query.steps：当前已有受控执行协议，另造执行面会扩大权限、审计和错误面。
- 默认对子目录/历史取摘要、简单删旧tool结果：会丢契约、影响续聊与缓存；先精确去重和可恢复寻址。
- 直接把所有金融MCP工具标为并发安全：原始数据只读仍可能修改会话引用、tracker和连接状态。
- 为完成控制再建一套业务状态机：继续以已有执行事实和SOFT解释衔接。

## 7. 分批验证方案

第一批：固定本地SDK/Node构建、Fin Agent工作区diff、Catalog revision和有效配置；运行无模型故障fixture，确认deadline、重试与异常证据。保留冻结CC基准。

第二批：在隔离工作区选取6类小样本，每次只改变一个机制。已有历史题优先，不为候选方案另造有利题目。

| 类别 | 核查重点 |
|---|---|
| 简单5/10日行情 | API/窗口/行数，是否无故多读目录/Skill |
| 多条件总体筛选/前N | 候选覆盖、交集、排序、前N指标关联 |
| 长文本Skill分析 | 后半段证据可读性、真实引用、结论限制 |
| 零行/部分失败/准备性查询 | 不早停、不把失败算零行、成功前缀保留 |
| 显式续聊、改条件、离题后回来 | 历史语义、结果归属、Catalog更新、输入不串轮 |
| 同参数暂时失败、超时、队列满 | 有限恢复、有界退出、证据完整、后续请求可用 |

真实模型阶段建议每题每配置至少重复3次并交错执行，减少顺序/缓存干扰；这是筛选实验，不作为稳定准确率或p95估计。行情会变化，确定性结果先用同一保存资产复核，实时端到端另记数据时点。

第三批：只有候选方案效果不退化后，再做固定workload的并发/长稳/恢复。对1、worker数、超过worker数的负载分别记录吞吐、排队、端到端分位数、RSS、DB连接及失败；选择足够请求数后才报告p95，不能从十几条样本外推。

统一指标：

- 效率：端到端、入场/worker排队、启动、每步模型、工具关键路径、最终交付耗时；并行跨度不能简单累加。
- 消耗：核心/外层模型次数分开、未缓存输入、缓存输入、输出、reasoning子集、失败已知消耗；供应商费率核实后才换算费用。
- 稳定性：完成/失败/超时/取消真实原因、worker回收、重启恢复、资源增长。
- 健壮性：部分失败保真、合理重试、身份与引用隔离、晚到事件处理。
- 效果：实际API/时间/单位/范围、名单/数值、汇总口径、因果取证、缺口说明；HTTP200和工具成功不是业务通过。

采用门槛：协议正常流、兼容输入、真正严重错误回归通过；小样本每个下降项查明原因，不允许用平均速度掩盖数据覆盖损失；再决定扩大验证或上线。所有生产操作遵守人工Gate。
