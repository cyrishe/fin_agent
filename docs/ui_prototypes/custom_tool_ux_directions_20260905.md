# 自定义金融工具：四种交互方向与推荐组合

日期：2026-09-05。范围：界面、对话、反馈与验证体验；不实施生产代码或协议变更。

## 结论

建议采用 **B「共同编辑的逻辑文档」作为主工作空间，A「对话卡片」作为轻量入口，C「样例教学」作为核对与纠错方式，D「实验对比」按需进入**。

这不是同时开发四套流程。四个原型是四种信息组织方式，便于讨论取舍。最终产品可共用现有工具资产、修订、运行记录和 Surface Renderer；对话始终可用，不把导航标签变成必须逐个确认的关卡。

最重要的变化是：用户不再只是不断确认模型的描述，而是围绕一份当前有效的逻辑、几个真实可核对的结果，以及修改前后的差异进行合作。

该推荐是基于现有代码和外部实践的设计判断，尚未经过用户可用性实验。原型使用人工构造数据和预设交互，没有调用模型、金融 API 或回测；自由文本只作本页演示留言，不伪装成真实语义理解。

## 1. 从当前产品出发

本轮定向检查了三个当前组件：

- [DesignArtifact](../../frontend/src/components/renderers/DesignArtifact.tsx)：已有目标首屏、核心规则、流程和折叠详情。可以继续使用，不必把整份设计改为大表单。
- [InteractionRenderer](../../frontend/src/components/renderers/InteractionRenderer.tsx)：已有选项与自然语言补充通道。问题主要在何时问、问什么、确认范围是什么，而不在是否有选择按钮。
- [CustomToolTestWorkbench](../../frontend/src/components/renderers/CustomToolTestWorkbench.tsx)：已有固定候选版本、输入表单、运行与诊断。当前主结果仍是“测试通过”、输入/运行/业务/输出状态及 JSON；用户难以直接核查某一数值为什么正确。

本轮没有启动生产系统做新的全链路仿真，不以原型演示证明系统已经具备相应能力。更广泛的代码问题见 [前一轮研究](../development_tasks/custom_tool_strategy_review_and_plan_20260905.md)。

## 2. 交互要建立的五种认知

| 用户需要知道 | 首屏应该回答 | 不应混淆为 |
| --- | --- | --- |
| 系统理解了什么 | 目标、决定结果的规则、关键默认值、输出示例 | 一篇泛化需求文档 |
| 系统准备怎么算 | 关键公式、窗口与边界，一条带数字的推导 | 工程模块列表或模型思维过程 |
| 实现当前做到了哪里 | 当前模块、真实已完成事项、失败点及可操作下一步 | 无依据的百分比、“正在深度思考” |
| 数值是否正确 | 输入、独立期望、实际结果、差异、覆盖范围 | 程序没报错、模型说正确 |
| 工具是否有用 | 相对于用途与对照的证据、限制和不利结果 | 计算通过就有投资价值 |

语义确认、数值核对、有效性研究是三个不同问题。不能合成一个“业务通过”或一个总置信分。

### 用户已表达清楚时，第一轮应该输出什么

不是再问一遍已经回答的问题，也不是把所有细节变成选择题。理想首屏是一份可直接修改的“理解镜像”：

> **回踩 EMA20，不明显放量。**
>
> 给定股票范围和交易日，筛出：
> 1. 收盘价与 EMA20 的绝对偏离不超过 2%；
> 2. 当日量不超过此前 5 个交易日均量的 1.5 倍，均量不含当天。
>
> 返回是否符合、两个指标值，以及符合/不符合的原因；数据不足单列。
>
> 建议按收盘后、同一复权口径计算。这里只做筛选，不包含交易执行。

关键阈值和排除规则不能一概藏进详情。“已明确”和“系统建议”在表达上区分；只有真有影响结果的歧义时才插入一个局部问题。没有歧义，就提供“按此实现”或自然语言继续，不制造确认仪式。

### 选择题的恰当边界

- 适合：两三种合理理解确实会改变核心结果，且选项能解释各自影响。
- 不适合：用户已明确、可从上下文确定、低风险可说明默认值、当前无需决定的技术细节。
- 每次只聚焦当前最重要的少量问题，通常一到两个；这是表达指导，不是新系统校验。
- 选项不是唯一合法输入；可自由描述、说“先用建议”、暂缓，或先问一个相关问题。
- 涉及真正缺失的执行信息，清楚说明缺哪一项与为什么不能执行；仍允许讨论，不锁死整段对话。
- 确认按钮写清对象：“这份逻辑符合我的意思”“保留这条样例”“采用候选版本”，不使用含义模糊的连续“确认”。

## 3. 六个环节应如何组织

| 环节 | 默认看到什么 | 用户怎么反馈 | 系统回什么 | 完整细节在哪里 |
| --- | --- | --- | --- | --- |
| 确定需求 | 目标、决定性规则、预期结果示例、关键假设 | 直接改一句话；真正歧义处选项 | 合并后的当前理解与本次变化 | 约束、输入输出、边界 |
| 逻辑与设计 | 关键公式、一条数字推导、主流程 | 点某条问“为什么”；指定另一口径 | 影响了哪条规则与哪些结果；不重复全文 | 数据源、时间窗口、模块与验收 |
| 实现 | 按模块更新的实现摘要和真实进展 | 要解释、暂停、补充或改需求 | 已完成/失败/未做事项；范围变化的影响 | 代码、技术日志与诊断 |
| 正确性 | 独立期望与实际对照、失败优先 | 点一个值或一条结果说“不对” | 原始依据与推导；是口径、数据还是实现差异 | 数据快照、版本、容差、参考算法 |
| 微调 | 修改对象、保持不变的部分、同输入对比 | 调参数、改规则、补正反例、撤回 | 新候选或新实验，及受影响证据 | 完整差异、回归结果与历史 |
| 有效性 | 评测目的、对照、适用范围、证据限制 | 换评价目标；查看分组；保留/不采用 | 支持/不支持/证据不足的有依据结论 | 样本划分、分布、成本和偏差检查 |

这些是可来回查看的工作对象，不是必须顺序完成的 UI 状态机。例如解释需求时就能看一个样例，实现之后仍能修改需求；只修改显示文案不要求重新验证数值。

### “计算正确”的最小可读证据

统一案例采用此前 5 日成交量 `[80, 90, 100, 110, 120]`，当天 `160`。

- 正确均量：100；量比 1.6；不符合 ≤ 1.5。
- 故意错误的窗口：`[90, 100, 110, 120, 160]`；均量116；量比约1.3793；错误地符合。
- 用户应在一屏看见这个差异；点击之后再查看数据窗口、公式、版本与运行标识。
- 这是固定样例的数学证据，不代表 EMA、数据源、所有边界和整个工具都已经正确。
- 期望值必须注明来源。模型提出的期望如果未经独立核对，只能标作建议，不能与独立参考值同等展示。
- 业务口径变更需要重新审视相关期望，但不能为了让测试通过而改掉旧期望、覆盖旧结果。

### “有效”必须先明确工具用途

- 数据查询/信息工具：覆盖、时效、来源、缺失表达和查找效率。
- 计算指标：口径一致、参考实现一致、稳定性、可解释性及实际使用价值；不默认要求预测收益。
- 筛选/信号工具：是否符合专家意图、覆盖和排除是否合理；若有预测目标，再做样本外区分度研究。
- 交易策略：在明确成交、持有、退出、仓位、成本与限制后，交给回测模块评估。不能从一个筛选器自行补出完整策略。

## 4. 原型 A：对话卡片，最接近当前系统

**中心对象：一轮轮对话中的业务卡片。**

需求以三五条理解镜像出现；设计展示必要公式和一个例子；实现以过程卡片更新；测试在消息中展示差异；微调只展示本次补丁与复算；有效性以另一张研究卡片说明。

可交互原型提供需求、方案、实现、核对、微调、有效性六个片段。默认需求明确，不额外发问；内置可选展示变体用于查看真正有方向歧义时的局部选择题。

- 优点：学习成本低；移动端友好；改动更贴近现有 Renderer 与对话框。
- 缺点：多轮长对话后仍可能找不到当前权威版本；对照多个规则、多个实验时需要来回翻。
- 最适合：简单工具、第一次创建、短周期修改。
- 不能只做：美化 Markdown，却仍把多次相互矛盾的方案留在聊天历史里，让用户自行判断哪个有效。
- 应补充：置顶当前资产摘要和“查看当前完整逻辑”的稳定入口；历史消息展示其对应版本。

## 5. 原型 B：共同编辑的逻辑文档，推荐主方案

**中心对象：一份持续更新的工具说明书；对话围绕具体对象发生。**

默认右侧或主区是当前逻辑，左侧或折叠区是对话。用户可以点规则、指标值、某次结果或某个变更，再自由反馈；系统知道反馈指向什么，不要求用户复述整套需求。

需求和设计不是两篇必须分别确认的长文：先有简短目标和判断规则，再逐步补充计算约定、实现方案和证据。精确的公式与数据依据可展开；界面不要求把自然语言文档拆成多层业务 JSON。

原型可以选择三条不同规则查看推导、确认语义范围、查看错误实现、演示修订与同样例前后对比。移动端改为上下布局。

- 优点：当前逻辑始终可找到；局部修改定位清楚；需求、代码和证据之间更容易建立引用关系。
- 缺点：比纯聊天有更多视觉组织；小屏需要良好折叠；不应变成让业务用户手工维护复杂规格的编辑器。
- 最适合：绝大多数需要多轮澄清、精确计算和持续微调的工具。
- 关键设计：正文是完整自然语义；规则锚点只是引用与反馈定位，不是重新发明业务状态机。规则是否已经被确认、核对过应由现有资产与证据推导，不能靠模型每次重复声明。
- 失效处理：修改公式后，原核对结果仍可看，但明确“来自旧口径”；未变化内容不必重新确认。

## 6. 原型 C：样例教学台，差异较大的方向

**中心对象：应该命中、不应命中、暂时无法判断的具体案例。**

当用户很难写完整公式、但能指出“我想要这种，不要那种”时，系统先拿几个真实或明确标注的合成案例帮助表达。选择结果后，展示相应规则建议；出现矛盾时指出冲突，不暗中改规则。

实现前的案例成为验收线索，实现后仍拿同一案例比期望与输出；修正留下版本化样例。除了教过的案例，还要用没有参与修改的样例复核，不能把记住例子误认为理解了需求。

原型提供普通、错误窗口、恰好边界三个样例。可以给标签、只写意见或“不确定”；独立公式期望与用户标签分栏保留。

- 优点：最容易发现“文字理解看起来一致，实际判断不同”；特别适合专业用户隐性经验的外显化。
- 缺点：少量案例不能完整描述规则；用户标注也会有噪声和冲突；存在迎合样例、过拟合案例的风险。
- 最适合：形态筛选、规则含糊、结果纠错、边界确认。
- 不适合单独承担：现金流折现、组合计算等复杂公式的完整规格。此时仍需 B 的精确计算说明。
- 必须区分：用户偏好标签、独立数学期望、实际代码输出；三者冲突是讨论入口，不能合成一个 pass/fail 掩盖原因。

## 7. 原型 D：实验对比工作台，面向频繁微调

**中心对象：在固定条件下比较不同假设、参数和候选版本。**

用户说“把 1.5 改成 2 试试”，系统先理解这是临时试算、改变默认值，还是修改算法；能根据上下文判断时不要机械追问。界面明确告诉用户本次动作的范围，正式版本不随试算变化。

实现没有改变时复用代码；代码改变时形成候选。默认比较同输入、同数据的差异：多选了谁、少选了谁、为什么、哪些旧证据仍然适用，而不是直接给两条收益曲线。

原型可以拖动上限，重算八个人工构造样例的命中集合与手工设定的后续表现，并展开逐例差异。所有“后续表现”均为合成值；样本外一栏明确未运行，不能形成真实效果结论。

- 优点：非常适合“微调—比较—判断—保留”的高频循环；不覆盖当前工具；不把多次试算混成一段聊天。
- 缺点：新用户容易被研究界面压倒；参数搜索可能诱导追逐样本内最优；需要可靠的历史数据与运行留存作为基础。
- 最适合：指标参数敏感性、筛选条件比较、策略研究和正式回测交接。
- 必须保留：全部尝试、固定对照、未用于调参的留出区间、数据与版本引用、无法得出结论的情况。
- 边界：回测模块负责真实交易评测；本工具界面负责选择版本、说明研究假设、展示关联证据，不重复建设回测引擎。

## 9. 共同必须设计好的异常与反馈

1. **需求变更**：指出本次改了什么，当前代码和测试证据是否仍适用。原结果可追溯，不静默覆盖。
2. **结果不对**：从选中值直接进入数据、公式、期望与实现差异；先确定是口径、数据还是代码，再讨论修改。
3. **预期也不确定**：允许“待核对”。没有独立参考就不宣称正确，提供可执行的核对建议。
4. **运行失败**：说明哪一步失败，已完成什么，保留现场；可重试/改输入/继续解释，不清空整个工具。
5. **运行很久**：根据真实模块事件更新；不编造百分比。用户可查看已有结果。暂停、恢复按钮只有底层确实支持时才开放。
6. **普通问题插入**：自然回答；当前工具、版本和未处理反馈保留，返回时给一句简短上下文。
7. **错误纠正**：把一次纠正变成可重复核对的案例；本轮解释不能作为下一轮唯一记忆。
8. **有效性不佳**：可以明确报告“逻辑按要求实现，但没有观察到稳定效果”；用户可以继续研究或保留为分析工具，不强行优化出好看的结果。

需要展示的是业务推导、原始依据、计算过程与执行记录，不是要求展示模型内部思维链。

## 10. 推荐的讨论与开发顺序

先讨论 B 的第一屏和局部反馈，再决定是否保留左右分栏；A 可以作为同一资产的轻量对话呈现，不另建一套业务流程。

建议顺序：

1. **理解镜像与规则定位**：明确需求首屏、关键口径、局部修改和确认范围。没有证据体系也可先验证阅读体验。
2. **可核对结果与样例纠错**：把 C 的具体案例和期望/实际差异嵌入 B；替换宽泛的“业务通过”表达。
3. **实现反馈与修订对比**：按真实模块事件呈现，明确当前版本、候选和过期证据。
4. **实验与有效性**：基于可靠的版本、运行和数据引用，接入 D 与回测模块。

这里只提出需求，不在本轮新增后端状态、字段或协议。未来如需稳定引用具体规则、样例、运行，应先检查现有资产和 Surface 引用能否满足；确实需要程序精确寻址时才增加最小引用，不为了 UI 扩写业务 Schema。

## 11. 如何判断原型是否真的更好

优先用相同任务比较 A 与 B，再单独验证 C 和 D 的价值，避免一次拿四个完整工作流让用户疲劳。测试顺序交错，避免后看者因熟悉案例获利。

建议让业务用户完成五项任务：

1. 阅读明确需求后的第一屏，复述系统会选什么、不选什么、如何计算。
2. 发现“均量含当日”错误，指出依据；不预先提示错误位置。
3. 只把上限改为 2，确认哪些逻辑没有变化、是试算还是正式采用。
4. 询问一个通用指标问题后返回，找回当前候选与待处理意见。
5. 面对计算核对通过、样本外未验证的结果，解释是否已经证明投资有效。

记录：找到当前逻辑所需时间、关键口径理解错误、发现植入错误的比例、修正轮数、是否误判“已正式采用”、是否误判“已证明有效”，以及需要反复翻历史的次数。暂不编造目标提升比例或原型评分。

验收的优先级：**不会误解已经验证的范围 → 能定位并修正错误 → 当前版本清楚 → 阅读负担和对话轮数降低**。界面漂亮与点击少，都不能弥补误以为工具正确的风险。

本轮产出为讨论稿和四个可操作界面原型；尚未进行业务用户可用性研究，不做实施承诺或生产正确性保证。
