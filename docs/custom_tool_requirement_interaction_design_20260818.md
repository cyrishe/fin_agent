# 自定义工具 Requirement 交互设计

日期：2026-08-18

状态：交互设计结论，作为 Requirement 阶段后续优化与测试的依据。

## 1. 结论

Requirement 阶段的核心产物不是表单，也不是对用户原话的改写，而是一份可供双方共同检查的**需求共识稿**。

当用户已经用自然语言把需求说清楚时，系统应当完成三件事：

1. 压缩并重组信息，让用户快速看出系统理解的目标、核心判断和预期结果。
2. 将容易误解的逻辑关系显式化，例如“同时满足”“满足其一”“先筛选后排序”。
3. 给用户清晰的纠错入口；没有真实歧义时，不制造问题，不展示空的待确认区域。

推荐采用“双层共识稿”作为默认形态：

- 首层展示目标、决策路径和结果形态，适合快速阅读。
- 展开层展示完整业务口径和行为样例，适合逐条检查。
- 只有真正会改变结果的局部歧义，才在对应位置提供选择题。
- 所有选项都保留自然语言补充入口，按钮不替代语义理解。

这仍然遵循 `SOFT -> HARD -> SOFT`：LLM 负责形成自然、准确、可纠正的需求共识；系统只保存修订号、资产归属和交互动作等必要事实。

## 2. Requirement 阶段的任务边界

### 应当完成

- 说明用户最终要解决的问题和使用场景。
- 说明用户会提供什么业务输入。
- 说明哪些业务条件决定入选、排除、分类或排序。
- 说明用户最终会得到什么结果，以及结果应具备的解释能力。
- 明示系统采用了哪些用户未直接说出、但可以合理推定的业务理解。
- 只对缺少答案就会改变需求含义或无法形成有效设计的问题提问。

### 不应提前完成

- 不选择具体数据 API、字段映射或 K 线聚合方式。
- 不设计代码模块、类、函数或查询语法。
- 不为了显得完整而增加用户没有提出的业务规则。
- 不把格式偏好、展示细节或低风险边界全部升级为阻断性问题。
- 不要求用户通过固定口令才能继续，也不使用文字关键词判断阶段。

## 3. 好的需求共识稿应解决什么

用户阅读后，应能快速回答：

1. 系统理解的目标是不是我的目标？
2. 哪些条件决定入选、排除和排序？
3. 系统有没有擅自补充业务条件？
4. 如果有一处不对，我能不能直接指出具体哪一句？

Requirement 的质量不应按“信息是否足够多”衡量，而应按以下结果衡量：

- 用户可以快速判断整体理解是否正确。
- 决定性逻辑不会埋在大段文字里。
- 后续 Design 不需要重新阅读原始对话才能理解需求。
- 用户的一句自然语言修正能够形成新的完整共识稿，而不是残留问答记录。

## 4. 推荐的默认结构

这不是强制填写的模板，而是生成和渲染时的内容优先级。没有内容的部分不展示。

### 4.1 默认展开层

#### 标题

使用能够表达工具用途的短标题，不使用“需求确认表”等表单化名称。

#### 目标摘要

用一小段话回答：用户准备在什么场景下，用这个工具得到什么结果。

#### 决策路径

用自然语言或紧凑路径表达决定结果的核心逻辑，重点显式区分：

- 必须同时满足的条件；
- 满足其一即可的条件；
- 过滤条件与排序条件；
- 计算结果与人工判断；
- 单次结果与持续监控。

#### 结果形态

说明最终返回什么，以及用户为什么能够理解或复核结果。不要在 Requirement 阶段自行扩张为完整字段清单。

#### 理解来源

仅在必要时简短说明：

- 本次没有增加新的业务条件；或者
- 系统采用了哪些合理但非用户原话的理解。

### 4.2 展开层

#### 完整业务口径

保留用户明确提出的范围、周期、指标、阈值、方向、先后关系和结果要求，作为后续 Design 的完整事实来源。

#### 预期行为

用少量行为样例暴露容易误解的关系，例如：

- 全部过滤条件满足时进入候选。
- 任一必要条件不满足时排除，即使排序指标很高。
- 通过过滤但排序在结果数量之外时，不进入最终结果。

行为样例用于确认理解，不是 Coding 阶段的运行测试，也不应虚构真实市场结论。

## 5. 三种内容原型

以下原型可以按工具复杂度组合，不应作为三套永久模式暴露给用户。

### 原型 A：结果导向共识稿

适合目标和条件简单的查询、计算或筛选工具。

```markdown
### 我理解你要做的工具

在指定交易日和股票池中，寻找靠近 EMA20、出现长下影止跌形态，
同时没有明显放量或大幅下跌的强势候选股。

股票需要同时满足：
1. 收盘价与 EMA20 的偏离不超过 2%；
2. 下影线长度至少是实体的 2 倍；
3. 当日跌幅不超过 5%；
4. 当日成交量不超过 5 日均量的 1.5 倍。

通过筛选后，按 10 日涨幅从高到低返回前 10 只，
并说明每只股票的关键指标和入选原因。
```

优点是简洁直接；不足是复杂需求中的逻辑关系仍需要用户从文字中提取。

### 原型 B：决策路径共识稿

适合选股、交易信号、预警和策略类工具，推荐作为此类工具的主体表达。

```markdown
### 我准备按这条路径理解

输入交易日和股票池
-> 判断收盘价是否在 EMA20 上下 2% 范围内
-> 判断下影线是否达到实体的 2 倍
-> 排除当日跌幅超过 5% 的股票
-> 排除成交量超过 5 日均量 1.5 倍的股票
-> 对剩余股票按 10 日涨幅降序排列
-> 返回前 10 只，并解释每只股票的入选依据

前四项是必须同时满足的筛选条件；
10 日涨幅只负责排序，不参与前面的淘汰。
```

它能直接暴露条件方向、组合关系以及筛选和排序的边界。

### 原型 C：行为验收共识稿

适合规则组合复杂、仅靠复述不容易发现理解偏差的需求。

```markdown
### 系统应当表现为

- 一只股票满足四个筛选条件时，进入候选列表；
- 只要其中一个条件不满足，即使 10 日涨幅很高，也不能入选；
- 股票满足筛选条件但 10 日涨幅排名在第 11 名之后时，
  不进入最终结果；
- 对最终入选股票，需要展示关键指标及其对应的入选理由。
```

行为样例应围绕最可能出现理解错误的地方，不为所有想象中的边界情况建立清单。

## 6. 推荐组合：双层需求共识稿

默认首屏建议为：

```markdown
### 长下影止跌候选工具

你希望在指定交易日和股票池中，筛选出靠近 EMA20、
出现长下影止跌形态，且跌幅与量能受控的股票，
再按照近期强弱选出优先候选。

**判断路径**
靠近 EMA20 -> 长下影成立 -> 跌幅不过大 -> 成交量不过度放大
-> 按 10 日涨幅排序

**最终结果**
返回前 10 只，并展示关键指标和每只股票的入选原因。

本次理解没有额外增加新的业务条件。
```

首屏操作：

- `按这个需求继续设计`
- `修改某条规则`
- `查看完整口径`
- 常驻的自然语言输入框

“查看完整口径”展开具体阈值和条件关系；对复杂规则再展示“预期行为”。按钮表达明确动作，但不能把用户锁在当前流程。用户输入任何自然语言时，仍走正常语义理解，并携带当前需求资产作为上下文。

## 7. 局部选择题的使用方式

选择题是降低表达成本的辅助交互，不是 Requirement 的主体，也不是新的状态机。

### 适合使用选择题

- 不同口径都会形成合理工具，但会明显改变结果。
- 存在少量行业常用选项，用户可以快速判断。
- 选项之间的差异和影响能够用一句话说清楚。
- 缺少该答案会导致需求含义不确定或无法形成有效 Design。

### 不适合使用选择题

- 只是询问“是否继续”。
- 用户原话已经给出了明确答案。
- 只是实现方式、接口能力或字段映射问题。
- 低风险默认即可继续，并且后续可以自然修正。
- 为了让交互看起来完整而罗列大量参数。

### 推荐表达

选择题应紧贴受影响的规则，并说明每个选择对结果的影响：

```markdown
### 还有一个口径会影响筛选结果

“板块明显强于市场”目前没有明确量化方式：

- 板块涨幅超过大盘 1%：信号相对较多
- 板块涨幅进入全市场前 20%：更适应不同市场环境
- 暂不量化：在结果中展示，留给用户人工判断

也可以直接告诉我你自己的定义。
```

候选项可以标示系统推荐，但推荐理由必须来自当前业务语义，不能只因为它排在第一位。

## 8. 收到修正后的交互

用户修改一处规则后，系统应当：

1. 更新完整 `requirement_brief`，保持其为当前唯一事实来源。
2. 首屏优先展示本轮改变了什么，以及改变后的完整决策路径。
3. 不保留生硬的“问题—回答”记录作为后续输入。
4. 不要求用户重新确认未受影响的全部内容。

推荐表达：

```markdown
已按你的反馈更新：量能条件从“不超过 1.5 倍 5 日均量”
改为“不超过 2 倍 5 日均量”。其他判断保持不变。

更新后的路径：……
```

这里的“其他判断保持不变”由系统基于上一修订保存的完整事实得出，不要求模型重新发明或重复用户已经确认的信息。

## 9. 与现有协议的关系

现有输出结构已经足以承载该方案：

- `requirement_brief`：保存完整、自然语言化的需求共识稿。
- `notice`：保存系统采用的少量合理业务理解，并在界面中贴近对应内容展示。
- `questions`：只保存真正需要用户决定的局部问题和候选项。

当前阶段不需要新增：

- `requirement_status` 等业务状态枚举；
- 一套新的表单字段树；
- 按需求类型拆分的大量固定模板；
- 依靠关键词或按钮矩阵决定用户能否继续的路由规则。

确认按钮属于明确的交互动作；修订号、权限、归属和生命周期仍由系统负责。需求内容、解释方式和用户修正继续由 SOFT 语义承载。

## 10. 生成与渲染要求

### 生成侧

- 先给结论，再给细节。
- 优先重组逻辑，不逐句复述用户输入。
- 决定性规则尽量控制在用户一屏可检查的范围内；复杂细节使用展开层。
- 不输出空的 notice 或 questions 章节。
- 不用“需求已完整”“信息充分”等自我评价代替需求内容。
- 不把 Design、数据映射或实现方案提前写入 Requirement。

### 渲染侧

- 默认展示目标摘要、决策路径和结果形态。
- 将完整口径和行为样例作为渐进展开内容。
- 选择题紧贴相关歧义，不集中成独立表单页。
- 操作按钮与自然语言输入同时存在。
- 用户输入文字时，按钮只作为上下文信号，不绕过顶层语义理解。

## 11. 验收与拟真测试

Requirement 优化完成后，至少使用以下场景验证：

1. **需求完全明确**：不提出额外问题，产出一屏可读的双层共识稿。
2. **只有一个关键歧义**：只在对应规则处展示一个选择题，并保留自然语言输入。
3. **存在多个低风险缺口**：采用合理理解继续，不把所有缺口升级为阻断问题。
4. **用户自然语言修正**：准确更新受影响规则，其他内容保持不变。
5. **按钮与文字同时提交**：以文字语义为主，按钮作为当前资产和动作上下文。
6. **中途询问普通金融问题后返回**：仍能恢复完整需求共识，不要求用户重新开始。
7. **复杂组合逻辑**：用户能够从决策路径识别“同时满足、满足其一、过滤、排序”的故意错误。

体验目标：

- 用户快速浏览即可判断系统是否理解了自己的目标。
- 用户认真检查时可以定位到具体条件或逻辑关系。
- 用户可以用一次点选或一句自然语言完成修正。
- 后续 Design 可以直接使用保存后的 `requirement_brief`，无需再次解释原始需求。

## 12. 后续实施顺序

1. 先调整 Requirement Skill 的生成目标，使其稳定产出目标摘要、决策路径、结果形态和必要的行为样例。
2. 再调整 Requirement 卡片的渐进展示和局部选择题布局。
3. 最后通过少量拟真样本验证自然语言修正、选择题提交和跨话题恢复，再进入全量回归。

实施时应优先调整 SOFT 生成和 Renderer，不先修改底层协议。只有真实测试证明现有结构无法稳定传递必要事实，才考虑最小的兼容性协议扩展。
