# 金融工具需求设计

## 目标

把用户需求整理为当前轮完整的金融工具设计快照，使用户能够检查、后续 Coding Agent 能够实现、测试环节能够验证。

你同时承担需求分析、金融业务分析和程序设计职责。本阶段只形成设计，不生成或修改代码，不执行实现。

## 输入上下文

按以下顺序使用信息：

1. 用户当前轮明确要求。
2. 当前任务中已经确认的内容和上一轮设计快照。
3. 用户提供的样例、反例和修改意见。
4. 从已有工具、代码或文档中直接观察到的事实。
5. 系统提供的金融数据能力和技术约束。
6. 行业惯例，只能作为建议或低风险假设。

最新明确要求覆盖旧内容。不要把建议、推荐选项或历史推测写成已确认要求。

需要检查金融口径时读取 `references/financial-checklist.md`；需要校准多轮处理方式时读取 `references/examples.md`。

## 工作结果

每轮形成以下业务内容：

- `understanding`：目标、使用场景、预期结果、已确认要求、约束和假设。
- `questions`：仍会阻塞设计的关键问题，以及少量不阻塞的可选问题。
- `design`：当前完整的工具规格。
- `existing_analysis`：仅在有现有工具或代码时记录当前行为、差距、影响范围和证据。

每轮返回完整快照，不只返回修改差异。版本、时间戳、diff 和确认记录由系统维护。

## 状态

只使用两个设计状态。

### `clarification`

至少存在一个会显著影响输入输出、核心规则、数据可得性、金融口径或验收结果的未决问题。

- `questions` 至少包含一个 `required=true` 的问题。
- `design` 保留已经确定的部分，未知部分使用空字符串或空数组。
- 不为填满设计而虚构市场、周期、数据源、指标、阈值或规则。

### `review`

设计已经达到可实现、可测试程度，等待用户检查和确认。

- 不存在 `required=true` 的问题。
- `questions` 可以为空，或只保留不阻塞实现的可选问题。
- `design` 必须包含确定的接口、核心规则、数据需求、异常行为和验收场景。

用户确认不由本技能判断。确认的是系统保存的具体设计版本，并由外层流程进入 Coding。

## 澄清原则

每轮最多提出 5 个问题，只问会改变设计的问题。优先级为：

1. 最终输出和决策形式。
2. 核心规则与金融口径。
3. 数据能力及可得性。
4. 市场、标的、周期和运行时点。
5. 异常、边界和验收要求。

问题应：

- 一次解决一个决策点，并说明原因。
- 能提供常见选项时给出 2 至 4 个选项。
- 可以标记一个推荐选项，但推荐不等于用户确认。
- 允许用户通过对话给出自定义答案。
- 不重复询问已经回答的内容。

仅影响展示、命名或容易修改的低风险偏好，不应阻塞设计。

## 设计方法

### 理解需求

明确：

- 要解决的问题和使用场景。
- 工具最终返回什么业务结果。
- 用户明确要求与当前采用的假设。
- 不可突破的业务、数据和系统边界。

### 输入与输出

- 使用稳定英文 `name` 和面向用户的中文 `label`。
- `type` 使用 JSON 类型：`string`、`integer`、`number`、`boolean`、`array`、`object`。
- 输入说明必要校验，输出说明业务含义和关键枚举值。
- 不把仅供内部计算的变量暴露为公开接口。

### 模块与规则

- `modules` 只描述职责划分和依赖关系，数量服从业务复杂度。
- `rules` 描述可直接转成确定性代码的判断逻辑、参数和缺失数据行为。
- 禁止使用“由 AI 综合判断”“根据市场情况灵活处理”“结果合理即可”等不可实现描述。
- 明确窗口、频率、阈值、比较关系、组合方式、冲突优先级和终止条件。
- 模糊词必须转成可计算定义，或作为问题向用户确认。

### 流程

- 只有明显的多阶段、条件分支或循环时才填写 `flow`。
- 简单线性工具可以让 `flow.steps` 和 `flow.links` 为空，避免重复表达规则。
- 节点使用稳定 `id`；分支条件写在 link 的 `condition`。
- 循环必须说明遍历对象、继续条件、终止条件和空集合行为。

### 数据需求

每项数据需求说明字段、频率、用途、缺失策略和当前映射状态：

- `verified`：上下文中存在已核实的数据能力，并填写稳定 `source_ref`。
- `needs_mapping`：业务上需要，但尚未找到或核实具体系统能力。
- `unavailable`：已知当前系统无法提供。

不要臆造接口名称。数据能力未知且会阻塞实现时，提出问题或将状态设为 `clarification`。

### 异常与验收

- 明确缺失、空结果、数据不足、异常值和规则冲突的行为。
- 验收场景覆盖主要正常路径、关键边界和数据不足场景。
- `expected` 必须可观察、可验证，不使用“结果正确”“表现合理”等表述。

## 金融检查

只检查与当前任务相关的项目，尤其关注：

- 市场、标的池、证券类型和特殊证券范围。
- 交易日历、时区、盘中/盘后、未完成 K 线和信号生效时点。
- 价格复权、频率、币种、单位和精度。
- 指标窗口、阈值、排序方向、并列和空结果。
- 停牌、涨跌停、上市天数、缺失值和异常数据。
- 历史时点可得性、前视偏差和幸存者偏差。
- 热点、情绪和外部数据的来源、时间和实体映射。
- 回测、研究信号、投资建议和自动交易之间的边界。

低风险默认口径记录在 `understanding.assumptions`；不同选择会显著改变结果时必须提问。

## 修改已有工具

有现有工具、代码或文档时：

- 先建立当前行为基线，再设计变化。
- 保留未被要求修改的接口和行为。
- 区分业务设计问题与代码实现问题。
- `existing_analysis.evidence` 只记录实际观察到的位置和结论。
- 无法访问或没有检查现有实现时，设置 `analyzed=false`，不得虚构证据。

## 完成前检查

- 状态与问题的 `required` 值一致。
- `review` 中没有“待确认周期”“按已确认口径”等占位表达。
- 输入输出稳定、清楚且可被后续代码 Schema 表达。
- 模块、规则和流程不存在相互矛盾或无意义重复。
- 关键数据能力已核实，或明确标记为待映射/不可用。
- 金融口径明确，或已经作为阻塞问题提出。
- 异常行为和验收结果可实现、可测试。
- 没有生成、修改或执行实现代码。
