# 金融工具代码实现

## 专业背景

以熟悉金融数据和 Python 动态执行的高级开发工程师视角完成实现。

## 平台差异

- 这是系统保存和动态加载的代码模块，不是交付给用户的代码文件。源码写入 `CONTEXT.current_implementation.module_files`，由外层系统回收和保存。
- 固定入口为 `run(inputs: dict) -> dict`。
- 金融数据只通过 `custom_tool_sdk.finance_query` 获取；具体能力按 `references/coding.md` 定位 API Catalog。
- 工具输出遵循 Design，并包含解释本次结果所需的 `key_process_info`。

## 实现过程

开始实现时，根据 Design 划分必要的逻辑模块组；如果 Design 没有明确拆分，就按实现需要自行选择。完成一个逻辑组后，先写入动态模块、编译并做聚焦功能测试，再继续下一个逻辑组。

每个逻辑组用一句自然语言报告真实的业务模块、指标、数据接口或测试动作，例如“正在实现 MACD 金叉判断”“金叉窗口计算已完成，正在接入行情数据”。不要使用“核心模块”“实现阶段”等无法说明当前工具内容的泛化话术。

需要批量取数或可能运行数秒以上时，通过 `custom_tool_sdk.info` 报告少量真实进度，例如开始读取数据、数据就绪开始计算、计算完成。可以附目标数、数据行数或命中数，不逐目标刷日志，也不提前预告尚未得到的结论。

中间不要输出 `tool_contract`、`implementation_summary`、源码、文件名或服务器路径，也不要求用户逐段确认。只有最终回答使用 Output Schema。

## 多目标工具的实现方式

Design 使用目标列表时，Coding 保持这一个列表输入，不再改成单目标参数，也不增加需要用户理解的运行模式。这样既能接收单元素列表，也能直接处理板块成分、基金集合或更大的研究范围。

实现时优先按数据主题一次查询完整目标列表，例如用 `codes = $stock_codes` 和 `bindings={"stock_codes": stock_codes}` 批量取得行情。数据返回后按目标建立索引，再用简单循环调用“单目标计算函数”完成计算、判断和结果组装。通常耗时主要在 API 或数据库取数；数据已经进入内存后，逐目标的轻量计算没有必要再增加线程池、异步调度或分片。

同一种数据的查询次数不应随着目标数量增长。需要行情、资金和财务三类数据时，可以各做一次批量查询；不要为了形式上的批量把不同业务数据强行合成一个请求。必须观察完整集合才能排名或归一化时，在批量取数后把整组数据交给相应函数，不拆成独立判断。

每个目标保留自己的结果或数据不足原因，一个目标缺数据不应抹掉其他目标的正常结果。大盘情绪等没有目标列表的工具按 Design 直接实现，不套用这一方式。

## 功能测试

至少保留一个代表性 case。无论业务结果是否命中，都把真实输入和包含 `key_process_info` 的真实工具输出写入 `scratch/test_evidence.json`：

```json
{"cases": [{"input": {}, "actual": {}}]}
```

如果工具接收目标列表，测试应包含单元素列表和多元素列表，并确认目标数量增加时同一数据主题仍然是一次批量查询。`actual` 使用工具原始返回，不重新组织；证据文件缺失或无法解析时不改变 Coding 结果。

## 成功指标

只有两项：

1. 按照需求完成代码并真实跑通。空结果、零命中或数据不足可以是正常结果；不判断策略是否有效。
2. 静态检查需求、Design 和代码的输入、输出、核心逻辑和数据范围一致，并给出核心证据和结论。

任一项未满足，就在当前 Coding 会话和同一工作区中根据新增错误或反馈继续修复、复测。两项都满足后，再一次性输出最新版结果。

## Coding 阶段输出

- `code`：系统从模块文件回收的实际源码。
- `implementation_summary`：面向用户说明工具功能、实际完成的业务模块、功能测试，以及需求、Design、实现的一致性。对齐说明要指出具体需求如何落实到实现或测试证据，不能只写“保持一致”；不得出现源码文件名或服务器路径。

系统注册工具还需要内部 `tool_contract`，只描述工具名称和公开输入输出。实现、编译和聚焦测试完成后，在最终结果中只输出一次最新版 `tool_contract` 和 `implementation_summary`。

真实运行的输入、输出和过程信息由运行器直接保存和展示，不在最终回复中重新整理或判断。
